## §A — Usage-Signal Capture (per turn)

```
turn completes ──▶ existing turn-close seam (where action_log is assembled)
                        │
                        ▼
          Profiling.UsageEvents.write (additive table, local SQLite)
            {decision kind, action name, confidence band, outcome class,
             model profile/role, surface, timing bands}
            ── NEVER message bodies, prompt text, or secrets (schema-level)
                        │
          retention sweep (max_rows / max_age_days) ── kill switch honored
```

Joined raw material (read-only, unchanged): `conversation_messages.
action_log`, `objective_events`, `scheduled_job_runs`, traces where the
operator enabled them.

## §B — Distill → Suggestion Cards

```
[profiling.distill managed job fires]      (or on-demand distill action)
  │   profiling.distill.enabled=false ──▶ NO-OP (proven)
  ▼
distill_usage_profile (registered action via Jobs → Actions.Runner)
  ├─ reads §A store + joined sources          (local only; zero egress)
  ├─ aggregates: turn-time bands per role/profile, fallback rate,
  │              steering-correction rate, repeated-prompt classes
  └─ bounded local-model assist only (ADR 0089 LD-R5 posture)
  │
  ▼
suggestion cards (existing suggestion store, additive types, INERT)
  {evidence aggregate + sample refs, concrete proposed change,
   predicted benefit, allowlist key or draft kind}
  │
  ├─ workspace Suggestions panel (cards now have handlers)
  ├─ CLI mix allbert.profiling suggestions
  └─ optional §E delivery of the redacted headline (default OFF)
```

## §C — Confirmed Customization (the only effectful path)

```
operator clicks Apply on a card (web) | CLI apply <id>
  │
  ▼
apply_suggested_customization (registered; confirmation: :required
                               AND safety-floor-pinned by action name)
  ├─ re-reads the card; proposed key ∈ shipped ALLOWLIST?
  │     ── no ──▶ DENIED (never reaches confirmation)
  ▼
durable confirmation created — renders the EXACT before→after diff
  │
  ├─ operator approves (web / typed command / button; free text never)
  │     ──▶ Settings.put with audit + linkage {suggestion_id, confirmation_id}
  ├─ operator denies ──▶ suggestion marked dismissed (writer added)
  │
  ▼
applied; card shows "applied <date>"; revert available via the same path
```

Allowlist categorically excludes: permissions.*, security policy, egress
and fallback gates, provider credentials.

## §D — Effectiveness Feedback

```
next distill run
  ├─ for each applied customization: before/after windows on the touched
  │  dimension (from §A data) ──▶ delta written onto the suggestion record
  ▼
panel: "applied 12 days ago — decide p50 −18%"   (display only)
  └─ operator may one-click revert ──▶ §C path in reverse; measured again
```

No automatic rollback; measurement informs, never acts.

## §E — Proactive Suggestion Delivery (ADR 0084 amendment)

```
distill completes with new cards
  │
  ▼
Channels.Notify.deliver(kind: :suggestion, headline-only payload)
  ordered gate: live-use → suggestions_enabled (DEFAULT false)
              → quiet_hours window → suggestion_max_per_day
              → throttle → Security policy → exact-origin binding
  ├─ any gate fails ──▶ ledger row suppressed {reason}, audited
  └─ pass ──▶ NEW message (never edit): redacted headline + surface pointer
              — never evidence body, never an approval affordance
```

Approval always happens on the ordinary confirmation surfaces (§C).

## §F — Per-Role Model Resolution

```
purpose key (direct_answer task list, coding.model_profile, router keys…)
  │            may now reference role aliases
  ▼
model_roles.fast|capable|thinking.profile  ──▶ Settings.Models (existing)
  ▼                                             │
ADR 0088 catalog rows (chooser renders roles)   ▼
                                    resolved profile → ReqLLM (unchanged)
```

A pure naming layer: unchanged purpose keys behave identically; remaps
only through §C.

## §G — Security Eval Rows (`:v14`, gate-bound, behavioral)

`:v14` enum lands first; distinct assert sets; production-boundary
execution; meta-contract sweep.

| Row id | Proves (at the production boundary) | Expected |
|---|---|---|
| `v14-suggestion-inert-001` | rendering + accept-click alone changes no setting, executes no action (only a confirmation record exists) | `dropped` |
| `v14-apply-confirm-required-001` | invoking apply without an approved confirmation is refused; the safety-floor pin holds even with the action contract adversarially set `:not_required` | `denied` |
| `v14-apply-allowlist-001` | a card targeting a non-allowlisted key (e.g. `permissions.settings_write`, `models.fallback.allow_local_to_hosted`) is refused before any confirmation is created | `denied` |
| `v14-usage-store-redaction-001` | a turn containing a seeded secret + long prose yields a usage event with no body/secret content (schema + value assert at the write boundary) | `allowed` + redaction assert |
| `v14-distill-zero-egress-001` | a full distill run makes zero external transport calls | `allowed` + zero-egress assert |
| `v14-notify-suggestion-default-off-001` | new cards with `suggestions_enabled` unset → zero transport sends; suppressed ledger row | `dropped` |
| `v14-notify-quiet-hours-001` | opted-in channel inside the quiet-hours window → suppressed/deferred per class semantics; ledger reason recorded | `dropped` |
| `v14-role-remap-spine-001` | a role remap mutates settings only through §C (registered action + confirmation + audit); direct suggestion-driven write attempt refused | `denied` |

## §H — Focused Operator Validation (FV, end of implementation)

**Source pre-filter, then packaged acceptance (AGENTS.md R2). v1.4 is the
first release to use this ordering.**

- **Source pre-filter** — before any binary exists, exercise FV-01..FV-04 from
  `mix allbert.*` against real configured providers. This is a *cheap filter*
  for obvious breakage, not acceptance. It opens after **preflight** is green,
  not after an aggregate.
- **Packaged FV is the acceptance bar** — FV-01..FV-05 are re-run on the real
  artifact and the real host. FV-05 additionally covers what only packaging can
  break. Nothing is accepted from source.

Why acceptance stays packaged: across v1.0.3, v1.0.4, v1.0.5 RC.1, and v1.3,
**every** defect that operator/host validation caught was packaging or host
integration, and none would have reproduced from source — v1.0.4's Chrome abort
reproduced only in the exact packaged configuration. See test-strategy.md
§ "Release Sequence And Re-Run Scope".

Standing preconditions: disposable Homes (`mktemp -d`) only; no
`set -e`/`exit`; paste-exact steps with inline PASS criteria;
provider/credential failures = `BLOCKED`.

**Corrective loop.** A defect caught by the source pre-filter is fixed and
re-proven through **preflight + the owning lanes** — no aggregate, no rebuild.
A defect caught in packaged FV requires a replacement generation; that is the
cost the pre-filter exists to reduce, not eliminate. The authoritative aggregate
runs once, and only if the change class requires it (R4).

Setup:

```sh
export ALLBERT_HOME="$(mktemp -d /tmp/allbert-v14-fv.XXXXXX)"
export V14_EVIDENCE="$HOME/allbert-validation/v1.4-$(git rev-parse --short HEAD)"
mkdir -p "$V14_EVIDENCE"
git rev-parse HEAD | tee "$V14_EVIDENCE/candidate-sha.txt"
```

Seed real usage (one warm TUI session, ~15 minutes): repeat a handful of
quick-lookup prompts, a few multi-step asks, and at least two corrections
of Allbert's choices, so the store has honest signal. Do not use
synthetic scripts beyond the paste-exact prompts the plan publishes.

### FV-01 — the flagship loop, live

Run the distill once (`mix allbert.profiling distill` or the landed CLI
route). Open the Suggestions panel; screenshot as `FV-01-cards.png`.
Pick one settings-class card; click Apply; approve the confirmation
after reading the diff; verify with `allbert settings get <key>`.

PASS: at least one card exists with visible evidence (aggregate +
sample refs) and a concrete proposed change; Apply produced a durable
confirmation showing the exact before→after; nothing changed before
approval (read the key mid-flow); after approval the key changed and
the audit log links suggestion → confirmation → write; the card shows
"applied". FAIL if any change occurred without the confirmation step.

### FV-02 — denial edges + dismissal, live

On the same Home: dismiss one card and verify its status; then attempt
the two denial edges — (a) craft/apply a card targeting a
non-allowlisted key (the plan ships a fixture card for exactly this),
(b) approve-then-revert the FV-01 change and confirm the revert also
required a confirmation.

PASS: dismissal persists with provenance (no dead status); the
non-allowlisted apply is refused before any confirmation exists; the
revert path required its own confirmation and restored the prior value;
audit shows all four events. Record as `FV-02-denials.txt`.

### FV-03 — suggestion notification, one real channel

On a configured live channel (operator's own, e.g. Telegram): leave
`suggestions_enabled` unset and complete a distill that yields cards —
verify silence + a suppressed ledger row. Opt in
(`allbert settings set channels.telegram.autonomous_notify.suggestions_enabled true`),
set quiet hours to cover "now", distill again — verify suppression with
the quiet-hours reason. Clear quiet hours, distill once more — verify
exactly one new-message headline arrives with a surface pointer and no
approval affordance.

PASS: all three phases behave as stated; the delivered message contains
the redacted headline only; the per-day cap key reads back; credential
failure = `BLOCKED`. Evidence: provider screenshot + redacted monthly
audit copy as `FV-03-notify.*`.

### FV-04 — mobile stage 1, phone viewport

In a real browser at 390×844 (device emulation acceptable): walk chat
(send two messages; composer stays sticky and usable), the objectives
tree, Settings Central, and the memory review panel.

PASS: no horizontal scroll anywhere; all four surfaces operable
one-handed with visibly adequate touch targets; the mobile
shellbar/tabs navigate correctly; zero browser console errors.
Screenshots per surface as `FV-04-<surface>.png`.

**End of the source pre-filter.** FV-01..FV-04 above run from source before a
binary exists. They are a filter, not acceptance — all four are re-run on the
packaged artifact below.

### FV-05 — packaged acceptance, real artifact on the real host

Runs after the binary build and artifact smoke. **Re-run FV-01..FV-04 on the
packaged binary first**, then the packaging surface:

1. **Install / uninstall** — signature verification, install, clean uninstall
   leaving no stray service or Home residue.
2. **Service lifecycle** — `allbert serve` start/stop under launchd or systemd;
   survives logout/login on the real host.
3. **Vault** — the packaged binary resolves the OS backend (Keychain / Secret
   Service), not the encrypted-file fallback.
4. **TTY** — `allbert tui` from a real terminal: raw-mode input, redraw, and
   clean exit from the packaged launcher.
5. **License viewer** — `allbert licenses` renders with no toolchain present.
6. **ABI / relocation** — artifact loads on the minimum supported glibc and runs
   from a relocated install prefix.
7. **Browser/bridge path**, where the release touches it — the packaged bridge
   under the packaged BEAM, not direct Chrome or direct Playwright. v1.0.4's
   abort passed every one of those and failed only here.

PASS: FV-01..FV-04 behave identically from the packaged binary, and every
numbered item above passes on the real host. FAIL is a packaging defect and
requires a replacement generation — it is not patched around.

### Result template

```text
FV-<NN>: PASS|FAIL|BLOCKED
candidate_sha: <40-char SHA>
host/surface: <OS, surface, channel alias>
expected: <copied PASS clause>
actual: <redacted observation>
evidence: <path under $V14_EVIDENCE>
```

Release PASS requires FV-01..FV-04 attested at one candidate SHA, then
the release-rehearsal §§1–6 binary flow.
