## Vocabulary And Frozen Defaults

- A **terminal response signal** is the one terminal runtime result returned
  for a user-owned turn: `completed`, `denied`, `failed`, `cancelled`, or
  `assistant_persistence_failed`. Background jobs do not produce usage events.
- A **usage event** is the minimized typed projection of one terminal response
  signal. It is not a message, trace, or transcript.
- A **profiling suggestion** is an inert, user-owned card. Rendering, delivery,
  dismissal, or selecting Apply grants no authority.
- An **application operation** is the durable coordination record spanning the
  SQLite suggestion state, Settings YAML, and append-only Settings audit.
- An **observed outcome** is a descriptive before/after association. Allbert
  never describes it as causal evidence or says a customization "helped".

| Setting | Default | Validation and effect |
|---|---:|---|
| `profiling.enabled` | `true` | Master analysis switch. `false` stops capture and all distillation, while status, retention, and confirmed clear remain available. |
| `profiling.usage_events.enabled` | `true` | Capture-only switch. `false` stops new events but does not disable retention, status, or clearing. |
| `profiling.usage_events.max_rows` | `10_000` | Integer `1_000..1_000_000`, applied per user. |
| `profiling.usage_events.max_age_days` | `90` | Integer `7..365`, applied per user. |
| `profiling.distill.enabled` | `false` | Controls the managed job only. An explicit on-demand distill remains available while `profiling.enabled=true`. |
| `profiling.distill.cadence` | `weekly` | Managed-job cadence; operator-tunable through Settings Central. |
| `model_roles.{fast,capable,thinking}.profile` | `nil` | An unconfigured role is skipped with a redacted diagnostic; existing concrete purpose chains continue unchanged. |
| `prompt_rules.direct_answer.useful_factual_and_brief.variant` | `default` | Closed enum `default|balanced_detail`; every other rule is non-tunable and has no variant setting. |
| `channels.<id>.autonomous_notify.suggestions_enabled` | `false` | Separate opt-in for this notification subject. |
| `channels.<id>.autonomous_notify.suggestion_max_per_day` | `1` | Per user, channel, and `operator.timezone` calendar day. |
| `channels.<id>.autonomous_notify.quiet_hours` | unset | Optional `{start: HH:MM, end: HH:MM}` local-time interval. |

## §A — Terminal Turn → Minimized Usage Event

```text
user-owned turn reaches one terminal response signal
  │
  ├─ profiling.enabled=false ───────────────▶ do not capture
  ├─ profiling.usage_events.enabled=false ─▶ do not capture
  ▼
UsageEvents.write_once(response_signal_id)
  ├─ derive typed values at the runtime/action boundary
  ├─ reject arbitrary prose and secret-bearing values
  ├─ insert idempotently in local SQLite
  └─ prune the same user's rows by age and count in a bounded transaction
       │
       ├─ success ─▶ update redacted health state
       └─ failure ─▶ update redacted health state; never fail the user turn
```

Exactly one row may exist for a `response_signal_id`. A retry after a process
crash or persistence error is an idempotent no-op once that identifier exists.
The user is resolved from the principal attached to the turn; a missing or
unverified user makes the event ineligible rather than assigning it to a
default user.

### Typed event contract

| Field | Contract |
|---|---|
| `id` | Stable event identifier. |
| `user_id` | Required owner; every read and prune predicate includes it. |
| `thread_id` | User-owned thread identifier, when present. |
| `message_id` | Assistant message identifier; nullable only for `assistant_persistence_failed`. |
| `response_signal_id` | Required unique idempotency key. |
| `request_signal_id` | Correlation identifier for the initiating user signal. |
| `terminal_outcome` | Closed enum: `completed|denied|failed|cancelled|assistant_persistence_failed`. |
| `intent_class` | Registry-bounded intent name or `unknown`; no model prose. |
| `action_class` | Registry-bounded action/capability name or `none`; never parameters or output. |
| `action_outcome_class` | Closed enum: `none|allowed|denied|failed|cancelled`. |
| `confidence_class` | Closed enum: `not_measured|low|medium|high`. |
| `fallback_class` | Closed enum: `none|same_endpoint|cross_endpoint|failed`. |
| `steering_class` | Closed enum: `none|operator_corrected|operator_retried`. |
| `model_profile` | Concrete resolved profile name or `none`, never a role alias. |
| `endpoint_class` | Typed provider/endpoint/locality tuple or `none`; no URL or credential. |
| `surface` / `channel_id` | Registered surface and channel identifiers; no external address. |
| `duration_ms` | Integer milliseconds clamped to `0..86_400_000`. |
| `prompt_length_band` | Closed enum: `empty|1_80|81_240|241_1000|1001_plus`. |
| `prompt_fingerprint` | HMAC-SHA256 over NFC-normalized, trimmed, whitespace-collapsed prompt text. |
| `inserted_at` | UTC timestamp. |

The fingerprint key is a random 256-bit per-Home secret held through the
existing secret boundary. It is never logged, exported, rendered, or placed in
Settings. Normalized prompt text exists only during event construction and is
discarded after HMAC calculation. The fingerprint supports equality classes;
it is not a reversible or portable prompt identifier.

The schema and writer categorically reject prompt text, message or response
bodies, snippets, trace payloads, action parameters/results, model prose,
external channel addresses, credentials, and arbitrary metadata maps. Existing
conversation messages, objectives, jobs, and traces are not copied into this
table.

Pruning runs at application startup and after a successful insert. It deletes
that user's rows when either `inserted_at` is older than `max_age_days` or the
newest-first count exceeds `max_rows`; each transaction uses a bounded batch.
Retention continues when capture is paused.

The first eligible operator surface shows a non-blocking, versioned disclosure
before or with its first captured turn: profiling is local and default-on, what
the typed store contains, what it never contains, the retention defaults, and
how to inspect, pause, clear, or change retention. A user-owned disclosure
receipt prevents repetition but is not consent or authority. `profiling status`
reports settings, row/card/outcome counts, oldest/newest timestamps, and the
redacted writer-health state; Settings Central and `allbert.settings`/
`allbert admin settings` provide the pause and retention controls.

## §B — Deterministic Distill → Dedicated Suggestion Records

```text
managed cadence fires                         operator requests distill
  │ profiling.distill.enabled=false ─▶ no-op          │
  └────────────────────────────────────────────────────┘
                         │ profiling.enabled=false ─▶ refused/no-op
                         ▼
distill_usage_profile (registered action via Jobs → Actions.Runner)
  ├─ reads only the user's typed usage events
  ├─ may join user-scoped typed objective/job outcome projections
  ├─ performs deterministic bounded aggregation; zero model/provider calls
  ├─ applies sample floors, cooldown, and dedupe
  └─ inserts inert profiling suggestion cards
```

ReviewCadence-style reconciliation keeps one reserved job per user:
`enabled=false` means paused with no effective due time; `enabled=true` resumes
the configured cadence; changing cadence while disabled updates the reserved
schedule without resuming it. On-demand distill does not change job state.

Distillation never reads conversation/message/trace bodies and has zero
egress. v1.4 has no model-assisted distillation path. Synthetic data may prove
the algorithm in automated tests but is never evidence that the product made a
useful recommendation. Metric version 1 uses the most recent 10–50 eligible
events from a window no longer than 14 days; fewer than 10 or an ambiguous
aggregate emits no card. An emitted card expires 14 days after creation unless
it reaches another terminal state first.

Profiling cards use a dedicated user-scoped record behind the shared
Suggestions surface; they do not overload the draft-oriented tool-discovery
record. A card binds:

- stable `suggestion_id`, owner, revision, and card digest;
- kind and metric-version identifier;
- exact target key, expected current value, and proposed value;
- evidence aggregate, eligible sample identifiers/counts, and UTC window;
- allowlist or prompt-catalog digest used to construct it;
- stable dedupe key, creation time, expiry, and state.

Card states are `open`, `confirmation_pending`, `applied`, `dismissed`,
`expired`, `stale`, and `reverted`. Allowed transitions are:

```text
open ─▶ confirmation_pending ─▶ applied ─▶ reverted
  ├──────────────▶ dismissed
  ├──────────────▶ expired
  └──────────────▶ stale
confirmation_pending ─▶ dismissed|expired|stale
```

`dismissed`, `expired`, `stale`, and `reverted` are terminal for that card
revision. An `applied` card never reopens and may move only to `reverted` through
the confirmed revert action. A matching dismissed or expired suggestion is
suppressed for 30 days; a changed current target value changes the dedupe key
and may yield a new card sooner.

Surfaces:

```text
source:   mix allbert.profiling status|distill|suggestions
packaged: allbert admin profiling status|distill|suggestions
web:      Workspace Suggestions panel, rendered from the same records
```

The panel uses a LiveView stream with a stable container id and stable per-card
DOM ids. It renders and dispatches registered actions; it owns no Settings,
confirmation, profiling, or security semantics.

## §C — Confirmed Compare-And-Set Customization

The exact allowlist is:

- `operator.communication_style`
- `operator.handoff_detail`
- `channels.<registered-id>.response_style`
- `model_roles.{fast,capable,thinking}.profile`
- `prompt_rules.direct_answer.useful_factual_and_brief.variant`

Cadence, diagnostics, accessibility, resource-limit, permission, security,
credential, provider-egress, and fallback-policy keys are excluded. A wildcard
outside the one registered channel response-style shape is not an allowlist.

```text
Apply(card id, revision)
  │
  ▼
apply_suggested_customization (registered action; confirmation: :required;
                               action-name safety-floor pin)
  ├─ verify user ownership and state=open
  ├─ verify card revision/digest, target, value, evidence version, expiry,
  │  allowlist/catalog digest, and role/prompt-specific constraints
  ├─ reject before confirmation on any mismatch
  ▼
durable confirmation with exact before → after
  ├─ binds suggestion revision, expected-before, proposed-after,
  │  target version, allowlist/catalog digests, and expiry
  ├─ deny/expire ─▶ card dismissed/expired; no write
  └─ approve ─▶ resume the same registered action through Actions.Runner
                  │
                  ▼
           durable application operation prepared
                  │
           Settings lock + binding revalidation + compare-and-set
                  │
           Settings YAML write + append-only audit metadata
                  │
           SQLite finalize (card applied; outcome pending)
```

Confirmation approval is idempotent by confirmation id. The application
operation has a unique confirmation id and stable operation id, so double
resume cannot produce a second Settings or audit write. Under the same Settings
lock that performs the write, the action re-reads the current target and every
bound digest. A changed value or definition marks the card `stale`, writes
nothing, and requires a newly generated confirmation.

Application-operation states are `prepared`, `applied`, `recovery_required`,
`reverted`, and `failed`. SQLite-local card, operation, and outcome changes use
one `Ecto.Multi`. YAML and markdown audit are outside that transaction:

- `prepared`: durable intent exists; no success is claimed and the Settings
  result is not yet finalized;
- `applied`: CAS write, audit linkage, and SQLite finalization agree;
- `recovery_required`: Settings may have changed but audit/linkage is incomplete
  or ambiguous;
- `reverted`: a separately confirmed CAS restored the recorded before value;
- `failed`: the operation is terminal and Settings is proven unchanged.

1. Persist `prepared` before acquiring the Settings lock.
2. Compare-and-set Settings and append an audit entry carrying stable
   entry/operation/suggestion/confirmation identifiers.
3. Finalize SQLite records as `applied` only after the Settings write and audit
   both report success.
4. If Settings changed but audit or SQLite linkage did not complete, return
   `recovery_required`; never report success and never perform a blind rollback.
5. Startup and a managed reconciliation pass inspect `prepared` and
   `recovery_required` records. An unchanged expected-before value with no
   audit may safely fail/retry; an expected-after value with a matching audit
   finalizes; an expected-after value without audit remains recovery-required
   until the idempotent audit append succeeds; any third value requires
   operator review.

Revert is a separate registered, safety-floor-pinned, confirmation-required
action. Its confirmation binds the application operation and exact
applied-value → prior-value diff. It succeeds only while the setting still
equals the applied value; an intervening edit produces `stale` with no write.
There is no automatic rollback.

Surfaces:

```text
source:   mix allbert.profiling apply|dismiss|revert <suggestion-id>
          mix allbert admin confirmations approve <confirmation-id>
packaged: allbert admin profiling apply|dismiss|revert <suggestion-id>
          allbert admin confirmations approve <confirmation-id>
web:      card actions → ordinary durable confirmation surfaces
```

`clear` is itself a confirmation-required registered action:

```text
source:   mix allbert.profiling clear
packaged: allbert admin profiling clear
```

An approved clear deletes the user's usage events, profiling suggestions, and
observed outcomes. It retains Settings, application operations, confirmations,
and security/Settings audit history. Raw Allbert Home backups may contain
profiling rows; the portable redacted export contains schema/version and counts
only. Uninstall preserves Allbert Home. Only an explicit purge against a
disposable or operator-confirmed Home removes it.

## §D — Observed Outcomes, Never Causal Claims

Each successful application creates an outcome in `pending`. The next distill
selects the nearest eligible events before and after the application time,
bounded to 14 days per side, capped at 50 events per side, and truncated to
equal sample sizes. Fewer than 10 eligible events on either side yields
`insufficient_data`.

Samples match the card's user, affected surface/channel, concrete profile or
role where relevant, and typed outcome class. A second applied customization
that touches the same metric dimension during either window, or a profile/
endpoint change not represented by the card, yields `confounded`.

Outcome states are:

- `pending`: the post window has not reached ten eligible events;
- `insufficient_data`: a completed 14-day window lacks the sample floor;
- `confounded`: a concurrent relevant change prevents a clean comparison;
- `observed_improvement`;
- `observed_regression`;
- `no_clear_change`.

Every display names the dates, equal sample counts, metric, before and after
values, and detected confounders. Copy says "observed after this change" and
never "caused", "proved", or "helped".

Metric mapping is closed:

| Customization | Primary comparison | Guardrail / descriptive context |
|---|---|---|
| Communication, handoff, or channel response style | Steering-correction rate; a movement of at least 5 percentage points determines direction. | Response-length distribution is descriptive only. |
| Model role | Median duration; a relative movement of at least 10% determines direction. | Any failure/fallback-rate worsening of at least 5 percentage points makes the outcome `observed_regression`. |
| Prompt variant | After ten eligible turns, an operator records the typed card-level rating `better|same|worse`. | Response length and steering-correction rate are descriptive only. |

Movement below the stated floor is `no_clear_change`. The typed prompt rating
maps directly to improvement/no-clear-change/regression. Reverted changes
retain their observed history and may accumulate a separately labelled
post-revert comparison; they never trigger an automatic action.

## §E — Per-Role Model Resolution

```text
purpose chain item: role:fast | role:capable | role:thinking
  │
  ▼
Settings.Models resolves model_roles.<role>.profile
  ├─ nil / missing / disabled profile ─▶ skip alias + redacted diagnostic;
  │                                    continue the existing purpose chain
  └─ configured concrete profile ─────▶ existing profile validation and ReqLLM
```

Only the exact `role:` prefix introduces aliases. Role values may name concrete
configured profiles only, never another role, so cycles are unrepresentable.
Existing purpose chains containing concrete profiles remain byte-for-byte and
behaviorally unchanged.

Suggestion-driven remaps require the proposed profile to have the same
provider, endpoint, and locality tuple as the current resolved profile. A
missing current role, disabled proposed profile, or local/hosted or endpoint
change is denied before confirmation. Operators may still make broader model
configuration changes through the ordinary explicit Settings path and its
existing security rules; profiling receives no such authority.

## §F — Immutable Prompt-Rule Resolution

M4.5 inventories six `PromptEnvelope` callers plus the separately replayed
`Worker.QualityPolicy`. All catalogs implement one immutable rule-spec and
snapshot contract:

```text
RuleSpec    {catalog, rule_id, purpose, version, tunable?, variants}
RuleSnapshot{catalog, rule_id, purpose, version, variant_id,
             resolved_text, digest}
```

Resolution validates the Settings variant against the reviewed shipped set,
then computes a digest over the complete snapshot. Durable jobs and receipts
store the snapshot and replay it rather than consulting current Settings.
Untuned catalogs and rules resolve byte-identically to their pre-v1.4 text and
retain the same digest.

Exactly one rule is tunable in v1.4:

| Catalog / rule | Variant | Resolved text |
|---|---|---|
| `direct_answer/useful_factual_and_brief` | `default` | Existing shipped text, byte-for-byte. |
| `direct_answer/useful_factual_and_brief` | `balanced_detail` | `Keep the answer useful, factual, and direct. Include enough detail to answer the request completely, without unrelated material.` |

Every other rule declares `tunable?: false`. Free text, unknown variant ids,
and settings for non-tunable rules are denied before confirmation.

## §G — Explicit Suggestion Notification Enrollment And Delivery

`Channels.Notify` accepts a typed notification subject. Existing Objective
fan-out uses its Objective adapter; suggestion delivery uses a dedicated
profiling-suggestion adapter. It never fabricates an Objective.

Enrollment is a registered identity-reverified action with exact user,
channel, and external thread/target reference plus a target digest. It succeeds
only when the existing channel identity mapping proves that target belongs to
the user. Last activity is never an enrollment source. Email is not eligible in
v1.4.

```text
source:   mix allbert.profiling notify-enroll <channel> <target-ref>
          mix allbert.profiling notify-unenroll <channel> <target-ref>
packaged: allbert admin profiling notify-enroll <channel> <target-ref>
          allbert admin profiling notify-unenroll <channel> <target-ref>
```

```text
distill commits one or more new open cards
  │
  ▼
typed suggestion subject + exact enrollment
  ├─ no enrollment / email / suggestions_enabled=false ─▶ dropped ledger row
  ├─ inside quiet hours ─▶ one durable deferred row per target/window;
  │                       coalesce to "N suggestions ready"
  ├─ calendar-day cap consumed ─▶ dropped ledger row
  ├─ throttle or Security denial ─▶ dropped/denied ledger row
  └─ pass ─▶ reserve sending → NEW deterministic message
                ├─ acknowledged ─▶ delivered
                └─ ambiguous transport result ─▶ uncertain; no blind retry
```

Quiet hours use `operator.timezone`, are start-inclusive/end-exclusive, and may
cross midnight. Equal start/end is rejected rather than interpreted as an
un-deliverable 24-hour window. A missing/invalid timezone fails closed to no remote delivery
with a redacted diagnostic. Deferred work becomes eligible at the next valid
window edge. Time-zone-database resolution determines ambiguous/skipped DST
times; no fixed UTC offset is cached. Deferred rows do not consume the daily
cap. `sending`, `delivered`, and `uncertain` reservations consume the cap for
the local calendar day on which sending begins.

At the window edge, all still-open cards for one enrollment/window become one
deterministic, length-bounded, redacted message: "N suggestions ready" plus a
pointer to the Suggestions surface. It contains no evidence body, target value,
secret, confirmation command, button, or approval affordance. Approval remains
on the ordinary confirmation surfaces in §C.

## §H — Loopback And Mobile-Web Stage 1

M0 corrects the packaged production web bind to loopback by default. v1.4 adds
no authenticated or configurable non-local access; OAuth and non-local bind
hardening belong to v1.6.

Stage 1 acceptance covers Chromium and WebKit measured browser tests or device
emulation on the same host:

- 320 CSS-pixel reflow (including 400% zoom equivalence), 390×844 portrait,
  and 844×390 landscape;
- chat, objectives, Settings Central, memory review, and Suggestions;
- no two-dimensional or unintended horizontal scrolling;
- keyboard order, accessible names/status, visible focus, and focus not
  obscured by sticky bars;
- 200% text resize;
- WCAG 2.2 AA 24×24 minimum targets, with 44×44 as the preferred enhanced
  target rather than a blanket AAA claim;
- stable streamed DOM ids and zero browser-console errors;
- sticky composer visibility and usable viewport-height behavior.

All handwritten breakpoint blocks, including the 760px outlier, migrate to one
reviewed mobile-first convention. Tailwind breakpoint tokens use rem units;
`48rem` preserves the existing 768px role. Viewport-height declarations retain
`vh` fallbacks, prefer `svh` for stable layout, and use `dvh` only where live
browser-chrome resizing is intentional.

Physical-phone validation is not v1.4 acceptance. Real-device dynamic-toolbar
and sticky-composer proof remains in the operator-authorized responsive
information-architecture remainder because browser emulation does not reproduce
all mobile browser UI behavior. Stages 2–4 remain the operator-owned responsive
information architecture, offline-capable PWA, and native-shell backlog items.

## §K — Focused Operator Validation

Source validation is a cheap pre-filter. Packaged validation on provisional
artifacts is acceptance. Fakes, seeded malicious cards, canned providers, and
synthetic efficacy evidence remain automated-test-only.

Standing preconditions: use disposable Homes created by `mktemp -d`; use real
configured providers/endpoints and the operator's own channel account; do not
use `set -e` or `exit`; every runbook step carries an inline PASS criterion;
credential/provider absence is `BLOCKED`, not PASS.

```sh
export ALLBERT_HOME="$(mktemp -d /tmp/allbert-v14-fv.XXXXXX)"
export V14_EVIDENCE="$(mktemp -d /tmp/allbert-v14-evidence.XXXXXX)"
mkdir -p "$V14_EVIDENCE"
git rev-parse HEAD | tee "$V14_EVIDENCE/candidate-sha.txt"
```

Seed at least ten eligible real turns per measured class with one warm
`mix allbert.tui` source session (and `allbert tui` for packaged FV): repeated
quick lookups, multi-step asks, and explicit corrections. Paste-exact prompts
are allowed; scripts that inject events or cards are not.

## §L — Binding Release Order And Corrective Loop

The release order is:

1. `mix allbert.test preflight`, independent audit, and source FV.
2. `mix allbert.test release.v1`, then bounded
   `mix allbert.test release.v14`.
3. Build/qualify provisional artifacts and complete packaged FV across the
   assigned platform matrix.
4. Classify findings as environment, documentation, or executable. Correct
   environment findings in place and repeat their row; correct documentation
   with diff/docs gates and repeat affected instructions; batch executable
   findings once, then rerun preflight, affected lanes, `release.v1`, and
   `release.v14`, replace the entire generation, and repeat invalidated FV.
5. Run `mix allbert.test release` exactly once on the accepted post-FV clean
   SHA. It is mandatory because v1.4 changes Settings, confirmations,
   registry/security, and gate infrastructure.
6. Rebind candidate identity, signatures, checksums, SBOM/provenance, license
   viewer, install/uninstall, and package-smoke evidence invalidated by final
   artifacts; publish, rehearse installation, and close out.

Audit findings are classified before source FV. Executable audit findings are
batched and re-enter through preflight plus affected focused/static gates; the
aggregate is not an audit-remediation loop.

No aggregate runs during implementation, per fix, before operator validation,
or inside a versioned gate. `release.v14` contains only its bounded focused
steps and never nests `release.v13`, `release.v131`, `release.v1`, `release`,
precommit, or a full suite. Structure-owner tests prove the v1.3/v1.3.1 gate
definitions frozen and aggregate owner coverage complete.
