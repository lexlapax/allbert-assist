## Build-Start Bindings

M0 records the exact v1.3.2 tag and clean source SHA that v1.4 starts from. It
binds commands that already exist, freezes each planned interface contract, and
assigned every former command-binding slot to the milestone that produced that
interface. A proposed command name is not evidence and must not be added merely
to make a runbook look complete. The producing milestone replaces its own slot
with the literal command and inline PASS criteria; workstream G verifies all
source slots before R4 and all build/package slots before R4a/R4b.

Every automated, handoff, and operator row ends in exactly one result:

- `PASS` — the stated assertion passed on the recorded source SHA or artifact.
- `FAIL` — the assertion ran and found an executable or documentation defect.
- `BLOCKED` — the assertion could not run; the external dependency, missing
  interface, missing authority, or environment fact is recorded.

Only `PASS` crosses a serial milestone barrier. `FAIL` rejoins remediation;
`BLOCKED` is not converted to `PASS` by explanation.

## §B — Existing Runner Param Validation

ADR 0065's central seam already exists. v1.4 re-verifies it; v1.4 does not
invent a second param-enforcement response contract.

```text
action invocation -> Actions.Registry -> Actions.Runner.run/3
  -> ParamContract.normalize_and_validate(action_module, params)
       valid   -> action_module.run(validated_params, context)
       invalid -> Response.error(..., {:invalid_params, redacted_reason})
                  wrapped in the normal {:ok, response_with_runner_metadata}
                  action body is not called
```

Non-map params follow the same `:invalid_params` response-envelope contract and
never reach an action body. Raw rejected input is not echoed into diagnostics,
traces, or audit metadata.

M0 compares the registry-derived catalog, dispositions, and Runner tests with
the exact registered-action inventory. If it finds no gap, M2 is verification
plus coverage for actions added since v0.59. If it finds a gap, M0 names the
exact action, invocation path, missing disposition, and focused test; only that
recorded gap becomes implementation work. M2 also opens an append-only action-
delta ledger. Every action
introduced, removed, or moved by v1.4 records its module, id, pack/order,
exposure, param contract, Security placement, envelope owner, and test owner;
M15 regenerates the closeout roster and reconciles every delta before final
acceptance.
A presumed historical count or a
claim that the v0.59 set was partial is not an implementation input.

## §C — Direct PermissionGate Facade Retirement

`PermissionGate` is a compatibility facade over Security Central, not a second
policy authority and not part of param validation. The operator selected option
A on 2026-08-06: its retirement is a direct call-site migration:

| Compatibility call | Direct owner after retirement |
| --- | --- |
| `PermissionGate.authorize(permission, context)` | `AllbertAssist.Security.authorize(permission, context)` |
| Permission, approval-mode, and coding-tier vocabulary/helpers | `AllbertAssist.Security.Policy` |
| `PermissionGate.response_status(decision)` | `AllbertAssist.Runtime.Response.permission_status(decision)` |
| `PermissionGate.allowed?(decision)` | The same exact `%{decision: :allowed}` predicate; no truthiness expansion |

The direct authorization decision intentionally records
`source: AllbertAssist.Security`. That is the one approved observable change
from the facade, whose source was `AllbertAssist.Security.PermissionGate`.
Permission, normalized context, policy, risk, decision, reason,
`requires_confirmation`, denial behavior, confirmation behavior, and response
status remain invariant.

```text
before
caller -> PermissionGate.authorize -> Security.authorize -> decision
       -> PermissionGate.response_status / allowed?

after
caller -> Security.authorize -> decision(source = AllbertAssist.Security)
       -> Security.Policy helpers / Runtime.Response.permission_status
       -> exact :allowed decision predicate where needed
```

The ordered retirement is binding:

1. M0 freezes the complete production call-site inventory by caller family and
   records direct Security callers already present.
2. Red-first parity fixtures capture every distinct context construction,
   permission, allowed/confirmation/denied branch, response mapping, and
   confirmation-resume path. Non-action callers are included.
3. Call sites move directly to Security, Policy, and Runtime.Response. Param
   validation is neither added nor removed by this edit.
4. Parity asserts the full decision and response behavior, allowing only the
   intentional `source` change.
5. Static enforcement proves zero production references before the facade is
   deleted. It scans all application and plugin production roots, release and
   runtime configuration, dynamic module-name construction, and hard-coded
   source readers; moved tests/evals are updated or explicitly retained as
   historical fixtures. Adversarial rows prove no direct caller bypasses
   Security Central.

If a caller cannot preserve those semantics, M6 stops with `FAIL`; it does not
leave a partially retired facade or redesign authorization inside Runner.

**Implemented checkpoint.** The facade and Boundary candidate are deleted and
production roots contain zero references. A fixture bound to
`7ae566f59f74cb51d8aed77e2f51c3df80172e1f` records 295 authorization, 182

## §D — Action envelope consolidation

```
use AllbertAssist.Action, permission: :memory_write, name: "update_memory_entry", ...
  |
  +-- capability metadata (already stored today as capability/0)
  |
  +-- M3 PROVIDES:
        one canonical internal action response,
        centrally validated by Runner,
        macro defaults/builders for the common cases,
        explicit adapters for existing 1.x surface/wire contracts,
        and characterized overrides for genuinely specialized actions
```

**Operator decision (2026-08-07): one new response format inside, compatible at
the edge.** Every action and future Pack targets one canonical internal response
owned by the capability/action plane. Runner validates that contract centrally.
CLI, TUI, channel, plugin, and public-protocol serializers preserve frozen 1.x
wire behavior until a major release; M3 does not make a minor release silently
break external consumers.

The M0 inventory remains the denominator, but the implementation survey rejects
the earlier assumption that existing `action/3` helpers differ only by name and
permission. The 109 current `action/3` definitions form 40 structural groups:
15 are safe flat defaults, 68 require an explicit metadata-key option, and 26
are computed/redacted/conditional overrides. Likewise, only 30 schemas are the
exact standard four-key shape; 112 extend it and 139 do not carry the complete
base. M3 therefore captures the pre-conversion internal and external envelopes,
introduces the canonical contract and boundary serializers, converts only
proved-equivalent groups mechanically, and records every remaining adapter or
override with its behavioral reason. Contract tests then cover the canonical
format plus a bounded serializer matrix instead of forcing every future Pack to
exercise all historical implementations.

**Implemented handoff (2026-08-07).** Runner now normalizes and validates the
nine-field canonical response centrally. The Action DSL exposes the common
builders; 30 exact legacy schemas, 15 flat action entries, and 37 static
confirmation envelopes use them. The four-field M0 schema is explicitly named
`:legacy_standard_response` and retains its frozen digest; it is a pre-Runner
compatibility shorthand, not a second canonical format. The 68 metadata-key and
26 computed/redacted/conditional action-entry groups plus four confirmation
outliers remain explicit for the behavioral reasons identified above. Shared
surface rendering and OpenAI/ACP mappings retain their frozen payload/status
selection, and the real 281-action production shadow reproduces the exact M2
behavior digest and 837,405 canonical bytes. The remaining M3 handoff work is
the coordinated exact-clean acceptance rejoin, not another full legacy-action
test sweep.

R1 attempt 1 found one shipped status omitted from the new inventory:
`create_calendar_event` returns `:answer` for its established graceful
no-calendar-server path. `:answer` is an explicit success outcome in the same
nine-field canonical response, not a second format. This retains the frozen
v1.0 edge behavior until M15 establishes the v1.4 component contract.

R1 attempt 4 found one Runner-owned pre-dispatch rejection that still built the
old partial map. App-scope membership denial now uses `Response.denied/2` and a

## §F — Pack Discovery And Ordered Action Registry

M1 cannot derive the current registry from `Application.loaded_applications/0`:
OTP reports only application specifications already loaded into the application
controller, not every application present in the release. M0 first binds a pack
contribution contract that makes ownership and order explicit without
recreating a kernel-owned list.

M1.a realizes that contract through three serial handoffs:

1. **M1.a1 — boundary/projection:** create minimal `allbert_kernel` and
   `allbert_composition` applications, wire the downward release dependency
   graph, add kernel/residual descriptors and raw `.app` declarations, and prove
   source-catalog -> release membership -> raw `.app` agreement. Kernel pack
   order is `0`; residual order is `100`; composition and Web remain
   descriptorless. Owner-CWD loading, scope selection, lanes, version parity,
   license finalization, and the test manifest learn both new application owners
   in the same checkpoint. No readiness claim is made.
2. **M1.a2 — shadow registry:** capture one complete candidate through read-only
   legacy adapters and atomically finalize a shadow snapshot. Existing
   Actions/App/Plugin/Extensions registries remain authoritative and byte-for-
   byte behaviorally unchanged. No signal, cache mutation, child start, or
   dynamic-overlay write occurs during capture/finalization. Registry instances
   are private gate/test processes only; production supervision starts in M1.a3.
3. **M1.a3 — activation:** start Registry/Readiness under a kernel `:one_for_all`
   supervisor, start the coordinator in composition, split metadata discovery
   from runtime children, and admit every effect through one pack-owned
   activation gate. Health plus effect-capable Web/session and runtime-needing
   packaged CLI dispatch plus runtime-bearing release-eval validation consume
   the same readiness state; pure diagnostics and static surfaces retain their
   explicit exemptions.

Each M1.a checkpoint is one logical handoff represented by two adjacent commits.
The implementation commit is evidence SHA `A`; the immediately following
docs-only handoff commit records evidence about its parent and is never called
the tested implementation SHA. The exact sequence is:

1. Work red-first and reconcile implementation, tests, request flow, planned
   docs, owner/CWD inventory, fixtures, and manifest rows.
2. Commit those bytes as `A` without pushing. With `HEAD == A` and a clean tree,
   run preflight first, then focused tests, affected `serial-owner` lanes,
   assigned assembly smoke, `release.v1`, the scope-selected `release.v132`
   predecessor regression, compiler-facing advisory compatibility, and
   `MIX_ENV=test mix precommit`. Accepted metrics require `full_sha == A`
   and `dirty == false`. A failure is repaired by amending/replacing unpushed
   `A`, then rerunning every exact-clean handoff gate on the replacement; dirty
   iteration rows are diagnostic only.
3. After `A` is green, append only its Build Progress record as adjacent
   docs-only commit `B`, including `A`, clean metric ids/digests, deviations,
   rollback base, and next command. With `HEAD == B` and `HEAD^ == A`, run
   exact-clean `git diff --check HEAD^..HEAD` and the docs gate. If that record changes,
   amend unpushed `B` and repeat the docs gate; executable gates do not repeat
   because `B` changes evidence prose only.
4. Verify adjacency and a clean tree, then push `A` and `B` together. The next
   checkpoint starts only from pushed `B`.

**Operator cadence decision (2026-08-07):** M1.a3, M2, and M3 use recoverable
midpoint commits pushed as each bounded implementation batch becomes green,
then one combined exact-clean rejoin after M3. Repeating preflight and the full
handoff matrix after every carrier/fixture remediation was explicitly waived as
over-strict and too slow. This does not waive the final focused/serial,
production-shadow, frozen-contract, release, or evidence requirements; it moves
them to the coordinated rejoin. Build Progress records the actual checkpoint
SHAs and diagnostic runs rather than claiming the older adjacent `A`/`B` shape.

The immediate-boundary rollback recorded in `B` is exactly
`test -z "$(git status --porcelain)" && test "$(git rev-parse HEAD^)" = "<A>" && git revert --no-edit HEAD "<A>"`.
It reverts evidence commit `B` and implementation commit `A` newest-first only
while they are still the tip pair. After a successor starts, the adjacency
guard fails closed and rollback requires an operator-reviewed newest-to-oldest
range. The command is evidence, never executed automatically.

After fixture reconciliation, M1.a1 first adds the metrics-owning
`release-assembly` gate, then runs this bounded assembly/finalizer smoke (not an
archive, candidate, signature, or aggregate):

```bash
MIX_ENV=test mix allbert.test release-assembly --checkpoint v14-m1a1
```

The gate creates its own `mktemp -d` root and Allbert Home. Before invoking
`MIX_ENV=prod mix release allbert --overwrite`, it accepts only the exact
generated `_build/prod/rel/allbert` root or a strict descendant of that
disposable root, rejects symlink ancestry, and removes only that exact release
root. This preclean is mandatory because `--overwrite` can retain stale
application-version directories. Before the asset clean, the finalizer snapshots
only its sorted repository-owned logical-gzip allowlist, proves each entry
decompresses to its source, and rejects symlink ancestry before any command. It
deletes ignored prior-build gzip output, then atomically restores the allowlisted
bytes and modes after success or failure; a restore failure retains the original
command diagnostic, and any crash-residue temp is rejected before a later asset
command can digest it. Gzip header variation across build hosts therefore cannot
dirty the clean evidence SHA.
Verification then runs through packaged
`$RELEASE_ROOT/bin/allbert eval` in a clean VM using the release code paths and
sys.config; it starts no Allbert application, and all mutable/root overrides
point at the owned Home.

The verifier emits exactly one canonical
`ALLBERT_RELEASE_ASSEMBLY_V1=<JSON>` line, and only after every check and loaded-
state cleanup succeeds. The M1.a1 object has exactly schema version, `PASS`
status, checkpoint, normalized `.rel` SHA-256, an exact kernel/residual raw
`.app` SHA-256 object, and sealed Pack-projection SHA-256. Missing, malformed, or
duplicate markers fail. Build/verifier output is redacted into per-command logs.
On PASS the temporary Home/root and logs are removed; on FAIL the exact temp path
is printed and redacted logs are retained beneath it for diagnosis. The structured
`release-assembly` metrics row records full SHA, checkpoint, status, wall time,
and those four digests.

Candidate; it validates carrier shape, Descriptor-to-Owner consistency, and

`implementation_module` as self-attesting, or claiming Canonical re-verifies a

Contribution callback authority is not the stored callback map. It is produced


leading colon. `canonical_identity` is exactly `%{"namespace" =>
Atom.to_string(row.identity.namespace), "value" => identity_value}` after the
normal string validation. `identity_value` is normally `row.identity.value`;
when the schema contract classifies the identity-source field itself as
packaging-owner or application-reference authority, it is the same reserved
`"<ALIAS_OWNER>"` marker used below. This keeps owner-only changes neutral for
schemas such as `test_lane_v1` whose identity is the owner field.
`semantic_order_value` is normally `row.order.value`; when lexical order is
derived from that same owner-classified identity source, it is also
`"<ALIAS_OWNER>"` so the order tie-breaker cannot reintroduce packaging-owner

`m0_payload_sha256`, and stored reference-digest fields. Semantic
`order.value` remains except for that owner-derived lexical case; a source-lane
namespace does not. The executable
`RowSchemas.schema_contract/0` inventory marks every nested packaging-owner or
application-reference field, and the alias projection replaces those values
with the reserved non-id marker `"<ALIAS_OWNER>"`. All unmarked fields,
including intrinsic ids, modules, paths, capability metadata, and

`projection_sha256` are recomputed from their owner-neutral underlying
authority values rather than compared as stored bytes. Missing underlying
authority or an unclassified owner field rejects the alias. Rows sort by frozen

authority bytes. `callbacks_sha256` is lowercase SHA-256 of
`"allbert.pack.contribution.callbacks.v1\0" <> canonical_json(owner_neutral_rows)`.
Source and target must have identical row sets and bytes. Packaging owner,
application, source lane, and compatibility evidence do not enter that digest;
trust and enabled state remain separately required-equal in the enclosing
contribution projection.

`authority_sha256` is lowercase SHA-256 of
`"allbert.pack.alias.authority.v1\0" <> canonical_json(shared_projection)`.

payload or order change rejects.

### Readiness and activation protocol (M1.a3)

`Pack.Supervisor` owns Registry and Readiness with `:one_for_all` strategy.
`Readiness.start_link/1` accepts `name:`, `registry:`, and `coordinator:`;
production uses registered coordinator name `:allbert_pack_composition_owner`.
Post-start calls accept `server:`. The API is:

```elixir
subscribe(pack_id, opts \\ [])
open(snapshot_digest, expected_pack_ids, opts \\ [])
ack(subscription_ref, snapshot_digest, opts \\ [])
nack(subscription_ref, snapshot_digest, reason, opts \\ [])
validate_activation(context, opts \\ [])
status(opts \\ [])
# Internal residual metadata-source calls; fixed 5,000 ms timeout.
bind_metadata(barrier_pid, registry_pid, generation, subscription_ref)
invalidate_metadata(barrier_pid, registry_pid, generation)
```

`status/1` and `validate_activation/2` accept `server:` and `timeout:`; the
timeout default is 5,000 ms. The status wrapper normalizes `:noproc`, `:normal`,
`:shutdown`, `:killed`, nested shutdown/killed, and call-timeout exits to
`{:error, :unavailable}` rather than exiting its caller; activation validation
normalizes the same race exits to `{:error, :product_not_ready}`.
Production activation validation targets `context.barrier_pid`; an explicit
different `server:` is a test seam and cannot validate the context. Web
admission always uses `status(timeout: 100)`; `open/3` retains its separate
fixed 31-second call wrapper.

`bind_metadata/4` and `invalidate_metadata/3` are exported kernel calls only so
the residual App/Plugin registries can participate without a kernel dependency
on their module names. Each uses a fixed 5,000 ms call timeout, verifies that
the GenServer caller is the supplied `registry_pid`, catches the same teardown
races as status, and returns exactly `:ok | {:error, :stale_epoch |
:invalid_phase | :unavailable}`. Binding is allowed only while collecting and
is idempotent for the exact `{registry_pid, generation, subscription_ref}`;
another tuple for the same registry is stale. Matching invalidation removes
the tuple while collecting. If an open is pending, authorizing, or ready, it
also fails the open or withdraws readiness and terminates the barrier after
replying `:ok`, causing the `:one_for_all` epoch reset. A caller, pid,
generation, or reference mismatch returns `:stale_epoch` without changing
state.

`subscribe/2` accepts a canonical pack id tentatively because Readiness contains
no shipped list before finalization. `subscriber:` defaults to the caller; the
caller must own later ACK/NACK calls. Success is exactly `{:ok,
%{barrier_pid: pid(), subscription_ref: reference(), phase: :collecting}}`.
Unavailable returns `{:error, :unavailable}`; invalid id or a duplicate live id
returns `{:error, diagnostic}`. Tentative unexpected ids are not activated:
`open/3` detects them when it obtains authority from the finalized Registry.
A tentative subscriber that exits before opening is simply removed and may
subscribe again; once its id becomes required in `:authorizing`/`:ready`, DOWN
invalidates the whole epoch as specified below.

Coordinator absence is legal while Readiness is `:collecting`; the barrier does
not resolve or monitor the configured registered name during `init/1`. Only the
registered coordinator caller may invoke `open/3`; accepting that call resolves
the name and atomically arms the coordinator monitor. Its options require
`metadata_sources: [{registry_pid, generation, subscription_ref}]`, the exact
unique tuples returned by the coordinator's bound snapshots. Readiness compares
that order-independent set term-for-term with its source-registered bindings;
it neither knows App/Plugin identities nor assumes there are two. It also
cross-checks the supplied digest and sorted expected effectful ids against the
finalized Registry snapshot rather than trusting the arguments. Registry
collecting, digest mismatch, expected-id mismatch, metadata-binding mismatch,
or an unexpected tentative subscriber returns `{:error, diagnostic}` and sends
no activation. Missing expected subscribers may
arrive during the opening handshake. The GenServer stores the caller and uses a
timer—it never blocks its mailbox—so `subscribe/2`, ACK, NACK, and monitor events
remain processable. One fixed 30-second deadline covers missing subscribers and
activation ACKs; the public wrapper uses a 31-second `GenServer.call` timeout so
the internal diagnostic wins instead of a caller exit.

The generic kernel comparison is not the production-source completeness proof.
The composition coordinator contract requires exactly the App Registry tuple
and Plugin Registry tuple returned by its two immediately preceding
`snapshot_and_subscribe/2` calls—no omission, substitution, or third source—and
the generated coordinator-roster gate asserts those two concrete owners before
every `open/3`. This preserves kernel genericity while making an omitted App or
Plugin source a composition failure.

Once the exact live set is present, phase becomes `:authorizing` and each gate
receives exactly
`{:allbert_pack_activate, barrier_pid, subscription_ref, snapshot_digest}`.
Activation occurs only from this message, never from `subscribe/2`'s return.
Each gate validates all identities and creates exactly one internal
`%AllbertAssist.Pack.ActivationContext{schema_version: 1, pack_id:
canonical_pack_id, gate_pid: self(), barrier_pid: barrier_pid,
subscription_ref: subscription_ref, snapshot_digest: snapshot_digest}`. The
context is confined to the activation-owned subtree, redacted from logs,
traces, and diagnostics, and is neither a public surface token nor Security
authority. The gate remains mailbox-responsive while an owned boot worker
starts the effect subtree and awaits its required boot completions; it never
blocks the gate GenServer in the activation-message callback.

Kernel `AllbertAssist.Pack.ActivationGuard.validate(context, opts \\ [])` makes
the bounded `Readiness.validate_activation/2` call. Readiness accepts only its
live `:authorizing` phase and the exact pack-id/gate-pid/barrier-pid/
subscription-ref/snapshot-digest tuple for an expected, subscribed, not-yet-
ACKed gate. Missing, malformed, unavailable, or non-authorizing state returns
`{:error, :product_not_ready}`; a well-shaped tuple that differs from the live
authorizing subscription, or an already-ACKed exact tuple while other gates
remain `:authorizing`, returns `{:error, :stale_activation}`. Validation is
read-only. The generic kernel guard contains no pack ids, module names, or boot-
callsite roster; expected ids come only from the finalized Registry snapshot,
and the generated residual fixture/static gate proves which callsites may
accept the internal carrier.

The gate transfers the carrier exactly once, as the initial argument/capture of
one owned-and-monitored boot worker, and records that worker pid/monitor ref.
Outside the gate's canonical activation state, the carrier copy may then travel
only down that worker's synchronous call stack. The worker never persists it,
captures it in another retained closure, delegates it to another task/process,
or sends it through a signal, queue, later message, or child start argument.
Any effectful child initialization that must finish before ACK is therefore
invoked as an explicit synchronous boot-completion function rather than
retaining the carrier in the child. The worker reports one tagged result and
exits. Draining requires both the matching successful result and the matching
monitor `DOWN` with reason `:normal`, in either arrival order; an ordinary
completion message alone is insufficient. In the same gate callback that
observes the second fact, before processing another message, the gate calls
`ack/3`; ACK atomically marks this gate closed in Readiness. Start or boot
failure tears down the subtree and calls `nack/4` with a redacted stable reason.
ACK/NACK from any pid other than the subscription owner, or with a stale
reference/digest, returns `{:error, diagnostic}`. ACK returns `:ok`; NACK
returns `:ok` and causes the pending `open/3` to return an activation-failed
diagnostic while Readiness exits. A failed ACK also tears the subtree down; no
closed context can reactivate it.

The exact guard interfaces are:

```elixir
Readiness.validate_activation(%AllbertAssist.Pack.ActivationContext{}, opts \\ []) ::
  :ok | {:error, :product_not_ready | :stale_activation}

ActivationGuard.validate(%AllbertAssist.Pack.ActivationContext{}, opts \\ []) ::
  :ok | {:error, :product_not_ready | :stale_activation}
```

Both accept `server:` and the bounded 5,000 ms default `timeout:`. A production
call targets the context's barrier pid; any different test server cannot make
the tuple valid. Both wrappers catch the teardown-race exits enumerated above.

calls each source's internal

coordinator or a source registry from that request. Only

mutation fails closed without changing candidate-source state. Registry
serialization is the compare-and-swap boundary; a registry `handle_call` must
never synchronously call the coordinator. Registry monitors clear abandoned
bindings on barrier/subscriber DOWN.

Candidate-changing mutation has an explicit four-state rule:

- with no live metadata subscription, the Registry preserves M0 mutation
  behavior and advances generation on a changed MetadataEntry list;
- while subscribed but unbound, it may commit, advance generation, and notify
  every live subscription, making each captured generation stale;
- while bound and still collecting, it must first receive `:ok` from exact-tuple
  `invalidate_metadata/3`, then commit, advance, clear the binding, and notify;
- while an open is pending, authorizing, or ready, the same CAS is required and
  Readiness additionally fails/withdraws and resets the epoch before the source
  commit proceeds.

A non-`:ignore` child registration before ready remains the one intentional M0
delta: it returns `{:error, :product_not_ready}` without committing an entry or
starting a child. Metadata-only/`:ignore` registration may use the applicable
pre-bind rule. Failure to prove a required bound-state invalidation changes no
source state. Dynamic-overlay mutation is outside all four static-generation
states.

The outer production compatibility facade never holds a Registry call open
while waiting for recapture or activation. Candidate-changing mutations are
staged behind the invalidation boundary, the Registry replies with the new
generation, and the facade preserves each M0-frozen result/state/signal/cache
outcome while any required replacement activation runs. In particular, App
registration cannot report success unless its child reaches the frozen started
state; failure compensates the provisional App entry before returning the
existing error shape. Plugin registration preserves its existing
registered-entry plus child-start-diagnostic semantics. A replacement that
cannot reopen leaves product readiness closed and returns
`{:error, :product_not_ready}` only on APIs whose existing error return admits
it; `:ok`-only unregister/clear surfaces retain their result after the mutation
commits. M1.a3 adds a generated per-surface mutation/replacement table so no
branch invents a common outcome. Private unbound explicit-server fixtures keep
their isolated M0 behavior. Dynamic-overlay reconciliation remains outside the
static Candidate source/generation and cannot invalidate its own authorizing
epoch.

Every staged effectful registration carries an operational `mutation_ref`, its
commit generation, entry key, and exact MetadataEntry projection digest. The
facade reports success only after a ready coordinator result names the same
source, has generation greater than or equal to that commit generation, and its
bound source snapshot still contains that exact key/digest; a concurrent later
generation cannot be mistaken for this operation. On App activation failure,
the Registry compensates only the still-current entry owned by `mutation_ref`,
advances and notifies the compensating generation, and the facade waits for
that generation to reopen before returning the frozen child-start error. If
compensation or reopen cannot be proved, the App API returns its admitted
`:product_not_ready` form and leaves product readiness closed; it never reports
the failed child as registered. Plugin activation failure instead preserves
the M0 registered-entry plus child-start-diagnostic outcome, leaves readiness
closed, and never claims the child started. The generated per-surface table
pins exact results for `:ok`-only or otherwise narrower APIs.

monitors the coordinator only after accepted `open/3`. A required subscriber DOWN in
`:authorizing` or `:ready` terminates Readiness immediately; there is no
replacement within that epoch and no false-ready interval. The kernel
`:one_for_all` restart resets Registry and Readiness; gates monitor the old
barrier and become unavailable before teardown. They stop the effect supervisor
with a five-second graceful deadline, then kill and verify it dead, return
dormant, and subscribe to the new barrier. A rebuilt snapshot may have the same
behavior digest; exactly-once means once per `{barrier_pid, subscription_ref,
snapshot_digest}`, so a new epoch may reactivate it while stale old-epoch
messages cannot. After ACK, unexpected effect-supervisor exit terminates its
ActivationGate; subscriber monitoring then invalidates the epoch instead of
leaving a partially ready product.

Failure while `:collecting` proves zero activation messages and zero calls
across the enumerated effect-owner boundaries. Failure during `:authorizing` may
follow activation and irreversible calls; it never publishes ready and ends in
bounded teardown with zero surviving effect processes, but does not pretend to
undo prior calls. Post-ready loss likewise guarantees immediate non-readiness;
after each gate observes barrier DOWN it admits no new effectful work and reaches
zero surviving effect processes after bounded teardown. Calls already in flight,
or initiated before the asynchronous DOWN observation, follow existing
cancellation/timeout contracts and are not misrepresented as rolled back.
Database migration, writer-lock/integrity-secret/key-custody work, and
metadata-registry reconstruction are permitted substrate writes and are not
misreported as pre-open effect violations.


### Web readiness and epoch handoff (M1.a3)

Web readiness has one non-capability admission/observer process.
`AllbertAssistWeb.PackReadiness` is supervised after
`AllbertAssistWeb.PubSub` and before SignalBridge/Endpoint. It never calls Pack
`subscribe/2` and is not in the effect-subscriber set. It exposes `admit/0`,
returning `{:ok, %{barrier_pid: pid, snapshot_digest: digest}} | {:error,
:product_not_ready}`, and `validate/1`, returning `:ok | {:error,
:product_not_ready | :stale_epoch}`. Both execute inside the observer and make a
fresh `Readiness.status(timeout: 100)` call; its cache is notification state,
never authority.

The public wrappers use a fixed 150-ms observer call timeout and catch
`:noproc`, `:normal`, `:shutdown`, `:killed`, and call-timeout exits, including
their nested GenServer exit tuples. `admit/0` normalizes every such case to
`{:error, :product_not_ready}`; `validate/1` does the same and returns
`:stale_epoch` only for a live observer's exact-token mismatch. HTTPGate,
LiveSocket connect, and lifecycle-hook race tests kill the observer during the
call and require 503/`:error`/redirect behavior rather than caller death.

The observer's Pack-admission state is exactly `:closed` or one monitored ready
epoch. Its notification-bridge rotation state is orthogonal and is exactly
`:absent | {:retiring, pid, monitor_ref} | {:opening, pid, epoch} | {:open,
pid, epoch}`; `admit/0`, `validate/1`, and Health depend only on Pack admission.
While Pack admission is closed
it keeps one immediate/fixed-100-ms retry outstanding. A result is adoptable
only after the observer arms a process monitor on `barrier_pid` and confirms the
pid remains alive; `admit/0` cannot return it sooner. `validate/1` additionally
requires exact pid/digest equality. DOWN, timeout, non-ready/unavailable status,
or an epoch different from the monitored epoch changes the observer to closed
before failing the current call; it never switches directly from E1 to E2 in
one admission. A later probe may adopt E2.

Every observer `init/1`, including cold start, performs the defensive close/
disconnect sequence before first adoption. At cold start no client exists;
after an observer crash this prevents a loss and replacement completed during
its absence from preserving an old session. LiveSocket and HTTPGate therefore
call `PackReadiness.admit/0`, never `Readiness.status/1` directly, so every
admitted request/transport has an observer-armed epoch.

`AllbertAssistWeb.LiveSocket` is a `Phoenix.Socket` with the standard `"lv:*"`
and `"lvu:*"` LiveView channels and replaces `Phoenix.LiveView.Socket` at
`/live` for both WebSocket and longpoll. `connect/3` calls
`PackReadiness.admit/0`; on success it calls
`Phoenix.LiveView.Socket.connect/3` with the original connect info and stores
the admitted epoch at
`socket.private[:connect_info][:allbert_pack_epoch]`, while failure returns
`:error`. `id/1` returns the single global socket topic
`"allbert_pack_readiness"`. Carrying the server-admitted epoch in connect info
closes the connect-before-transport-subscription race: a broadcast missed
before `Phoenix.Socket.__init__/1` subscribes the id still leaves an E1 token
that an E2 mount must reject.

On each observed ready-to-closed transition the observer marks itself closed
before broadcasting the targeted disconnect below. A live observer emits at
most one transition broadcast for its locally tracked epoch; observer-init and
stale-callback defenses may emit duplicates. The contract is idempotent
at-least-once disconnection, not globally exactly once:

```elixir
Phoenix.Channel.Server.broadcast(
  AllbertAssist.PubSub,
  "allbert_pack_readiness",
  "disconnect",
  %{}
)
```

`AllbertAssist.PubSub` is the Endpoint transport bus and is distinct from
`AllbertAssistWeb.PubSub`, which carries SignalBridge/UI events. The direct
Channel Server path is required because the core-owned Endpoint transport bus
is already started but Endpoint's ETS configuration table does not exist when
the earlier PackReadiness child performs its cold-start defense. Endpoint
broadcast helpers are forbidden in that pre-Endpoint path. A from-scratch
Web-supervisor test proves child ordering and the first defensive broadcast
without a pre-existing Endpoint.

No code emits `phx_drain`, `:socket_drain`, or stops/drains Endpoint: health and
static HTTP remain available. With the locked Phoenix 1.8.9 dependency,
targeted `"disconnect"` closes WebSocket with code **1001 Going Away**, which
phoenix.js reconnects; socket drain is the distinct **1012 Service Restart**
path. Longpoll terminates/rejoins but has no WebSocket close code. The old
transport's root LiveViews, stateful LiveComponents, and upload channels die;
rejoin is refused while closed and creates new processes only after replacement
readiness.

The first readiness `on_mount` hook runs before `SharedShellHooks`. On a
disconnected mount it reads the exact HTTPGate token from
`session["allbert_pack_epoch"]` and validates it; it does not call `admit/0`
again and substitute a replacement epoch. One named `live_session` covers all
six roots and uses `{AllbertAssistWeb.PackReadiness, :live_session, []}` as its
session MFA. `live_session(conn)` returns exactly
`%{"allbert_pack_epoch" => conn.private[:allbert_pack_epoch]}` when the gate
stored a well-shaped token, otherwise `%{}`; Phoenix signs that extra session
map. On a connected mount the hook ignores the older HTTP session token and
reads the transport token at `:allbert_pack_epoch` through
`Phoenix.LiveView.get_connect_info/2`, validates that exact transport epoch,
and assigns it. Missing or stale tokens emit the idempotent global disconnect
and return `{:halt, Phoenix.LiveView.redirect(socket, to: "/health")}`.
LiveView 1.1.32 requires the redirect on a halted mount; an unredirected
`{:halt, socket}` from `on_mount` is forbidden. Focused tests pin both the
disconnected signed-session and connected custom-connect-info extraction seams,
including E1 loss after HTTPGate but before static mount.

The `handle_params`, `handle_event`, `handle_info`, and `handle_async` hooks call
`PackReadiness.validate/1` immediately before the callback. A mismatch emits
the disconnect and returns that stage's valid `{:halt, socket}`. A phase-only
check is forbidden: an old session cannot cross into a fast replacement epoch
even when the digest is unchanged. Upload consumption likewise validates the
stored epoch immediately before persistence.

The exact root roster is `WorkspaceLive`, `JobsLive`, `ObjectivesLive`,
`ObjectiveLive`, `AllbertArtifactsWeb.ArtifactLive`, and
`StockSageWeb.AnalysisLive`. Root lifecycle hooks do not propagate to stateful
components under LiveView 1.1.32, so `Onboarding`, `IntentsPanel`,
`ModelsPanel`, `SurfacePolicyPanel`, `ChannelsPanel`, `NotesPanel`,
`MemoryPanel`, `PlanPreviewPanel`, `SettingsCentral`, and `TemplateCreate`
attach the common component readiness hook in `mount/1`; it covers the
LiveView-1.1.32-supported `handle_event` and `handle_async` stages. Each root
passes a required `allbert_pack_epoch` attribute. The component's first
`update/2` validates and stores it, later updates reject a missing or changed
token, and every runtime-bearing update performs a fresh validation. A rejected
component update emits the global disconnect and returns the valid LiveComponent
result `{:ok, old_socket}` without applying new assigns or effects; `update/2`
never returns a lifecycle `{:halt, socket}`. Components never call
`get_connect_info/2`. M1.a3 closes **all** product LiveViews on loss;
there is no claimed diagnostic-only current view. `/health` and already-served
static HTTP are the closed-mode UI.

`AllbertAssistWeb.SignalBridge` stays substrate-owned and is not a Pack
subscriber, but each bridge process is scoped to one epoch. It starts closed
and unsubscribed. On observer init or ready-epoch loss, PackReadiness closes
notification state, emits the idempotent targeted disconnect, then
asynchronously asks a still-live open bridge to unsubscribe and stop; the
observer never blocks while a signal handler may be calling `validate/1`. It
monitors the retiring pid and cannot adopt a replacement Pack epoch until that
pid is DOWN. On bridge crash the pid is already DOWN: Pack admission remains
ready, notification state becomes `:absent`, and the observer emits the reload
disconnect without trying to stop the dead process. Messages already addressed
to an old pid die with its mailbox.

The Web supervisor supplies a different closed bridge pid. Once Pack admission
holds an epoch—new E2 or unchanged E1—the observer retries
`SignalBridge.open(epoch)` on a fixed 100-ms cadence until the new process has
subscribed and stored that exact epoch. Signals during this
notification-only gap are dropped rather than buffered; HTTP/transport Pack
admission is not made dependent on the bridge. Successful open emits another
idempotent targeted disconnect so any view that rejoined during the gap reloads
durable state only after the new subscription exists. A same-Pack-epoch bridge
restart uses the same new-pid/open/reload handshake while `admit/0` continues
to return the ready Pack epoch. Tests assert that separation explicitly.

Before Objective lookup or PubSub broadcast, the bridge calls
`PackReadiness.validate(stored_epoch)` and drops on closed, unavailable, or
mismatch. Barrier teardown completes before E2 can open, so old effect
publishers are gone before the new pid subscribes. New pid plus exact epoch
validation—not a fresh status check performed when an untagged queued message
happens to run—proves an E1 signal cannot replay into E2.

`AllbertAssistWeb.PackReadiness.HTTPGate` runs in Endpoint after `Plug.Static`
but before `PublicProtocolBodyCap`, `PublicProtocolWebhookAuth`, parsers,
router/controller auth, rate limiting, event recording, or any runtime call. It
calls `PackReadiness.admit/0` and stores the returned epoch in
`conn.private[:allbert_pack_epoch]`. Only exact
`/health` and a static response already served by `Plug.Static` are exempt;

WhatsApp GET/POST, `/v1/models`, and chat completions, fails before body/auth/

`retry-after: 1`, and `cache-control: no-store`; its path-specific body is:

- browser/other: `text/plain; charset=utf-8` body
  `Allbert product is not ready.\n`;
- MCP: JSON body
  `{"jsonrpc":"2.0","id":null,"error":{"code":-32000,"message":"product_not_ready"}}`;
- OpenAI `/v1/*`: JSON body
  `{"error":{"message":"Allbert product is not ready.","type":"service_unavailable","code":"product_not_ready"}}`;
- WhatsApp webhook: JSON body
  `{"error":{"code":"product_not_ready","message":"Allbert product is not ready."}}`.

Each admitted HTTP request calls `PackReadiness.validate/1` on its stored epoch
immediately before Runner/Runtime/Workspace/Settings/adapter dispatch. Central effect boundaries
validate the token too; readiness is a liveness precondition, never Security

accounts for every Web call into effect boundaries as guarded or explicitly

The equality proof covers element order, action names, modules, agent/internal

## §G — Distributed Settings Composition

Settings Central retains resolution, provenance, validation, version checking,
additive-only enforcement, future migration-policy authority, and the secret
vault. Schema ownership moves to the
kernel or the contributing pack without changing stored key names or semantics.

```text
kernel settings contribution + discovered pack contributions
  -> validate unique fragment ids and key ownership
  -> order by the bound deterministic composition contract
  -> compose schema rows, defaults, safe-write metadata, sensitivity,
     fragment versions, deprecations, and cross-key validators
  -> compare complete result with M0 baseline

  -> publish settings snapshot with provenance per row and validator
  -> Settings reads/writes resolve through that snapshot
```

The M5 ownership ledger names every moved row and every validator, including
validators that span fragments. Duplicate ownership fails closed and reports
both contributors. Pack enablement must not make an operator's stored settings
unreadable; M0 binds whether a disabled shipped pack still contributes schema
and how an absent pack is diagnosed.

therefore does not enter §A. v1.4 admits no runtime migration step.

### Approved option A — sealed concern contracts

ADR 0098's downward dependency rule is implemented through concern-specific
contracts, not a second discovery authority:

```text
compiled native/residual concern owners
  -> contribute immutable snapshots and narrow port implementations
composition candidate finalization
  -> validate schema + unique owner + implementation application/module
  -> bind the complete contract set atomically to Registry snapshot/Readiness epoch
  -> open effects only after successful binding
kernel concern
  -> read/call only its kernel-owned contract
  -> missing | duplicate | malformed | stale | provider lost
       => close/fail Readiness; return product-not-ready/fail-closed result
```

Use a snapshot for immutable Home/config, policy posture, action-catalog, and
membership/availability facts. Use a narrow kernel-owned behavior/port for
operations such as HMAC/verification custody, audit/redaction, and signals. A
provider is compiled first-party application code validated by composition;
pack metadata, YAML, model output, or a module name alone cannot become an
implementation. Raw integrity secrets never cross the boundary, and a port
returns an operation result or opaque handle rather than key material.

The following are forbidden because they recreate the monolith behind a new
name: one free-form `KernelContext` or global service locator; a kernel module
that names `allbert_assist`, a pack, App Registry, or Plugin Registry; a callback
whose provider was not validated and bound to the current generation; fallback
to a previously bound generation; and snapshots containing secrets or live
mutable owner state. Composition remains the single lifecycle join and does not
create a parallel startup coordinator.

The generated closure ledger begins with these known edge families and assigns
each direct/transitive compile, export, runtime, resource, configuration,
startup, and test edge exactly one disposition before R2:

| Relocation concern / target | Known inward dependency family | Required disposition before R2 |
| --- | --- | --- |
| Home/Paths | `ConfigContext`, Artifacts, Confirmations, Execution Audit, Memory, Settings | Move companion Home substrate or provide a non-secret immutable snapshot/narrow port. Feature path overrides stay owner contributions; no Registry lookup. |
| Security Policy/Context/Decision/Status | Settings/Schema/Secrets/Store, Coding grants, Skills, App/Plugin/Action Registry, Runtime audit/redaction/safe-term | Snapshot policy and membership facts; port operations. Preserve Security authority and fail-closed semantics. |
| `External.HttpPolicy` / `External.RequestSpec` | Their paired references plus Resources/Settings | Move together as Security substrate or close the paired seam; neither may leave a kernel-to-residual edge. |
| Capability Registry/Runner | App/Plugin Registry, ActionsOverlay, release availability, RegistryContext, Signals, Runtime response/redaction | Consume the sealed action catalog and membership/availability snapshot plus narrow effect ports. Dynamic overlay remains composition-validated authority, not a kernel pack lookup. |
| Canonical `Response` | intent approval/decision/resource-access types and Runtime redaction | Move companion value types or invert redaction; preserve the one M3 response format. |

### Common disposable-Home preflight

This preparation block is paste-executable now. It copies a caller-supplied
configured Home and never writes to the source Home:

```bash
set -euo pipefail

V14_SOURCE_SHA="$(git rev-parse HEAD)"
if test -n "$(git status --porcelain)"; then
  echo "BLOCKED: worktree is not clean"
  exit 2
fi

: "${ALLBERT_FV_SOURCE_HOME:?BLOCKED: set ALLBERT_FV_SOURCE_HOME to the configured source Home}"
V14_SOURCE_HOME="$(cd "${ALLBERT_FV_SOURCE_HOME}" && pwd -P)"
if test "${V14_SOURCE_HOME}" = "/"; then
  echo "BLOCKED: source Home resolved to filesystem root"
  exit 2
fi

same_or_below() {
  local child="$1" parent="$2"
  test "${child}" = "${parent}" && return 0
  case "${child}/" in
    "${parent}/"*) return 0 ;;
    *) return 1 ;;
  esac
}

V14_FV_BASE="$(cd /tmp && pwd -P)"
if same_or_below "${V14_FV_BASE}" "${V14_SOURCE_HOME}"; then
  echo "BLOCKED: scratch base is inside source Home"
  exit 2
fi

reject_unsafe_home_tree() {
  local root="$1" bad
  if IFS= read -r -d '' bad < <(
    find "${root}" -mindepth 1 \( -type l -o ! \( -type d -o -type f \) \) -print0 -quit
  ); then
    echo "BLOCKED: source Home contains a symlink or special file: ${bad}"
    exit 2
  fi
  if IFS= read -r -d '' bad < <(
    find "${root}" -mindepth 1 -name $'*\n*' -print0 -quit
  ); then
    echo "BLOCKED: source Home contains a newline in a path: ${bad}"
    exit 2
  fi
}

portable_lstat() {
  local path="$1"
  # Directory allocation size is filesystem/history-dependent and is not part
  # of logical tree identity; regular-file byte length is framed separately.
  if stat -f '%HT|%Lp|%u|%g|%m' "${path}" >/dev/null 2>&1; then
    stat -f '%HT|%Lp|%u|%g|%m' "${path}"
  else
    stat -c '%F|%a|%u|%g|%Y' "${path}"
  fi
}

sha256_stream() {
  if command -v shasum >/dev/null 2>&1; then
    shasum -a 256
  else
    sha256sum
  fi
}

fingerprint_home_tree() {
  local root="$1" output="$2"
  # Path order is canonical rather than filesystem traversal order. Each
  # relative path and lstat tuple is byte-length-prefixed before regular-file
  # bytes, so ambiguous concatenations cannot compare equal. Unsafe entry types
  # and newline-bearing paths were rejected above.
  (
    cd "${root}"
    export LC_ALL=C
```
