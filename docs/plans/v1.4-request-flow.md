## Build-Start Bindings

M0 records the exact v1.3.2 tag and clean source SHA that v1.4 starts from. It
binds commands that already exist, freezes each planned interface contract, and
assigns every `MILESTONE-BIND` command slot to the milestone that produces that
interface. A proposed command name is not evidence and must not be added merely
to make a runbook look complete. The producing milestone replaces its own slot
with the literal command and inline PASS criteria; workstream G verifies all
source slots before R4 and all build/package slots before R4a/R4b.

Every automated, handoff, and operator row ends in exactly one result:

- `PASS` — the stated assertion passed on the recorded source SHA or artifact.
- `FAIL` — the assertion ran and found an executable or documentation defect.
- `BLOCKED` — the assertion could not run; the external dependency, missing
  interface, missing authority, or environment fact is recorded.

Only `PASS` crosses a serial milestone barrier. `FAIL` rejoins remediation;
`BLOCKED` is not converted to `PASS` by explanation.

## §A — Explicit Per-Fragment Settings Migration

### Admission: prove a real consumer

ADR 0046 admits only independent per-fragment steps. Before the runner is used
on operator data, each proposed consumer gets one committed ledger row:

| Field | Required content |
| --- | --- |
| Migration identity | Stable `{fragment_id, from_version, to_version}` and reviewed module |
| Stored source | Exact key, type, encoding, current owner, and current readers/writers |
| Stored destination | Exact key, type, encoding, target owner, and target readers/writers |
| Transition | Identity, rename, transform, removal, or no stored-data change |
| Compatibility | Deprecation release, warning behavior, alias read/write behavior, and earliest legal removal |
| Secrets | Proof that the step does not migrate secret-store contents |
| Forward proof | Exact expected postimage and validation result |
| Reverse proof | Exact preimage restoration rule and conflict behavior |

Telegram/email ownership relocation does not become a migration merely because
the owning module moves. Likewise, a legacy key is not removed unless the ledger
proves ADR 0046's deprecation window, the exact replacement, and every remaining
consumer. The candidate ledger starts with these exact dispositions:

| Candidate | Stored transition under review | Conflict and compatibility rule | M0 admission bar |
| --- | --- | --- | --- |
| Telegram/email ownership | Existing dotted keys keep the same serialized keys while their complete schema rows and validators move to pack ownership | No stored rewrite solely for ownership; values and fragment versions remain unchanged | M0 enumerates every key and proves a real non-additive storage diff before admitting any step |
| Model preference | `intent.model_profile` → `model_preferences.primary` | Canonical value wins when both exist; the public legacy read/write alias remains compatible through v1.4 | Stored legacy-key evidence, ADR 0046 deprecation/version proof, and proof that one fragment legally owns the entire step |
| Direct-answer preference | `intent.direct_answer_model_profile` → one-element `model_preferences.tasks.direct_answer` list | Canonical value wins when both exist; the public legacy read/write alias remains compatible through v1.4 | Stored legacy-key evidence, scalar-to-list proof, ADR 0046 deprecation/version proof, and single-fragment ownership proof |
| Router preference | No transition: `intent.router_model_profile` remains its own live setting | It is not covered by an `intent.*model_profile` wildcard | Excluded unless a later explicit operator decision changes its semantics |

The operator decision requires the runner and one real non-additive migration in
v1.4. If neither model-preference candidate clears its admission bar and the
ownership moves are identity-only, M11 is `BLOCKED`: implementation must produce
another genuine ledger-proven consumer or return for operator disposition. It
must not manufacture a rewrite to satisfy the milestone.

ADR 0046 forbids cross-fragment coordination. If an intent candidate requires
one fragment step to advance or atomically coordinate two independently
versioned fragments, it is ineligible under the chosen option and cannot serve
as the real consumer without a separate operator-approved ADR amendment. A
legacy unowned storage alias may be absorbed by one target fragment only when
M0 proves that ownership and all readers/writers unambiguously.

### Invocation and preview

There is **no migration or rollback on boot**. Boot may detect and report a
pending, forward, or interrupted fragment state, but it performs no write. The
operator invokes the bound migration interface explicitly:

The packaged surface is attach-first: an already-running daemon remains the
single Settings writer. M0 must also bind the recovery route for a Home whose
pending/forward/interrupted status prevents the full runtime from starting. That
route may start only the minimum Settings maintenance ownership needed to take
the same cross-process lock; it must not silently start a second full runtime or
bypass Security/confirmation/audit.

```text
explicit preview request
  -> acquire the existing Settings Store cross-process lock
  -> read fragment version and serialized operator values
  -> reject an unknown/forward version
  -> resolve the one ordered path from stored to known version
  -> compute the persisted-state digest and prospective transform in memory
  -> release the lock
  -> return a redacted preview: ids, versions, affected keys, and effects
  -> request confirmation per migration, or one explicit --all confirmation
```

The preview never prints values marked sensitive and never copies secret-store
contents into the migration journal. It creates no journal, preimage, audit, or
other durable file. The preview digest is only a stale-plan guard for confirmed
apply.

### Confirmed apply

```text
confirmed fragment step
  -> enter one Settings Store migration transaction and cross-process lock
  -> re-read version and serialized bytes
  -> compare them with the preview version and persisted-state digest
       mismatch -> BLOCKED as concurrent modification; write nothing
  -> run the reviewed migration module against an in-memory copy
  -> validate the complete target fragment and cross-key invariants
  -> compute the expected postimage digest
  -> stage, fsync, and atomically publish one write-ahead bundle containing
       the protected preimage, integrity-tagged manifest, and `prepared` record
       (migration id, versions, source SHA/build, preimage digest,
       expected postimage digest, preimage reference, attempt id, timestamp)
  -> write through registered Settings actions in that transaction using Store
     atomic replacement; do not acquire a nested independent Store lock
  -> append durable `applied` record
  -> read back, validate, and compute the postimage digest
  -> append durable `verified`
  -> append the redacted operator audit entry idempotently by attempt id
  -> append durable `complete`
  -> release the lock
```

The restricted recovery journal and preimages live under
`<ALLBERT_HOME>/settings/migrations/`; the redacted operator audit continues
through the existing `<ALLBERT_HOME>/settings/audit/` authority. Audit entries
identify the binary/source that performed the write and link to the protected
preimage without embedding operator values. Each recovery transition and
preimage manifest is integrity-tagged with the existing domain-separated
per-Home integrity secret; invalid tags fail closed. Fragment version changes
commit atomically with the fragment data they describe. The protected preimage
preserves existing encrypted-at-rest bytes or secret references; the runner
never decrypts a secret into it. v1.4 never prunes a preimage automatically;
any future prune is explicit, confirmed, and limited to terminal records outside
supported rollback. A failure before atomic replacement leaves the stored
version unchanged. A failure after replacement leaves a `prepared`, `applied`,
or `verified` recovery state whose digests drive explicit resume or rollback;
it must not be reported as an unchanged store.

### Interruption, retry, and rollback

An incomplete recovery record is diagnostic state, not permission for boot to
mutate the Home:

| Observed state | Explicit next action |
| --- | --- |
| `prepared`; current bytes match the protected preimage | Recompute the deterministic transform, require the recorded expected-postimage digest, then apply once |
| `prepared`; current bytes match the expected postimage | The atomic replacement completed before the `applied` marker; advance to `applied`, then verify without re-transforming |
| `applied`; postimage matches the journal | Explicit retry may complete verification without re-transforming |
| `verified`; audit/complete marker was interrupted | Explicit retry idempotently appends or confirms the attempt-id audit and then marks `complete` without re-transforming |
| `prepared`; operator requests rollback; current bytes match the protected preimage | Mark `recovery_required`, perform no Settings write, verify the original bytes/version, append/confirm the `no_commit_to_restore` rollback audit, then mark `rolled_back` |
| `prepared`; operator requests rollback; current bytes match the expected postimage | The replacement committed before its marker; mark `recovery_required`, atomically restore and verify the exact preimage/version, append/confirm the rollback audit, then mark `rolled_back` without first forcing resume |
| `applied`, `verified`, or `complete`; operator requests rollback | Under the Settings lock, verify the expected postimage digest, mark `recovery_required`, atomically restore the exact preimage/version, read back, append/confirm the rollback audit, then mark `rolled_back` |
| `recovery_required`; current bytes match the expected postimage | Retry the exact preimage restore; do not run an inverse transform |
| `recovery_required`; current bytes match the protected preimage | The restore committed before its marker; verify, append/confirm the rollback audit, then mark `rolled_back` |
| `rolled_back`; rollback is repeated | Return the existing terminal result; perform no Settings write and append no duplicate audit |
| Current bytes match neither preimage nor expected postimage | `BLOCKED`; do not overwrite concurrent or unknown state |
| Journal/preimage is absent, unreadable, or fails its digest/integrity tag | `BLOCKED`; report the migration id and audit path |
| Stored version is ahead of the binary | `BLOCKED`; no preview, apply, retry, or rollback write |

Rollback is automated machinery but explicitly operator-invoked. It restores
the serialized preimage byte-for-byte; it does not run a guessed inverse
transformation. Retry never applies a transform on top of an already transformed
postimage.

### Migration acceptance evidence

For each admitted ledger row, tests cover read-only preview/redaction,
confirmation, concurrent-write rejection, every interruption boundary around
preimage persistence/`prepared`/atomic replace/`applied`/`verified`/audit/
`complete`, idempotent retry,
exact rollback, version-ahead refusal, checksum/integrity-tag tamper refusal,
audit redaction, and restoration of the operator-authored preimage. Evidence runs on a disposable clone of a real
configured Home, never on the operator's live Home. Release acceptance starts
from the packaged v1.3.0 Home shape, applies and rolls back with v1.4, then proves
the packaged v1.3.0 binary can read the restored Home; the older binary never
performs rollback itself.

## §B — Existing Runner Param Validation

ADR 0065's central seam already exists. v1.4 re-verifies it; v1.4 does not
invent a second param-enforcement response contract.

```text
action invocation -> Actions.Registry -> Actions.Runner.run/3
  -> ParamContract.normalize_and_validate(action_module, params)
       valid   -> action_module.run(validated_params, context)
       invalid -> Response.error(..., {:invalid_params, redacted_reason})
                  wrapped in the normal {:ok, response_with_runner_metadata}
                  action body is not called
```

Non-map params follow the same `:invalid_params` response-envelope contract and
never reach an action body. Raw rejected input is not echoed into diagnostics,
traces, or audit metadata.

M0 compares the registry-derived catalog, dispositions, and Runner tests with
the exact registered-action inventory. If it finds no gap, M2 is verification
plus coverage for actions added since v0.59. If it finds a gap, M0 names the
exact action, invocation path, missing disposition, and focused test; only that
recorded gap becomes implementation work. M2 also opens an append-only action-
delta ledger. Every action
introduced, removed, or moved by v1.4 records its module, id, pack/order,
exposure, param contract, Security placement, envelope owner, and test owner;
M14 regenerates the closeout roster and reconciles every delta before final
acceptance.
A presumed historical count or a
claim that the v0.59 set was partial is not an implementation input.

## §C — Direct PermissionGate Facade Retirement

`PermissionGate` is a compatibility facade over Security Central, not a second
policy authority and not part of param validation. Its retirement is a direct
call-site migration:

| Compatibility call | Direct owner after retirement |
| --- | --- |
| `PermissionGate.authorize(permission, context)` | `AllbertAssist.Security.authorize(permission, context)` |
| Permission, approval-mode, and coding-tier vocabulary/helpers | `AllbertAssist.Security.Policy` |
| `PermissionGate.response_status(decision)` | `AllbertAssist.Runtime.Response.permission_status(decision)` |
| `PermissionGate.allowed?(decision)` | The same exact `%{decision: :allowed}` predicate; no truthiness expansion |

The direct authorization decision intentionally records
`source: AllbertAssist.Security`. That is the one approved observable change
from the facade, whose source was `AllbertAssist.Security.PermissionGate`.
Permission, normalized context, policy, risk, decision, reason,
`requires_confirmation`, denial behavior, confirmation behavior, and response
status remain invariant.

```text
before
caller -> PermissionGate.authorize -> Security.authorize -> decision
       -> PermissionGate.response_status / allowed?

after
caller -> Security.authorize -> decision(source = AllbertAssist.Security)
       -> Security.Policy helpers / Runtime.Response.permission_status
       -> exact :allowed decision predicate where needed
```

The ordered retirement is binding:

1. M0 freezes the complete production call-site inventory by caller family and
   records direct Security callers already present.
2. Red-first parity fixtures capture every distinct context construction,
   permission, allowed/confirmation/denied branch, response mapping, and
   confirmation-resume path. Non-action callers are included.
3. Call sites move directly to Security, Policy, and Runtime.Response. Param
   validation is neither added nor removed by this edit.
4. Parity asserts the full decision and response behavior, allowing only the
   intentional `source` change.
5. Static enforcement proves zero production references before the facade is
   deleted. It scans all application and plugin production roots, release and
   runtime configuration, dynamic module-name construction, and hard-coded
   source readers; moved tests/evals are updated or explicitly retained as
   historical fixtures. Adversarial rows prove no direct caller bypasses
   Security Central.

If a caller cannot preserve those semantics, M6 stops with `FAIL`; it does not
leave a partially retired facade or redesign authorization inside Runner.

## §D — Action envelope consolidation

```
use AllbertAssist.Action, permission: :memory_write, name: "update_memory_entry", ...
  |
  +-- capability metadata (already stored today as capability/0)
  |
  +-- NOW ALSO GENERATES:
        denied/1, error/2, action/3,
        the standard four-key output_schema,
        the confirmation-summary helper
        — all defoverridable
```

**Behaviour-preservation is the acceptance bar.** The M0 action inventory is
the denominator. Generated-versus-overridden helper output is compared for every
converted module, and runtime paths are exercised across every action category.
The full response envelope is captured before and after — `message`, `status`,
`permission_decision`, `error`, `actions` — on completed, confirmation, denied,
and error paths. Any unrecorded difference is a defect.

Outliers keep hand-written helpers, each recorded with the reason it differs.

## §F — Pack Discovery And Ordered Action Registry

M1 cannot derive the current registry from `Application.loaded_applications/0`:
OTP reports only application specifications already loaded into the application
controller, not every application present in the release. M0 first binds a pack
contribution contract that makes ownership and order explicit without
recreating a kernel-owned list.

Each shipped pack contribution identifies at least:

- the exact `descriptor/0` identity shape: schema version 1, canonical id, OTP
  application/version, `:kernel | :native` tier, signed-release component
  provenance, and globally unique numeric `registry_order`;
- frozen App-contract modules/descriptors through `apps/0`, when present;
- action modules with their stable action-order identity, exposure, and
  capability metadata;
- settings fragments and gate owners, when present;
- typed Allbert Home roots and portability policy, when present;
- application-owned assets needed by release, license, and inventory tooling.

M0 binds where the OTP application declares its pack module, the exact acyclic
application dependency/start DAG, and the composition coordinator. Packaged
completeness is the exact `pack` projection of
`$RELEASE_ROOT/THIRD-PARTY-MANIFEST.json`, produced last by
`finalize_license_evidence/1` from strict first-party `beam_app` Pack objects in
`apps/allbert_assist/priv/licenses/catalog.json`. Each Pack object fixes schema
version 1, id, descriptor-module string, startup role, and registry order; the
packaged projection also fixes the raw `.app` SHA-256. The overall component
inventory keeps its best-effort claim, but this Pack subset is a closed set.

The coordinator consults the independent
`$RELEASE_ROOT/releases/$RELEASE_VSN/allbert.rel` and each raw packaged `.app`.
It obtains application/module atoms only from those trusted terms, compares
manifest strings without atomizing them, verifies the `.app` digest, and calls
`Application.load/1` for each reconciled application. An effective
`:allbert_pack` value different from the raw `.app` value is a forbidden
runtime-config override; only the raw module atom may be invoked.
`Application.loaded_applications/0` is used only for diagnostics and detection
of an unexpected already-loaded declaration. Start order never becomes
composition order; product readiness nevertheless waits for both a finalized
snapshot and successful start of every required native pack. A coordinator/pack
dependency cycle is a design `FAIL`, not a startup-order workaround. M0 also
binds how a pack snapshot is invalidated. Source/dev/test use the same validated
source-catalog projection against code-path raw `.app` files, while a build gate
reconciles root Mix release membership; Mix data is not a runtime discovery API.
Packaged unsafe-Home maintenance uses the same component manifest/`.rel`/`.app`
records and has no fallback. The post-build candidate/qualification manifests
and `SHA256SUMS` never bootstrap discovery. The kernel contains no shipped-pack list.

The Pack projection lists every descriptor-bearing application and classifies
its startup role as kernel prerequisite, passive native, or effectful native.
Kernel-prerequisite rows require descriptor tier `:kernel`; both native roles
require tier `:native`; and all three require normalized `.rel` mode
`:permanent` (including an omitted OTP default). Other start modes fail. The
passive/effectful distinction comes from the Pack role and readiness proof, not
from `.rel`.
`allbert_kernel`, residual `allbert_assist`, and named packs all use the same
component row -> `.rel` -> raw `.app` -> `descriptor/0` validation path. Composition/support hosts
have no descriptor. The kernel application is already-started prerequisite;
passive native packs do not subscribe; only effectful native children wait on
the activation barrier.

`AllbertAssist.Pack.Readiness` is the generic kernel barrier. Effectful children
start dormant and subscribe by validated pack id. After finalizing the snapshot
and starting/verifying every expected application under the bound DAG, the
coordinator opens the barrier with the snapshot digest and expected pack ids.
Each subscriber activates at most once for that digest; a late subscriber gets
the open result deterministically. The M0/M1.a contract freezes the exact API,
timeout, diagnostics, and coordinator/barrier restart behavior. Timeout or
failure keeps product readiness false and performs no effect.

```text
artifact-sealed component-manifest Pack projection
  -> consult .rel and raw .app; verify atoms/version/start mode/.app digest
  -> reject effective-env descriptor override
  -> explicitly load each reconciled expected application spec
  -> reconcile component row / .rel / raw .app / descriptor
  -> pack-module lookup and contribution validation
       malformed or duplicate pack id -> FAIL closed
  -> order packs and actions by the M0-bound stable identities
  -> validate duplicate action names/modules and exposure metadata
  -> compare with M0's ordered registry baseline
       mismatch -> FAIL and disposition before deletion
  -> publish one immutable/cached registry snapshot
  -> start/verify every required native-pack application under the M0 DAG
       missing start or DAG mismatch -> FAIL; product does not report ready
  -> open Pack.Readiness for the finalized snapshot digest
  -> every frozen Actions.Registry surface, including modules, capabilities,
     app filtering, resolution, resumability, duplicate checks, diagnostics,
     and registry-change emission
```

The equality proof covers element order, action names, modules, agent/internal
partitions, resolution results, and three explicit collision classes: a shipped
native collision fails closed; an exact deprecated alias may deduplicate only
after identity/authority parity; a dynamic overlay retains its existing
replacement/precedence contract and does not generalize that rule to packs. An
unordered set comparison is insufficient. Disabled-at-runtime and absent-from-
artifact semantics are separately bound: enablement must not accidentally
change discovery or erase diagnostics.

The `apps/0` proof separately snapshots every current `AllbertAssist.App.Registry`
read/mutation projection, order/collision result, cache invalidation, lifecycle
signal, and default/explicit-server behavior. Native OTP application supervision
remains application-owned; preserving a legacy App-contract surface does not
turn Pack metadata into a native child-spec callback.

M0 also snapshots every public `Plugin.Registry` lookup/mutation/registered
projection, order, diagnostic, source/enablement, action mapping, lifecycle
signal, and residual legacy child-spec observation, plus every
`Extensions.Registry` aggregate projection. M1 must reproduce those snapshots
before `@shipped_modules`, `@reserved_app_owners`, or any compatibility alias is
deleted.

After equality passes, static aliases and lists may be deleted. Adding the next
pack must then require only its application, root release membership, and
first-party component-catalog Pack row, never a kernel registry edit.

### Unsafe-Home maintenance projection

If an affected fragment prevents normal startup, the explicit administrative
entry loads and validates the same signed descriptors but materializes only a
closed maintenance projection: migration status/plan/apply/resume/rollback and
their Settings/Security/confirmation/audit dependencies. Resolution and
execution still use the central Registry and `Actions.Runner.run/3`; all other
actions are unavailable, affected pack applications/effects remain stopped, and
product readiness remains false. Recovery completion triggers a fresh normal
startup; it does not open the product barrier in place.

## §G — Distributed Settings Composition

Settings Central retains resolution, provenance, validation, version checking,
migration orchestration, and the secret vault. Schema ownership moves to the
kernel or the contributing pack without changing stored key names or semantics.

```text
kernel settings contribution + discovered pack contributions
  -> validate unique fragment ids and key ownership
  -> order by the bound deterministic composition contract
  -> compose schema rows, defaults, safe-write metadata, sensitivity,
     fragment versions, deprecations, and cross-key validators
  -> compare complete result with M0 baseline
       mismatch -> FAIL unless explicitly dispositioned
  -> publish settings snapshot with provenance per row and validator
  -> Settings reads/writes resolve through that snapshot
```

The M5 ownership ledger names every moved row and every validator, including
validators that span fragments. Duplicate ownership fails closed and reports
both contributors. Pack enablement must not make an operator's stored settings
unreadable; M0 binds whether a disabled shipped pack still contributes schema
and how an absent pack is diagnosed.

Ownership movement alone preserves serialized values and fragment versions and
therefore does not enter §A. Only a ledger-proven non-additive change invokes a
migration.

## §H — Gate Ownership And Inventory

Gate inversion happens before any test relocation. A gate consumes stable owner
identities and owner-relative test inventories rather than kernel-maintained
source paths.

```text
application / pack contribution
  -> stable gate-owner id + owner application root + lane classification
  -> discover owner-relative tests and support files
  -> validate tags and manifest coverage
  -> resolve selected owner files at execution time
  -> run each owner from its declared CWD
  -> append structured metrics with owner id, lane, seed, count, and SHA
```

M0 binds the exact contribution and discovery interface. The inversion must
cover focused selection, scope classification, source-reading evals, test
support paths, confirmations scanning, inventory tags/manifests, metrics, and
aggregate owner coverage—not merely the visible versioned step lists.

Before M8, the inventory covers every active path-bearing definition and source
reader, especially `release.v1` plus the v1.3/v1.3.1/v1.3.2 definitions. A
structure proof compares normalized ordered step/owner semantics before and
after inversion; literal source paths are expected to become owner-relative and
therefore are not mislabelled as byte identity. A second proof shows that moving
a test between owner applications changes only its owner contribution and that
the aggregate neither loses nor executes it twice.

## §I — Dependency Closure Then Pure Relocation

The zero-content relocation decision applies after dependency closure, not in
place of it.

### Closure checkpoint

Before `apps/allbert_kernel` receives a file, M7.1 records and freezes an exact
move manifest consumed unchanged by M8:

| Field | Required content |
| --- | --- |
| Module | Stable BEAM module name |
| Source and destination | Exact old and new paths, including the owning test |
| Content identity | Pre-move source and test digests |
| Dependencies | Kernel, retained application, and pack references |
| Disposition | Move, retain, split before move, or adapter/port introduced before move |
| Verification | Isolated compile, boundary proof, focused tests, and frozen-contract result |

Content-changing seam inversion occurs in a prior reviewed checkpoint and is
green before relocation begins. This includes closing inward dependencies from
Runner, Registry, Security, Home/Paths, writer locking, and the
`External.HttpPolicy`/`External.RequestSpec` pair. No unresolved kernel-to-pack
reference is waived as “relocation.”

### Pure move checkpoint

```text
clean dependency-closure SHA
  -> create declared umbrella dependency direction
  -> move one manifest-approved source/test group
  -> compare pre/post file contents and module names
       any content change -> FAIL; split back into seam work
  -> compile kernel in isolation from packs
  -> compile every dependent pack/application
  -> run focused owner tests, inherited freeze regression, and boundary proof
  -> record clean relocation SHA and manifest result
```

The compile graph permits packs to depend on the kernel and forbids the kernel
from depending on a pack. The proof includes static/source and runtime/dynamic
references, not only declared Mix dependencies. Gate-owner metadata, not a
version-gate path edit, follows relocated tests.

## §J — Pack Extraction And Hybrid Packaging

Extraction proceeds `notes_files` first, then Telegram and email only after
their exact settings ledgers are dispositioned.

```text
legacy compiled-in capability
  -> create apps/allbert_<pack> with an acyclic declared dependency on
     kernel/allowed packs; no composition-host dependency cycle
  -> move code, tests, settings contribution, gate owner, and owned assets
  -> give the pack an application callback/supervision ownership when needed
  -> add the OTP application to the root release set and its strict first-party
     component-catalog Pack row
  -> discover actions/settings/gates through §§F-H and cross the finalized +
     application-started readiness barrier
  -> prove registry and settings equality
  -> prove feature behavior from source
  -> build provisional artifact
  -> prove assets, license/component-inventory entry, discovery, and feature
     path in package
```

The release remains hybrid while any legacy `plugins/` directory remains:

- extracted pack code and owned assets use its OTP application and `priv/`;
- legacy plugin manifests/assets retain the compatibility staging and scan they
  still require;
- `packs` is the declared-tier path and `plugins` remains a compatibility scan;
- both declared scan roots use the existing validated `allbert_plugin.json`
  grammar; v1.4 does not add a second manifest format;
- schema-version-1 Home normalization retains identity plus contained top-level
  `skill_paths`; top-level `module` and non-empty/non-list
  `contributions.apps|actions|channels|children` reject, while all other unknown
  fields remain inert/ignored and never become contributions;
- one physical contribution is resolved once even if compatibility metadata is
  visible through both paths;
- the global legacy staging step is not removed until its last real consumer is
  removed and package inventory proves parity.

For every extracted pack, evidence records release start mode/order,
supervision children, application environment ownership, `priv` paths,
discovery provenance, settings ownership, gate ownership, license/component
inventory rows (under the existing best-effort, managed-seam contract),
artifact paths, and installed feature behavior. Telegram/email extraction does
not depend on the migration runner unless §A proves an actual non-additive
transition.

## §K — Freeze Supplement And Release Sequence

The v1.0 freeze remains a hard stop through all implementation checkpoints. A
Tier-1 deviation cannot be recorded through and waived in a 1.x release; it
requires a major version and an ADR. The v1.4 closeout adds a generated
topology/ownership supplement while carrying every existing obligation forward.

```text
post-dependency-refresh source shape
  -> generate and commit the source topology/ownership supplement
       no artifact digests/signatures; compare every Tier-1/Tier-2 entry with
       v1.0 and fail on removal/rename/shape drift
  -> push exact clean R4 SHA containing implementation, docs, and supplement
  -> preflight
  -> independent implementation/readiness drift audit
  -> source primary-function FV pre-filter
  -> separate release.v1 hard stop and bounded v1.4 delta gate
  -> generate provisional artifacts tied to the exact clean SHA
  -> record artifact digests, signatures, package inventory, and build identity
       in external release-validation evidence, never back into source bytes
  -> attended packaged FV (acceptance bar)
       executable findings -> one batched remediation rejoin
       tracked-byte docs findings -> source-doc rejoin
       environment findings -> disposition with evidence, no byte change
  -> if tracked bytes changed: return to source supplement/R4, regenerate artifacts,
     and repeat invalidated rows
  -> exactly one authoritative aggregate
  -> repeat only identity, integrity, package smoke, and explicitly invalidated
     operator rows
  -> record ADR 0098 implementation and artifact-binding evidence, publish,
     rehearse install, and close out
```

The committed source supplement is the generated v1.4 section in
`docs/developer/public-contract-freeze.md`; it is part of the exact SHA from
which artifacts are built and contains source ownership/hash evidence only.
`docs/validation/v1.4/` evidence binds that SHA to build id, artifact digests, signatures, packaged FV,
and aggregate results without creating a self-referential artifact. Any tracked-
byte remediation invalidates both SHA and generation and returns to the source
supplement/R4 step. A later administrative closeout commit may reference the
accepted/tagged SHA but must not claim to be the artifact source. From v1.5
onward, authors read the v1.0 freeze together with the v1.4 supplement; the
supplement does not supersede the v1.0 reference.

### Common disposable-Home preflight

This preparation block is paste-executable now. It copies a caller-supplied
configured Home and never writes to the source Home:

```bash
set -euo pipefail

V14_SOURCE_SHA="$(git rev-parse HEAD)"
if test -n "$(git status --porcelain)"; then
  echo "BLOCKED: worktree is not clean"
  exit 2
fi

: "${ALLBERT_FV_SOURCE_HOME:?BLOCKED: set ALLBERT_FV_SOURCE_HOME to the configured source Home}"
V14_SOURCE_HOME="$(cd "${ALLBERT_FV_SOURCE_HOME}" && pwd -P)"
if test "${V14_SOURCE_HOME}" = "/"; then
  echo "BLOCKED: source Home resolved to filesystem root"
  exit 2
fi

same_or_below() {
  local child="$1" parent="$2"
  test "${child}" = "${parent}" && return 0
  case "${child}/" in
    "${parent}/"*) return 0 ;;
    *) return 1 ;;
  esac
}

V14_FV_BASE="$(cd /tmp && pwd -P)"
if same_or_below "${V14_FV_BASE}" "${V14_SOURCE_HOME}"; then
  echo "BLOCKED: scratch base is inside source Home"
  exit 2
fi

reject_unsafe_home_tree() {
  local root="$1" bad
  if IFS= read -r -d '' bad < <(
    find "${root}" -mindepth 1 \( -type l -o ! \( -type d -o -type f \) \) -print0 -quit
  ); then
    echo "BLOCKED: source Home contains a symlink or special file: ${bad}"
    exit 2
  fi
  if IFS= read -r -d '' bad < <(
    find "${root}" -mindepth 1 -name $'*\n*' -print0 -quit
  ); then
    echo "BLOCKED: source Home contains a newline in a path: ${bad}"
    exit 2
  fi
}

portable_lstat() {
  local path="$1"
  # Directory allocation size is filesystem/history-dependent and is not part
  # of logical tree identity; regular-file byte length is framed separately.
  if stat -f '%HT|%Lp|%u|%g|%m' "${path}" >/dev/null 2>&1; then
    stat -f '%HT|%Lp|%u|%g|%m' "${path}"
  else
    stat -c '%F|%a|%u|%g|%Y' "${path}"
  fi
}

sha256_stream() {
  if command -v shasum >/dev/null 2>&1; then
    shasum -a 256
  else
    sha256sum
  fi
}

fingerprint_home_tree() {
  local root="$1" output="$2"
  # Path order is canonical rather than filesystem traversal order. Each
  # relative path and lstat tuple is byte-length-prefixed before regular-file
  # bytes, so ambiguous concatenations cannot compare equal. Unsafe entry types
  # and newline-bearing paths were rejected above.
  (
    cd "${root}"
    export LC_ALL=C
    find . -mindepth 1 -print |
      sort |
      while IFS= read -r rel; do
        meta="$(portable_lstat "${rel}")"
        bytes="0"
        if test -f "${rel}"; then
          bytes="$(wc -c < "${rel}" | tr -d ' ')"
        fi
        printf 'P%010d%sM%010d%sB%020d' \
          "${#rel}" "${rel}" "${#meta}" "${meta}" "${bytes}"
        if test -f "${rel}"; then
          command cat "${rel}"
        fi
      done
  ) | sha256_stream | awk '{print $1}' > "${output}"
}

reject_unsafe_home_tree "${V14_SOURCE_HOME}"
V14_FV_ROOT="$(mktemp -d "${V14_FV_BASE}/allbert-v14-fv.XXXXXX")"
V14_FV_ROOT="$(cd "${V14_FV_ROOT}" && pwd -P)"
if same_or_below "${V14_FV_ROOT}" "${V14_SOURCE_HOME}" ||
   same_or_below "${V14_SOURCE_HOME}" "${V14_FV_ROOT}"; then
  echo "BLOCKED: source Home and scratch root overlap"
  exit 2
fi
V14_FV_HOME="${V14_FV_ROOT}/home"
fingerprint_home_tree "${V14_SOURCE_HOME}" "${V14_FV_ROOT}/source-before.sha256"
cp -a "${V14_SOURCE_HOME}" "${V14_FV_HOME}"
reject_unsafe_home_tree "${V14_FV_HOME}"
fingerprint_home_tree "${V14_SOURCE_HOME}" "${V14_FV_ROOT}/source-after-copy.sha256"
fingerprint_home_tree "${V14_FV_HOME}" "${V14_FV_ROOT}/clone-before.sha256"
cmp "${V14_FV_ROOT}/source-before.sha256" "${V14_FV_ROOT}/source-after-copy.sha256"
cmp "${V14_FV_ROOT}/source-before.sha256" "${V14_FV_ROOT}/clone-before.sha256"
export ALLBERT_HOME="${V14_FV_HOME}"

verify_v14_source_home_unchanged() {
  reject_unsafe_home_tree "${V14_SOURCE_HOME}"
  fingerprint_home_tree "${V14_SOURCE_HOME}" "${V14_FV_ROOT}/source-after.sha256"
  cmp "${V14_FV_ROOT}/source-before.sha256" "${V14_FV_ROOT}/source-after.sha256"
}

echo "PASS: disposable Home=${V14_FV_HOME} source_sha=${V14_SOURCE_SHA}"
```

The source Home must be quiescent for the clone; any concurrent change blocks
the comparison. Rejecting all symlinks is deliberately stricter than merely
rejecting an escaping target and keeps the preflight portable across packaged
hosts. Before it is accepted as release evidence, M0 binds a fixture check that
runs this BSD/GNU `stat` helper on the supported packaged macOS and Linux hosts
and proves identical trees compare equal while path, metadata, and content
changes compare unequal. The operator keeps `V14_FV_ROOT` for evidence and
removes it only after release closeout under the normal evidence-retention
procedure. Each FV row calls
`verify_v14_source_home_unchanged`; any difference is `FAIL` and stops the
sequence.
