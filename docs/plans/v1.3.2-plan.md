Request flow: `docs/plans/v1.3.2-request-flow.md`
ADRs: no new ADR. `mix allbert.test preflight` is release tooling, not an
authority boundary. `model_roles.*` ships under ADR 0090 §4, which already
decided the per-role naming layer; this release lands the resolution half of
that decision and **not** the suggestion-driven remap path, which stays with
ADR 0090's own release (v1.8). Consumes ADR 0088 (catalog the roles resolve
against) and ADR 0072/0061 (model substrate) unchanged.

Status: **in progress — M0 complete; M1 implementation and focused evidence
complete on 2026-08-06.** M2 is the active milestone. The
implementation-readiness contract was frozen at `bd79ff9dc` immediately before
M0.

Source: the 2026-08-06 operator resequencing. Both items were milestones of the
adaptive-profiling release (then v1.4, now v1.8) and were extracted because
**every later release depends on them and nothing depends on profiling**.
Bundling foundation behind a flagship feature was the single largest constraint
on the 1.x ladder: it forced the spine release to wait on profiling for
preflight, and Knowledge Central to wait on it for `model_roles.capable`.

This is an operator-approved **source-only** point tag carrying
`[skip-artifacts]`. No GitHub Release, native archive, checksum bundle, cosign
operation, Homebrew change, packaged FV, or Latest movement occurs. v1.3.0
remains the packaged Latest; both enablers reach packaged operators at v1.4.

## Purpose

v1.3.2 is complete only when all four outcomes hold:

1. `mix allbert.test preflight` exists as one cheapest-first gate that
   completes under two minutes and can be made the mandatory predecessor of
   every expensive phase;
2. every recorded predecessor stop cause has a red-first row proving preflight
   catches its class;
3. `model_roles.fast|capable|thinking` resolve as an additive naming layer over
   the ADR 0088 catalog, with existing concrete purpose chains byte-for-byte
   unchanged; and
4. the accepted code is tagged source-only without creating artifacts or moving
   the packaged v1.3.0 release/tap.

### Why these two are together

They have nothing in common as features. They are together because they share
one property that nothing else in the profiling release has: **other releases
are blocked on them.**

- **preflight** is what makes v1.4's sweep over 249 action modules cheap to
  fail. v1.3 M9.b burned six authoritative release attempts, none stopped by a
  product regression; every one was cheap, deterministic, repo-wide, and ran
  late or was not in a gate at all. Landing preflight *before* the largest
  mechanical sweep on the ladder is the entire point.
- **`model_roles`** is a hard dependency of Knowledge Central (v1.6 ingest uses
  `model_roles.capable`) and the consumer that makes hosted-provider OAuth
  meaningful (v1.7).

Shipping them as one small source-only tag costs one release cycle and unblocks
four.

## Locked decisions

1. **Source-only, `[skip-artifacts]`, v1.3.1's precedent.** The source version
   advances to 1.3.2; the installed product line remains v1.3.0 until v1.4
   packages the accumulated source changes. Consequence stated plainly: an
   operator cannot use `model_roles` from a packaged build until v1.4.
2. **preflight is tooling, not authority.** It gates when expensive work may
   start. It grants nothing, denies nothing at runtime, and has no ADR because
   it decides no boundary.
3. **This release ships the resolution layer only.** `model_roles.*` resolve;
   nothing *proposes* a remap. The suggestion-driven remap path, its allowlist
   entry, and the egress-class guard (same provider/endpoint/locality) stay in
   v1.8 with the rest of ADR 0090's confirmed-customization machinery. Landing
   resolution early is additive; landing the remap path early would ship half of
   an authority boundary.
4. **Nil-default, concrete-profile-only.** Role mappings accept concrete
   profiles only, so cycles are rejected at write time. An unconfigured role, a
   missing profile, or a provider-disabled/unavailable mapped profile records a
   diagnostic and continues with the next item in the existing purpose chain;
   it never invents a fallback. Resolution retains both the requested role and
   the concrete profile so a later consumer can report which it asked for.
5. **Existing behavior is byte-for-byte unchanged.** Purpose keys that name
   concrete profiles today keep resolving exactly as they do. This is provable
   and must be proved, not asserted.
6. **preflight dogfoods itself.** This release runs its own preflight before its
   own expensive phases. A gate that has never gated anything is not evidence.
7. **v1.3.1's temporary bridge retires here.** v1.3.1 M0 ran a named
   constituent bundle precisely because `preflight` did not exist. Once
   red-first rows prove equivalence, the bridge is removed rather than left as a
   parallel convention.
8. **No aggregate per fix.** Focused owners per milestone; the bounded
   `release.v132` delta once; exactly one `mix allbert.test release` aggregate
   at the final rejoin.
9. **One central reference seam, bounded consumers.** v1.3.2 adds role-reference
   expansion to `AllbertAssist.Settings.Models` and uses it for the
   `model_preferences.tasks.*` chains that this release and Knowledge Central
   consume. Scalar coding/router settings that currently bypass
   `Settings.Models` are not claimed as consumers. Later migrations must call
   the same resolver rather than create surface-local role logic.
10. **Compatibility is a bounded rejoin, not local preflight.** The production
    source pair runs on every preflight. The Elixir 1.20.2/OTP 29 probe runs in
    the immutable official image
    `elixir:1.20.2-otp-29@sha256:7ee41a9a8a8427dbd40c9133ee5b9047f585b58db4968fd675fbcd9498e3b22e`
    after dependency/gate/compiler-facing changes and once at the final clean
    SHA. Documentation-only and unrelated focused remediations do not rerun it.

## Workstreams And Serial Barriers

After M0, two bounded workstreams may proceed independently:

- **W1 — release tooling:** preflight composition, exact-state attestation,
  owner-CWD test loading, fixture sentinels, scope selection, and the advisory
  compatibility probe.
- **W2 — model roles:** Settings fragment/schema, central reference expansion,
  chooser/catalog DTO, and operator rendering.

Each workstream runs only its named focused owners while changing. Their first
serial rejoin is M3 documentation/drift reconciliation. M3.1 then requires an
independent full post-implementation review by another agent before attended
source validation begins at one exact clean pushed SHA. Only after validation
passes do `release.v1`, the bounded `release.v132`, and the one authoritative
aggregate run. A finding invalidates its focused owner and affected attended
row; it does not trigger an aggregate per fix.

### M2 — Nil-default model roles

`[code]` `[docs]`

Implement a `model_roles` Settings fragment with `schema_version: 1` and the
three nil-default profile mappings. Extend profile-list validation so only
`model_preferences.tasks.*` accepts the reserved references
`role:fast|capable|thinking`; mappings themselves accept **concrete profiles
only**, so a `role:*` mapping is rejected at write time. Either operator write
order is valid: a purpose chain may reference an unconfigured role before the
mapping is set.

`Settings.Models.for/2` and `candidates_for/2` expand through one central
reference function. An unconfigured role, missing mapped profile, disabled
provider, or incapable mapped profile contributes a redacted diagnostic and
continues to the next chain item. Expansion deduplicates by resolved physical
profile while preserving first occurrence, so `role:fast` and a later concrete
name cannot invoke the same provider twice. Concrete `"fast"` remains the
existing catalog profile and is distinct from `"role:fast"`.

Role resolutions add provenance without changing the public map returned for
legacy concrete selections: role-specific metadata carries
`requested_reference`, `requested_role`, and `resolved_profile`; concrete
resolutions retain their exact existing map/output bytes. The central catalog
DTO reports all three roles and an `assigned_roles` list per profile; CLI, TUI,
and Web render that action-owned DTO rather than reading Settings locally. Nil
roles render as `unconfigured` and never imply that profile `fast` is role
`fast`.

Explicitly **not** in this release (LD3): any path by which a suggestion, card,
or automated process proposes a remap; the customization-allowlist entry for
`model_roles.*.profile`; and the same provider/endpoint/locality egress guard.
Those are one authority boundary and ship whole in v1.8.
