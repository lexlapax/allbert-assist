## Purpose

Ship the 1.2 flagship: install, open, chat. First run auto-detects an
already-provisioned model provider, auto-selects it local-preferred among
usable candidates, enables
direct answers with an audited disclosure, and never dead-ends when nothing
is provisioned. Onboarding survives as an optional, step-addressable
customization surface, and the model surface gains a real catalog/chooser
and an opt-in fallback policy.

1. **Zero-click chat-ready.** A fresh Home with any reachable provisioned
   provider (configured local endpoint, localhost Ollama with a usable
   model, or a configured hosted profile whose key reaches the provider)
   answers the operator's **first question with the
   model, zero prior clicks**, on every surface — web workspace, packaged
   `allbert tui`, dev `mix allbert.tui`, `allbert ask`, bare `allbert` —
   with the one-time disclosure visible (ADR 0087 §1–§3).
2. **Honest empty state, no dead ends.** A fresh Home with nothing
   provisioned still opens a working chat: the deterministic fallback
   answers, exactly one primary repair CTA per detect state is presented
   (one-click curated pull / guided install / BYOK), and no wizard wall or
   TUI refusal exists anywhere (ADR 0087 §4).
3. **Onboarding is optional and step-addressable.** Every wizard step is
   directly enterable at any time, including after completion; re-entry and
   rewind never re-gate chat or the TUI; `onboarding_complete` stops gating
   anything user-facing (ADR 0087 §5, ADR 0069 amendment).
4. **A real model catalog and chooser.** One read-only catalog (curated
   local + live runtime inventory + configured profiles + verified hosted
   metadata) rendered by web/TUI/CLI/onboarding through registered read-only
   actions; selection and pulls write only through existing Settings actions
   (ADR 0088 §1–§2).
5. **Fallback with an egress line.** Selection-time local-first ordering is
   always on; runtime failover is default-OFF opt-in, local→hosted is
   double-gated, at most one failover per turn, every event audited, and the
   whole-chain-failed message stays honest (ADR 0088 §3).
6. **The consent line is redefined deliberately, not incidentally.**
   ADR 0087 Accepted; the DIT-2-class acceptance criteria replaced; an
   operator-stored `false` is never overridden; detection never provisions
   (no installs, pulls, key writes) and performs no hosted egress.

## Locked Decisions

Decisions 1–3 are operator-locked (2026-07-24 planning review); the rest are
derived from those three plus code evidence, recorded for veto at plan
review.

1. **Auto-enable on any detected configured provider (operator).**
   Availability-first, local-preferred order: a healthy configured local
   endpoint → healthy localhost Ollama → configured hosted key. An unusable
   local rung (`model_missing`, `runtime_unhealthy`, or
   `below_hardware_floor`) does not block a configured hosted rung; hosted
   selection carries the pre-egress disclosure and local repair remains a
   secondary suggestion. Detection is enablement; provisioning is consent.
   ADR 0087 and request-flow §D.0 bind the projection and guardrails.
2. **Additive-only release (operator, applies to 1.2–1.4).** No non-additive
   migration; the Settings Runtime Migration Runner stays on the 1.5/1.6
   train; legacy `intent.*model_profile` aliases remain untouched. Each
   milestone's acceptance includes "no non-additive migration introduced".
3. **Validation is flagship-focused FV rows (operator).** The v1.1
   OV-00..OV-12 correction is the standing convention: FV-01..FV-03 cover
   only the primary Zero-Click First Run feature set (local first answer,
   honest empty-state repair, hosted first answer + sticky revert), opened
   only after one uninterrupted authoritative release gate at the pushed
   candidate SHA. Onboarding navigation, catalog/chooser, fallback, and the
   model bakeoff are supporting scope and MUST be proven by automated suites
   or scripted machine-verifiable external smokes, never operator FV. No
   validation-only product capability may ship (M12.11 principle).
4. **Sticky explicit-false (derived, v1.1 LD32 pattern).** Auto-enablement
   fires only when the consent key is absent (schema default). An
   operator-stored `false` is never overridden by detection; disabling once
   means disabled until the operator re-enables. **Stickiness is per-key
   across the whole write set (third readiness pass):**
   `intent.direct_answer_model_enabled` gates whether enablement runs at all;
   `intent.model_assist_enabled` and `model_preferences.primary` are each
   written only when raw-absent. An explicitly stored value on ANY of the
   three is preserved — a one-key stickiness rule would let detection
   overwrite an operator's stored `model_assist_enabled: false`, which is the
   same defect LD16 exists to prevent, one key over. The provenance audit row
   records which keys were written and which were already present.
5. **Disclosure, not confirmation (derived, ADR 0087 §3).** One-time durable
   marker per surface; text generated from the audit provenance
   (`enabled_by: detection`, profile, provider class); hosted selection
   names the provider and the egress fact before the first message is sent.
6. **Detection never provisions and never performs hosted egress (derived).**
   No installs, no pulls, no key writes from detection; hosted detection is
   key presence only; model pulls stay one-click confirmation-gated.
7. **TUI guard inversion with dev/packaged parity (derived).** The TUI
   always starts; non-ready detect states render as in-TUI guidance.
   `mix allbert.tui` and packaged `allbert tui` adopt identical posture —
   the current divergence closes.
8. **`onboarding_complete` is decoupled from availability (derived).** It
   remains a wizard-progress marker only. Rewind/step re-entry never
   re-gates chat, never re-triggers auto-open, never re-blocks the TUI.
   The ADR 0069 false-complete rule stands: the wizard still cannot claim
   complete while readiness is non-ready. **Completion is decoupled from
   consent (operator, 2026-07-26):** `first_chat_ready?/1`
   (`onboarding.ex:325-327`) today requires readiness `:ready` AND the
   consent key `true`, so a sticky-disabled Home could never finish the
   wizard — a permanent dead end of exactly the class Purpose #2 removes.
   M3 completes the wizard on readiness `:ready` alone, records the model
   step as explicitly declined, and surfaces a ONE-TIME "re-enable model
   answers?" affordance on that step which never nags again. The ADR 0069
   false-complete rule is preserved in its real sense: completion still
   requires a genuinely ready model path, not a consent flag.
9. **Detection stays off the hot turn path (derived).** Boot-time +
   event-driven (settings change, explicit re-detect); results cached
   through the existing `detect_details` caching seam (M7.9 precedent).
   M6 carries a measured budget: no regression to the decide-turn baseline
   and a bounded boot-to-ready cost, both cited from the metrics store.
10. **Catalog per ADR 0088 §1 (derived).** Four merged sources; `llm_db`
    fitness is an M4 verification with the result recorded either way;
    exposure only via registered read-only actions; the chooser writes only
    through existing settings actions and safe-write keys.
11. **Fallback split per ADR 0088 §3 (derived).** Selection-time ordering
    always on; runtime failover default OFF
    (`models.fallback.enabled=false`), local→hosted double-gated
    (`models.fallback.allow_local_to_hosted=false`), at most one failover
    per turn (`models.fallback.max_failovers_per_turn` default 1, clamp
    1..2), every event traced + audited, reply metadata names a non-primary
    answering profile.
12. **Gate = `release.v12` stacked on `release.v11` (derived).**
    `@release_v12_steps = @release_v11_steps ++ @v12_focused_steps` — the
    v105-on-v104 stacking precedent; v1.1's fan-out contracts are one
    release old and stay enforced; the added wall cost is minutes. The
    docs-gate active-plan list (`allbert.test.ex:212-219`) gains the v1.2
    triad in the same commit that starts the build.
13. **Behavioral eval rows from day one (derived, M12.5 lesson).** The
    `:v12` rows ship with the v11-style meta-contract (exact id set,
    distinct assert sets, production-boundary execution, no source-grep
    proofs) as a red-first deliverable of M7 — and the two flagship
   acceptance scenarios (zero-click answer; empty-state repair path) land
   as ordinary automated regressions in M1b/M2, before any UI milestone,
    so operator validation cannot be the first end-to-end execution
    (M12.12 lesson).
14. **DIT-2-class acceptance criteria are replaced, not patched (derived,
    ADR 0087 §6).** The plan's M9 documentation deliverable rewrites the
    first-run acceptance rows; stale criteria may not survive in
    `docs/validation/` or operator guides.
15. **Fresh-Home fixtures are the validation substrate (derived, M12.9
    lesson).** Every automated acceptance scenario and every FV row runs
    against a disposable Home; nothing touches `~/.allbert`; no cloned
    state weakens clean-install evidence; runbooks avoid `set -e`/`exit`.
16. **Raw presence is the consent fact, and the primitive is multi-key
    (readiness review; corrected third pass).** Effective `Settings.get`
    values are default-merged and cannot distinguish absent from explicitly
    stored `false` — `Store.put_user_setting/3` demonstrates the trap
    directly, computing `old_value` from the merged map (`store.ex:167`).
    M1a adds ONE Store-owned atomic compare-and-write operation that reads the
    raw user-settings map, checks `Schema.get_dotted(user_settings, key)`,
    and writes under the same `StoreLock`; `nil` may auto-enable, stored
    `false` is sticky, stored `true` is idempotent. No caller performs a
    read-then-write sequence.
    **The primitive takes a key→value MAP, not one key.** Enablement writes
    three keys and the plan requires atomic application of the raw-absent
    subset; `StoreLock.with_lock/2`
    opens a fresh connection and issues `BEGIN EXCLUSIVE`
    (`store_lock.ex:29-40`), so it is NOT reentrant — composing the operation
    out of three per-key writes either self-deadlocks for the 5 s timeout or
    produces three non-atomic commits that can strand
    `direct_answer_model_enabled: true` beside `model_assist_enabled: false`.
    One lock, one raw read, absent-key filter, one merged validation, one
    write, one audit row per applied key, and one transaction provenance
    envelope listing applied and preserved keys. Validation failure writes
    none of the absent subset.
17. **M1a owns a minimal usable-model selector (readiness review).** First-run
    cannot depend on the M4 chooser. M1a selects: configured doctor-healthy
    local profile; otherwise the curated pulled tag; otherwise the first
    pulled text-generation model that passes a deterministic compatibility
    predicate recorded at M0. M4 reuses this predicate in the catalog rather
    than replacing it. If that predicate cannot be made trustworthy, M1a is
    deliberately curated-tag-only and `detected_needs_model` remains honest.
18. **Hosted detection is configured-but-unverified (readiness review).** Key
    presence performs no probe and makes no reachability claim. Hosted
    priority is existing explicit `model_preferences.primary`, then
    task-specific configured order, then a stable provider order recorded at
    M0; never environment enumeration order. A bad/expired key may enable the
    configured path but its first failed turn returns the honest unavailable
    state and repair CTA, never a false `provider_ready` claim.
19. **Disclosure precedes hosted transport atomically (readiness review).**
    Every entrypoint, including one-shot `allbert ask`, durably records the
    pending disclosure, renders/acknowledges it, and only then admits hosted
    inference. A crash before acknowledgement causes disclosure to repeat,
    not egress to occur first; the durable marker is consumed only after
    render acknowledgement. Local inference does not require an egress ack.
20. **Fallback classification is adapter-owned (readiness review).** M5
    records a table mapping concrete ReqLLM/provider/streaming results to
    `definitive | ambiguous | partial`; unknown shapes default to `partial`
    (no retry). Provider adapters normalize errors before the executor decides;
    the executor never parses exception strings.
21. **Budgets are fixed at M0 (readiness review).** M0 records numerical
    cross-platform cold/warm boot-to-ready, time-to-first-token, peak-memory,
    and decide-turn regression thresholds before M1. M6 proves those fixed
    thresholds; it may not choose a favorable bound after implementation.
22. **Curated-model change is evidence-gated (operator confirmed
    2026-07-26).** The candidate set includes `llama3.2:3b` (control), Qwen 3
    4B instruct/non-thinking, `qwen3.5:4b` (direct successor), and
    `qwen3.5:9b` (higher-floor quality challenger). Exact tags/digests are
    reverified at M0; first-run trials force non-thinking behavior while
    thinking variants remain catalog options.
    Thinking variants are catalog options, not the zero-click default. A
    candidate tag that does not exist publicly at M0 records `BLOCKED` and is
    dropped from the bakeoff; it is never silently substituted with a
    nearest-name tag. Test
    macOS arm64, Linux x64/arm64, and WSL2 where the release supports them;
    record download bytes/time, cold/warm TTFT, tokens/sec, peak RSS, direct-
    answer quality, tool/JSON conformance, malformed-call rate, multilingual
    behavior, context behavior, license, and exact public Ollama tag/digest.
    **Promotion targets macOS arm64 AND Linux x64 measured. One of those two
    primary rows may record `BLOCKED` only with explicit operator disposition
    naming the unavailable host and evidence gap; Linux arm64 and WSL2 may
    also record `BLOCKED` with their gaps named in Build Progress and in the
    CHANGELOG entry.**
    Promotion requires material Allbert-suite improvement without materially
    regressing first-answer latency. Raising the current 8 GB floor is allowed
    when the quality/tool-reliability gain is recorded and the operator accepts
    the reach tradeoff. A raised floor must produce an explicit consumer /
    prosumer disposition: either retain a lower-floor consumer curated default
    and recommend the winner as the prosumer profile, or promote the winner and
    prove the existing `below_floor` BYOK/repair path on excluded machines. No
    machine is silently reclassified as ready. Changing the default or tier
    updates every schema/catalog/doc/test occurrence as one M4 commit.
23. **Competitive bar, not parity scope (readiness review, 2026-07-26).** Hermes sets
    the bar for model choice, learned skills/memory, and delegated work;
    OpenClaw for gateway/channel activation and remote availability; IronClaw
    for packaged security/privacy positioning. v1.2 answers only the shared
    activation gap. Allbert differentiates through Security Central,
    registered actions, durable Objectives, audited settings, and one runtime
    spine; no autonomous skill/memory expansion or new channel scope enters
    this release.
24. **Availability-first with local preference (operator, 2026-07-26).** A
    healthy local provider always wins. When the local runtime is present but
    unusable (`model_missing`, `runtime_unhealthy`, or
    `below_hardware_floor`) and a hosted key is configured, Allbert
    auto-enables the hosted profile so the first question still receives a
    model answer. The disclosure names the provider and egress before the
    send; the relevant local pull/restart/hardware guidance is secondary and
    never blocks chat. Without a hosted key, the same states remain honest
    repair states with one primary CTA. Request-flow §D.0 is the binding
    derivation table and every cell is automated in M1b/M6.
25. **Auto-enablement has no global off switch (operator, 2026-07-26).** The
    per-Home sticky explicit-false (LD4) is the only control. v1.2 adds no
    `first_run.auto_enable.*` policy key; a fleet/packaged policy lever is out
    of scope and is recorded in Non-Goals so a later release can revisit it
    deliberately rather than by drift.

## Operator-Visible Win

Install Allbert, open it, and ask a question — it answers. No wizard, no
toggle, no "Start QuickStart". If you already run Ollama, it finds it; if
you configured a provider key, it uses that (and says so, once, with the
revert command). If you have nothing, the chat still opens, answers
honestly, and shows exactly one button that fixes it. Want to customize?
Open onboarding anytime, jump straight to any step. Browse models in a real
catalog instead of typing tags — and if you opt in, Allbert survives a dead
provider by falling back down a chain you configured, never silently
falling into a paid one.

## Competitive Readiness Bar (research refreshed 2026-07-26)

- **Hermes Agent:** one-command/desktop activation, `hermes model`, broad
  provider choice, delegated subagents, scheduled work, and a visible learning
  loop across bounded memory and agent-managed skills. Source:
  <https://hermes-agent.nousresearch.com/docs/>.
- **OpenClaw:** a single self-hosted gateway connecting many chat channels to
  sessions, memory, agents, web control, and mobile nodes; its product promise
  is reachability from where the operator already chats. Source:
  <https://docs.openclaw.ai/>.
- **IronClaw:** packaged cross-platform Agent OS positioning centered on
  privacy, encrypted local credentials, onboarding, model status, and
  extensibility. Source: <https://github.com/nearai/ironclaw> and
  <https://docs.ironclaw.com/>.

The 1.2 answer is narrower and testable: Allbert removes the setup toll before
first value while retaining a stronger explicit-authority story. Success is
not feature-count parity; it is a first useful answer with fewer decisions,
honest repair when no model exists, and no weakening of the action/security
spine.

## Planned Interfaces

- `AllbertAssist.FirstRun.Enablement` (name final at M1) — the
  detection→enablement engine: consumes the existing
  `FirstRun.detect_details/1` chain, applies the ADR 0087 §1 ordering,
  performs the audited safe-write pair + profile selection when the consent
  key is absent, records provenance, and exposes
  `enablement_state/1 :: :auto_enabled | :sticky_disabled | :needs_model |
  :nothing_detected | :below_floor | :enabled_unavailable` for surfaces.
  Idempotent; no hosted egress; one atomic audited settings transaction.
  `:enabled_unavailable` covers the most common real-world dead end — a Home
  auto-enabled against a local runtime that has since disappeared, where the
  consent key is `true` but every turn returns `{:model_unavailable, _}`. It
  renders the honest unavailable text plus the same repair CTA as
  `:nothing_detected`, and never re-shows the disclosure. States derive from
  the six existing `model_state` values per request-flow §D.0; this enum is a
  presentation projection, not a seventh detection state.
- `Settings.Store.put_user_settings_if_absent/2` (name final at M1) — one
  StoreLock-owned raw-presence compare-and-write primitive over a key→value
  MAP (LD16: single-key cannot atomically apply the absent subset under a non-reentrant
  lock). Inside one `StoreLock.with_lock/2` + `Fragments.with_composition/1`
  — the existing `store.ex:158-162` shape — it reads raw `user_settings`
  once, tests each key with `Schema.get_dotted(user_settings, key)`, applies
  only absent keys, validates the merged result once, writes once, and emits
  one audit row per applied key plus one transaction provenance envelope
  listing written and preserved keys. Returns
  `{:ok, %{written: [key], present: %{key => value}}}`; a validation failure
  writes nothing. Never treats a schema default as an operator value. No
  caller may nest `StoreLock` or rebuild this out of per-key writes.
  **Write layer:** enablement is system-initiated, so it writes through
  `Settings.Store` (which audits) rather than a registered action (which is
  the agent-facing boundary). It is not a new privileged capability: it writes
  only the three named keys, only when raw-absent, only from the boot/detect
  path, and M1 proves no other key is reachable through it.
- `FirstRun.UsableModel` (name final at M1) — deterministic compatibility
  predicate and local selection order shared first by detection and later by
  `Models.Catalog`; no catalog/UI dependency in M1.
- Disclosure surfaces: pending/acknowledged marker helper (Home marker file, per
  surface) + renderers — web chat preface, TUI banner line, CLI first-run
  paragraph. Text derives from the audit provenance record. Hosted paths use
  a durable pending→acknowledged state machine: transport admission requires
  acknowledged disclosure; crashes fail closed and may repeat disclosure.
  Per-surface acknowledgement mechanics (v1.1 delivery-ack precedent):
  **web** acknowledges an exact mounted delivery handle bound to the LiveView
  socket — absent, stale, or forged leaves the disclosure `pending` and hosted
  transport inadmissible; a reconnect re-renders and re-acknowledges rather
  than assuming the prior mount delivered. **TUI/CLI** acknowledge after a
  successful write to the output stream, whether or not it is a tty — a
  redirected `allbert ask "x" > out.txt` is acknowledged when the write
  succeeds, matching v1.1's "after every kickoff line is written" rule.
  Per-surface marker keys are updated read-modify-write through the existing
  atomic marker path (`cli/first_run.ex:301-310`); a lost update under
  concurrent first boot of two surfaces may only REPEAT a disclosure, never
  suppress one.
- `AllbertAssist.Models.Catalog` — `list/1` merged rows (source, id,
  size, capabilities, floor, purposes, status), backed by the curated
  catalog file (`priv/model_catalog/*.yaml` or equivalent), Ollama tags,
  configured profiles + doctor status, and (conditional) `llm_db` hosted
  metadata. Registered read-only actions: `list_model_catalog`
  (`exposure: :internal`, `permission: :read_only`); `model_doctor`
  unchanged.
- Fallback: `Settings.Models.candidates_for/2` extended to text
  generation; a bounded failover executor inside the direct-answer path
  (classification: definitive advances, ambiguous advances once, possible
  partial-answer never silently retried); trace + audit events
  (`Runtime.Audit` existing kinds or an additive `:model_fallback` kind —
  M5 decides against the audit-writer precedent). Provider adapters emit a
  typed normalized result; unknown/partially streamed outcomes classify as
  `partial` and are never retried.
- New Settings Central keys (additive fragments, ADR 0031):
  `models.fallback.enabled` (false), `models.fallback.allow_local_to_hosted`
  (false), `models.fallback.max_failovers_per_turn` (1, clamp 1..2),
  `first_run.disclosure_shown.*` only if the marker cannot carry it (prefer
  the Home marker; Settings is not a per-surface flag store).
- Changed policy surfaces: `Workspace.FirstRun` auto-open states (auto-open
  only for repair states, never as a chat gate), `CLI.Tui.readiness_guard`
  inversion + parity for `mix allbert.tui`, chat first-run CTA states per
  the ADR 0087 §4 matrix.
- `mix allbert.test release.v12` — the release gate
  (`@release_v11_steps ++ @v12_focused_steps`).

## Security Posture

This release moves a consent line and is planned like it:

- **The only relaxation is ADR 0087's**: detection of an already-provisioned
  provider enables direct answers without a wizard step. Compensating
  controls are structural: sticky explicit-false, audited provenance,
  one-time disclosure naming provider + egress class, strict usable-local-first
  ordering, and zero provisioning/egress in detection itself. Gate-bound
  `:v12` rows enforce each (request flow §G).
- **Nothing else grants.** Catalog reads are `permission: :read_only`
  registered actions; chooser writes ride existing settings actions and
  safe-write keys; pulls stay confirmation-gated; fallback never crosses
  local→hosted without the double gate; `Security Central`, the vault
  model, and provider key custody are untouched.
- **No new egress class:** detection probes only loopback/configured-local
  endpoints; hosted "detection" is key presence; catalog hosted metadata is
  static; the only new egress possibility (hosted failover) is double-gated
  and audited.
- Secrets remain encrypted/redacted end-to-end; disclosure and audit text
  never include key material or raw endpoints (doctor envelope rules).

## Non-Goals

- Removing the wizard, the QuickStart/Advanced tracks, or the persona
  system — they persist as the customization surface.
- Removing or migrating legacy `intent.*model_profile` aliases (1.5/1.6
  migration-runner cluster; additive-only rule).
- OAuth-authenticated hosted providers (1.4/1.5 enabler train); the catalog
  lists what exists, it does not add provider auth.
- Bundling a model or model runtime into the artifact (ADR 0078 stands).
- Auto-pull, auto-install, or any zero-click provisioning.
- A global/fleet policy switch disabling detection-based enablement (LD25).
  Per-Home sticky explicit-false is the only control in 1.2; a
  `first_run.auto_enable.*` policy key is a deliberate later decision, not an
  omission.
- Multi-user/remote first-run semantics; mobile-ready web (rides 1.4).
- Per-role fast/capable/thinking profile schema (v1.4, ADR 0090 scope).

## Validation Design (the v1.1 churn guardrails, binding)

The v1.1 M12.4–M12.13 corrective chain is the negative example this plan is
built against. Binding rules, each carried by a named milestone above:

1. **No validation-only product capability** (M12.11): nothing ships in
   `lib/` whose sole purpose is producing validation evidence. FV rows use
   the product as an operator would.
2. **The flagship scenarios are automated first** (M12.12): zero-click and
   empty-state land as fresh-Home regressions in M1b/M2; FV re-executes what
   CI already proves, live.
3. **Behavioral eval rows with the meta-contract** (M12.5): no structural
   presence checks, no source-grep proofs, no shared assert triples.
4. **Capability wiring is census-proved, not grep-inferred** (M12.6): the
   surface matrix suite enumerates web/TUI-packaged/TUI-dev/CLI explicitly.
5. **Disposable Homes only** (M12.9): no FV row touches `~/.allbert`; no
   cloned state; runbooks are paste-executable without `set -e`/`exit`.
6. **FV opens once, after one green uninterrupted authoritative gate at the
   pushed candidate SHA**; the corrective loop is fixed: fix → focused →
   `mix precommit` → `release.v1`/`release.v12` → authoritative gate →
   reopen FV. No renumbering, no ad-hoc rows.
7. **Supporting scope is machine-proved.** Onboarding navigation,
   catalog/chooser, fallback, and model-candidate evaluation have no FV row.
   Their automated suites and scripted external-smoke records are release
   evidence and must be green (or carry an allowed operator-disposed BLOCKED
   host row) before the authoritative gate opens FV.
