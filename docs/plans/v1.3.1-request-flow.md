## §A — What This Release Does Not Touch

```
chat turn ──▶ intent classification ──▶ DirectAnswer ──▶ answer
                                             │
                                             └── UNCHANGED by v1.3.1
```

No request path changes. The qualification bar never runs inside a turn, never
gates an answer, and never inspects operator content. A head that fails the bar
still answers exactly as it does today; the bar informs the operator, it does not
police the runtime.

This is the ADR 0021 line. A future-tense detector in the request path would be a
domain oracle deciding product behavior, and it stays forbidden. A frozen offline
corpus with recorded expected values, run by an operator against a candidate
model, is evidence about a model — not an oracle inside Allbert.

## §B — Qualification Run

```
mix allbert.test qualify-head [--profile <name>] [--trials N] [--output <path>]
  │
  ├─ resolve profile ── from intent.direct_answer_model_profile, or --profile
  │     └─ record: profile name, provider, model, endpoint digest, trials
  │
  ├─ load frozen corpus  (test/fixtures/v1.3.1/head_qualification.json)
  │     ├─ schema validate ── fail closed BEFORE any provider call
  │     └─ digest check   ── recorded in evidence
  │
  ├─ for each row × N trials:
  │     ├─ issue through the PRODUCTION DirectAnswer request path
  │     │     (same temperature 0.0, same max_retries 0, same rule catalog)
  │     ├─ provider unavailable / empty / refusal ──▶ recorded as FAIL
  │     └─ score deterministically (§C) ──▶ pass|fail per trial
  │
  └─ aggregate ──▶ per-row pass counts, per-class pass rate, verdict vs. the
                   frozen minimum
```

Running through the production request path is deliberate. v1.3 SV-6A.1a.ii spent
thirty-six trials establishing that a failure reproduced in *no* condition,
including a hand-built harness; a bar that used its own prompt assembly would not
be measuring the head Allbert actually ships.

## §C — Scoring Boundary

```
model answer ──▶ scorer ──▶ {pass|fail}
                    ▲
                    │ frozen expected value from the corpus row
                    │   factual row:     the recorded discriminating fact
                    │   instruction row: the recorded closed criterion
                    └── NO model judge, NO heuristic quality score
```

Two row classes, two closed predicates:

- **Factual.** The row records the one fact that discriminates a correct answer
  from the observed wrong one. The `rest_for_one` row passes only on an answer
  stating that the failed child *and the children started after it* restart; an
  answer describing only the failed child fails, which is precisely the v1.3
  observation.
- **Instruction-following.** The row names the DirectAnswer rule under test and
  its criterion. The acknowledgment row scores `no_future_commitment`: an answer
  asserting that something will happen on a schedule fails, whatever else it
  says.

A scorer that cannot decide a trial records it as a fail and says so. There is no
"unscored" bucket, because an unscored bucket is where a failing head hides.

## §D — Evidence

```
qualification run ──▶ TestMetrics rows (repo metrics store)
                        {run_sha, profile, provider, model, endpoint_digest,
                         corpus_digest, row_id, class, trials, passes,
                         class_pass_rate, minimum, verdict}
                      NEVER prompts, NEVER answers, NEVER operator data
```

Content-free by construction, matching the `v13_fanout_eval` recording contract.
A reader can reproduce any row from the corpus digest plus the row id; nothing in
the store leaks what was asked or what came back.

## Authority Invariants

1. The bar never changes an answer, a default, or a setting. It reports.
2. No model scores another model's output, anywhere in this release.
3. Provider unavailability fails the run rather than silently shrinking it.
4. The minimum pass rate is frozen in the plan before any head is measured.
5. Recorded evidence carries digests and counts, never content.

## Attended Operator Validation (HQ-0 … HQ-5)

Written for a disposable Home, paste-executable, each step carrying its own PASS
criterion. Concrete commands are written at build time against real code, not
guessed here — a lesson v1.3 attended validation charged four defects for.

- **HQ-0 — clean tree and full rebuild.** `mix compile --force
  --warnings-as-errors` from a clean checkout at the pushed SHA; record the SHA.
  PASS: zero warnings, SHA recorded.
- **HQ-1 — corpus integrity.** Run the owner tests for fixture schema and digest
  with no provider reachable. PASS: green, and the run fails closed rather than
  scoring zero rows.
- **HQ-2 — scorer on fixed inputs.** Feed the scorer the v1.3-recorded wrong
  answers and the corresponding correct ones. PASS: the recorded failures score
  fail, the correct answers score pass, no provider call is made.
- **HQ-3 — baseline head.** Run the bar against the shipped default. PASS: a
  per-class rate is printed and recorded; the operator can read the verdict
  without interpreting raw output.
- **HQ-4 — a second head.** Set `intent.direct_answer_model_profile` to a
  different local profile and rerun. PASS: the recorded evidence shows the
  *different* resolved model and endpoint digest, proving the run followed the
  setting rather than the default.
- **HQ-5 — evidence and docs.** Inspect the recorded rows and read the operator
  page as written. PASS: no prompt or answer text appears in the store, and the
  page tells an operator how to run the bar and what a rate does and does not
  mean.

## Explicitly Out Of Scope Here

Changing the shipped default head, any runtime rule enforcement, and any
model-judges-model evaluation. See `docs/plans/v1.3.1-plan.md`.
