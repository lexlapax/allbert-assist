## §A — The Fan-Out Lifecycle (frame → deliver → acknowledge → run → join)

```
user prompt (Runtime caller declaring exact `fanout_delivery_ack_v1` capability)
  │
  ▼
Runtime.submit_user_input  ──────────────  synchronous, unchanged entry
  │
  ├─ capability absent/malformed/unsupported ──▶ single-turn pipeline
  │      (no decomposition and no durable fan-out framing)
  │
  ▼
IntentAgent turn (settings-pinned)
  │
  ├─ Stage-0 Decomposer (S3)         :single ──▶ today's pipeline, unchanged
  │      broad automatic eligibility: ≥2 independent tasks; explicit
  │      parallel language not required; uncertain/nested ⇒ :single
  │      count > max_children_per_fanout ⇒ clarify before framing; no task loss
  │      │ :fanout (task list, advisory)
  │      ▼
  ├─ Objectives.Fanout.frame/2       parent + N children (durable, one txn,
  │                                  origin attribution copied to children)
  │      │
  │      ▼
  └─ response = KICKOFF ACK + opaque start receipt
         │   children remain durable open; NOTHING executes yet
         ▼
caller delivers/records kickoff
  ├─ remote chat: transport success      ├─ HTTP non-streaming: durable record
  ├─ SSE: kickoff event flushed
  ├─ Web: exact browser marker mounted   ├─ TUI: every line written
  ├─ CLI: output completed               └─ Jobs: durable kickoff event
         │
         ├─ reported delivery/print failure ──▶ `blocked`; retry or cancel
         ├─ absent/stale/forged Web mount ACK ──▶ `pending`; children stay open
         ▼
Runtime acknowledges receipt (single-use, identity-bound, idempotent,
non-authoritative) ──▶ queue runnable ──▶ Coordinator starts
  (confirm_before_start=true adds its durable confirmation before start)
         │
         ▼
caller is free; duplicate acknowledgement cannot start work twice

background (per child, in parallel, supervised):
  RunServer: propose ──▶ evaluate ──▶ authorize ──▶ Actions.Runner.run/3
     ▲                │            (cancel-token checkpoints between operations)
     │                ▼
     │        observe/advance ──▶ next step … until terminal
     │                │
     │                ├─ needs_confirmation ──▶ park (step blocked +
     │                │                          confirmation_id); siblings
     │                │                          unaffected; notify kind
     │                │                          :confirmation_request (§E)
     │                └─ run.* signals on the SignalBus (status stream)
     ▼
  Objectives/Fanout terminal transition (one database transaction):
     child terminal + child event ──▶ durable sibling reduction
     │  … this commit makes all children terminal
     ▼
  JOIN in the SAME transaction: parent terminal + one join event +
     pending report receipt/outbox
     │
     ├─ Coordinator: capacity/process cleanup + low-latency joined signal
     └─ Scheduler/boot reconciliation: idempotent historical repair
     │
     ├─ attached web/TUI ──▶ render/print exact report ──▶ ACK that receipt
     ├─ remote autonomous notify ON ──▶ Channels.Notify ──▶ transport
     └─ detached/default-OFF ──▶ keep pending ──▶ exact next-turn report + ACK
```

The three presentation branches consume the same parent projection. Attached
web/TUI delivery is attended session output, not ADR 0084 authority. Kickoff
acknowledgement occurs only after the Web browser mounts the exact runtime
delivery marker or TUI stdout writes every kickoff line. An absent, stale, or
forged Web marker leaves kickoff `pending`; a returned TUI write error,
exception, exit, or partial output records it `blocked`. Both leave the children
open. Report acknowledgement likewise occurs only after
the browser mounts the report marker or stdout writes the complete response.
Failed/partial output does not consume either receipt.
Several pending fan-outs may be rendered independently; an ACK names one exact
report receipt and cannot consume another. Remote delivery reserves its unique
ledger key before transport and acknowledges the parent only after a definitive
delivery receipt. Default-OFF never means discard: the report remains pending
for exact next-turn retrieval.

**Attached Web continuity (M12.21).** For a joined parent whose exact origin is
the current owned Web thread, the attached path first invokes a registered
internal `conversation_write` action. That action re-proves ownership, joined
truth, origin, and report identity, then ensures one canonical assistant
message keyed to the parent. The LiveView refreshes the ordinary conversation
timeline and renders the exact hidden report marker beside that canonical
message. Browser mount acknowledges the receipt; persistence alone never does.

If the browser disconnects after persistence but before mount acknowledgement,
connected remount reconciliation ensures the same message and re-emits the same
marker. A duplicate joined signal or ACK retry cannot create another message.
If persistence, render, or acknowledgement fails, the report stays pending and
remains eligible for this attached retry or the normal next-turn path. Once
delivered, the canonical report remains visible through later turns and
remounts. The kickoff card says fan-out started/running while children are
active, the objective summary says `N active`, and child cards link to their
owned detail views with safe bounded result previews. None of these Web
presentation rules changes fan-out authority or remote autonomous delivery.

OpenAI-compatible/ACP presentation (Locked Decisions 17/26/29; clarified
2026-07-19 and 2026-07-22): the request HOLDS until join. For non-streaming
requests, durable server-side kickoff recording satisfies the start
precondition; for SSE, successful kickoff-event flush does. Children then
run, and the HTTP response completes with the join report, bounded
by the request timeout (timeout ⇒ kickoff returns; the report remains behind
its delivery receipt in `pending_reports`); SSE clients stream status chunks then the report.
Disconnect-before-record/flush never starts work; disconnect after durable
recording retains the report for restart-safe `pending_reports` retrieval.
The controller/server awaits through the additive fan-out continuation API,
outside `Runtime.submit_user_input/1`. OpenAI SSE is genuinely chunked:
kickoff flush → start acknowledgement → status chunks → join → `[DONE]`.
ACP prompt work runs concurrently with the stdio reader, so `session/cancel`
remains serviceable and routes to the active run. Timeout returns the kickoff;
the report remains pending until its report-delivery receipt is acknowledged.
No existing request field or terminal response shape is removed.

Status streaming while running: `run.progress` signals fan to (a) the web
workspace via the existing SignalBridge objective-event path, (b) an attached
TUI session registered ephemerally in `Channels.TUI.Subscriptions` and rendered
through its live region (no PID/function is durable), (c) remote channels ONLY through `Channels.Notify`
when `level = "status_and_completion"` (coalesced, throttled; on channels
declaring `status_update_mode: :edit_in_place` the one status message is
edited in place, with append fallback — S7b/M7).

Rules (ADR 0083 / plan Locked Decision 5): `restart: :temporary` everywhere in
the run scope (restart is a COORDINATOR decision from durable state, not a
supervisor reflex); monitors not polling; Registry-addressed steering; no bare
`Task.async` for steerable work; OS processes spawned by steps are captured as
os_pid/process groups (ADR 0085) — supervision is never a security boundary.
Delivery state/receipt digest, queue position, run-attempt count, review
reason, and join outcome are durable. Coordinator memory and lifecycle signals
are rebuildable projections and own no private goal-loop or join truth. Every
fan-out terminal writer uses the same transaction boundary; whichever child
terminalizes last closes the parent. Coordinator initialization reconciles the
parent before scheduling children, and live/boot recovery select every
acknowledged `not_ready` parent, including all-terminal historical rows.
Scheduler reconstructs a global run slot only for a Registry-proved live
RunServer and installs its own monitor before Coordinator recovery. If that
process exits or disappears during rehydration, the monitor releases the slot;
stale reconstructed capacity cannot block later fan-outs. The
interactive Engine's generic continue/cancel commands either delegate a fan-out
child transition to this boundary or reject the incompatible path; they cannot
silently terminalize a fan-out row. Parent cancellation is reduced from stable
child outcomes rather than racing them with an independent parent terminal
write.
RunServer executes the full child lifecycle; a task title is never treated as
an already-authorized executable step. It calls `Objectives.Lifecycle`, whose
transactional/CAS operations own transitions, events, attempt policy,
Registry/Runner invocation, confirmation parking, observation, and advance;
private Engine Jido command modules are not its execution API.

never edits — and an edit counts as a delivery for the min-interval

## §E — Steering Flows

**Classification (advisory, S5).** Mid-flight input on a thread with an
active fan-out extends the existing `:continue_objective` seam:

```
inbound text ──▶ engine candidates (fan-out parent/children present)
  ├─ no fan-out candidate wins ──▶ normal pipeline (new request)
  └─ fan-out candidate wins ──▶ Intent.Steering.classify
        ├─ :status      ──▶ aggregate every active fan-out in thread/session
        ├─ :steer/:adjust ─▶ steer_objective_run action ──▶ directive event
        │                     (durable) ──▶ Registry send to RunServer ──▶
        │                     applied at next lifecycle-operation boundary,
        │                     never during an effect
        ├─ :cancel      ──▶ cancel_objective_run (child ref or whole fan-out)
        │                     ──▶ tiers: cooperative → supervised → OS kill
        ├─ :new_request ──▶ normal pipeline (decomposer may run)
        └─ low confidence ─▶ clarify turn (list children, ask which/what)
```

Invariants (gate-bound): the classifier is advisory; free text NEVER approves
a pending confirmation (approval stays on `ALLBERT:APPROVE`/buttons through
`ConfirmationCallback`); steering can raise but never lower a confirmation
class; an identity-unmapped sender cannot steer at all (inbound trust
unchanged); steering another user's objective is denied at the action.
Mutating steering resolves an explicit child/fan-out reference. If multiple
targets remain plausible, Allbert clarifies; it never silently chooses the
newest run. In particular, an ordinal such as `cancel task 1` is parent-local:
with two active fan-outs it is ambiguous until the operator names the parent
(id or title) or a specific child. Read-only `status` may aggregate both.

`adjust` refines how an existing child pursues its goal (for example, shorten
the answer or add citations); `steer` redirects the goal. They remain distinct
for acknowledgement, audit wording, clarification, and accuracy metrics, but
both use `steer_objective_run` with identical ownership, authority, and
confirmation posture. Mentioning two ordinal targets is ambiguous and produces
a clarification rather than selecting the first.
Redirect/skip against a confirmation-blocked child resolves the old
confirmation as `cancelled` with reason `superseded_by_steer` and the steering
event id before replanning; the prior button/typed callback can no longer run it.
Directive recording re-reads the owned active child inside an immediate
transaction. A non-cancellation terminal writer refuses to commit over a
durable unapplied directive, and Lifecycle checks again at its final boundary.
The serialized result is therefore one of two honest outcomes: the directive
commits first and is applied before completion, or completion commits first and
the later steer returns a terminal-target result. No accepted directive is
orphaned after terminalization.

**Attended raw-TUI admission and ordering (M12.17).** The raw input driver
remains the only prompt/buffer writer, while the Adapter owns admission and
fan-out attachment state:

```
complete raw line ──▶ Adapter admits line to bounded FIFO ──▶ fresh prompt
  └─ if no ordinary turn is active ──▶ supervised attended worker
       ──▶ existing Runtime/channel pipeline ──▶ successful terminal write
       ──▶ exact kickoff attachment handoff to Adapter
       ──▶ delivery acknowledgement ──▶ worker completion ──▶ FIFO head

while worker is active:
  raw line ──▶ FIFO tail (never a concurrent ordinary Runtime turn)
  lifecycle signal ──▶ Adapter ──▶ InputDriver redraws prompt + typed buffer
  worker DOWN ──▶ visible attended failure ──▶ FIFO head
```

The FIFO holds at most 32 waiting lines; overflow is rejected visibly. `/quit`
keeps accepted-turn ordering, while driver EOF/Ctrl-C shutdown terminates the
active worker and restores terminal mode. Only raw, non-coding attended input
uses this seam: synchronous `Adapter.submit/3` and line-mode input remain
synchronous, and Pi-mode keeps its asynchronous coding-turn/correction path.
A line admitted during the short `/pi` transition is re-dispatched after the
worker's narrow coding-state handoff, so it cannot accidentally run as an
ordinary turn. Worker state never replaces newer Adapter lifecycle or
attachment state.

**Post-render report acknowledgement (M12.18, implemented).** A successful terminal write
and durable receipt consumption are intentionally two phases. Receipt
persistence cannot own the attended surface process:

```
joined durable parent ──▶ Adapter writes complete report to stdout
  ──▶ ephemeral session claim suppresses duplicate joined signals
  ──▶ unlinked supervised acknowledgement worker
       ├─ success ──▶ idempotent pending → delivered transition
       ├─ known transient DB failure ──▶ bounded backoff + retry, no reprint
       └─ exhaustion/other failure ──▶ one warning; durable state stays pending

in parallel:
  Adapter keeps prompts, lifecycle signals, and FIFO admission responsive
  attended worker failure/finish remains independent of report ACK work
```

The Runtime receipt boundary uses one shared closed classifier for known
DBConnection and SQLite busy/locked failures. Identity/receipt errors never
retry, and unknown programming failures are not mislabeled as contention.
Every caller retains delivery-before-acknowledgement; TUI alone needs the
unlinked task because its long-lived Adapter owns the terminal. If the process
or VM ends between stdout and the durable transition, the report remains
available for honest later redelivery. No new durable outbox or retry daemon is
introduced: the joined parent with `report_delivery_state=pending` remains the
source of truth. The TUI keeps at most 32 active acknowledgement workers and 32
in-session suppression claims; capacity exhaustion follows the same visible
warning plus durable-pending fallback instead of risking unbounded surface
state. Scheduler rehydration and Coordinator join recovery use the same closed
classifier for both raised exceptions and nested process exits, so receipt and
fan-in recovery cannot drift into contradictory definitions of database
contention.

**Serialized SQLite admission (M12.19).** Parallel work does not require
parallel SQLite writers. Development and packaged production use one Repo
connection, WAL, immediate write transactions, and a short bounded foreign-
contention timeout:

```text
parallel provider/run processes
  ├─ effect work outside Repo
  ├─ short durable phase ─┐
  ├─ short durable phase ─┼─▶ one ordered SQLite writer ──▶ commit
  └─ effect work outside Repo
                                             └─▶ publish signals after commit

inbound provider event (deduped)
  ──▶ one immediate admission transaction
       ├─ canonical user message + thread timestamp
       ├─ channel-thread binding
       └─ provider-message reference
       ├─ commit ──▶ Runtime routing/steering
       └─ rollback ──▶ definitive failed event + concise retry message
```

The admission transaction uses stable ids, so retry cannot create a second
message or reference. It never contains model/action/provider work. A known
database exception becomes a typed bounded error; an unknown programming fault
remains visible to supervision/logging but the TUI never renders its exception,
stack, SQL, or paths. The existing channel event remains the provider dedupe
boundary and never stores raw prompt text. Test Sandbox pool sizing is an
isolation implementation, not the operator persistence topology; a separate
non-Sandbox regression proves the one-writer configuration.

Prompt visibility alone is not responsiveness. The raw TUI regression records
prompt display, byte/complete-line acceptance, next-prompt display, and Runtime
start/result separately while fan-out lifecycle output is active. Output may
interleave with editing, but it must not make the terminal appear usable and
then freeze editing or admission for five to ten seconds. If serialized
persistence does not remove that symptom, InputDriver, Adapter mailbox/output,
BEAM scheduler load, and provider handoff are profiled and corrected before the
focused flagship walkthrough reopens.

The implemented M12.19 correction found that repeated `run.progress` signals
were each queued through the TUI Adapter, performed a durable ownership read,
and synchronously redrew the prompt before a completed input line could reach
Runtime. TUI therefore admits only the first progress display per child run
attempt, resets that display claim on steer/resume/block, and keeps at most 128
claims. It does not suppress start, steer, block, terminal, join, or report
output. A 25-event raw-terminal burst produces one progress redraw and a fresh
prompt within 200 ms of line admission while FIFO Runtime execution remains
ordered. This is an operator-responsiveness rule, not a debug-log setting;
`ALLBERT_TUI_LOG_LEVEL=none` continues to affect Logger output only.

**Fail-closed missing-run recovery (M12.20).** A durable `running` child with no
live RunServer is never enough authority to execute. Coordinator first derives
the same retry-safety/attempt disposition used at boot:

```text
worker absent + durable child running
  ├─ safe and attempts <= 1 ───────────────▶ one supervised retry
  ├─ safe and attempts > 1 ── persist failed/retry_exhausted
  └─ unsafe or unknown ────── persist blocked/uncertain_effect
                                  │
                                  ├─ commit ──▶ reconcile parent; never rerun
                                  └─ DB transient ──▶ retry this write; never rerun
```

An unapplied steering directive is retained and applied before recovery settles,
but it does not make a possibly-effectful prior attempt safe. The operator sees
the steered title in review-blocked state and can explicitly decide what happens
next. Permanent transition faults stay visible to supervision/logging without
turning into an execution grant. Successful starts clear both worker-start and
pre-effect retry history.

The operator persistence contract is one live Allbert runtime per Allbert Home.
Use daemon attach for commands against a served Home, or assign a different
`ALLBERT_HOME` to a second standalone runtime. M12.20 adds a disposable-Home,
non-Sandbox production-profile gate over real Allbert persistence/fan-in code;
it does not add another manual validation harness.

**Background-raised confirmations, out-of-band.** A run hitting
`needs_confirmation` parks its step (`confirmation_id`) and emits
`run.blocked`:

```
run.blocked ──▶ Channels.Notify kind=:confirmation_request
  ├─ notify ON  ──▶ origin channel gets the request rendered with its
  │                 approval primitives (buttons / ALLBERT:APPROVE:<id>)
  └─ notify OFF ──▶ visible in web/TUI approval surfaces (as today) and
                    surfaced with pending_reports on the next turn
user approves (any surface, existing ConfirmationCallback path, identity
re-proved) ──▶ confirmation resolves ──▶ Scheduler resumes the child through
RunServer/Objectives.Lifecycle (never the generic interactive Engine path);
siblings were never blocked
```

Objective/step/action provenance is copied only when the trusted Runner context
actually supplies it. A direct confirmation-gated action outside an objective
run keeps its declared target; an absent `selected_action_module` is not a
module value. When provenance is present, conflicting objective, step, action,
or module values still fail closed before the confirmation is created.
Every newly built record carries `objective_binding_version: 2` and one
internally stamped kind. `ordinary` means there is no complete objective/step
pair and approval does not probe Objectives. `objective` means a complete pair
has no fan-out parent marker; approval durably verifies that the row is not a
fan-out child before taking the generic resume path. `fanout_child` can be
created only from complete trusted user/child/step/parent context, and approval
requires the stored action and owner to match the durable step, child, and
parent before Scheduler is woken. Parent-present incomplete context is rejected
before a prompt is written. The short-lived local version-1 transition shape
remains readable and keeps its complete-pair classification. An unversioned
record written by pushed candidate `107a5ce2` that still carries complete
objective/step/origin provenance uses exact durable classification first. An
older unversioned record without complete provenance may use the legacy
`Step.confirmation_id` lookup only when exactly one step owns it. An unmarked
record with no linked Step is ordinary; partial or stale provenance and
duplicate links deny approval and leave the confirmation pending.

A target-policy recheck that is now denied follows the same classification
before the confirmation is resolved. For a valid parked fan-out child, the
denial is persisted and Scheduler is woken so Lifecycle cancels that child and
reduces the parent without executing the target. A tampered, stale, or
ambiguous record stays pending and cannot wake another run. The operator can
deny that record and retry the task rather than risk resuming the wrong child.
Only the unversioned compatibility paths intentionally query Steps for a record
without current binding metadata.

## §F — Failure, Crash, and Rehydration Flows

- **Run crash:** RunServer dies → Coordinator `:DOWN` → crash event and
  attempt count recorded. ONE restart is allowed only for a step whose action
  contract proves retry safety/idempotency. A possibly committed external
  effect without a durable observation becomes
  `blocked`/`uncertain_effect`; explicit retry or skip is required. A second
  crash → child `failed`.
- **Pre-worker admission failure:** if `DynamicSupervisor.start_child/2` fails
  before a RunServer exists, the Coordinator releases the scheduler grant and
  requeues the still-open child with capped exponential backoff. No run attempt
  or uncertain-effect state is recorded because no lifecycle or effect began;
  siblings continue independently.
- **Coordinator crash:** children keep running (they are supervisor siblings,
  not linked). Their terminal transactions can close the parent without the
  Coordinator. Scheduler observes `:DOWN`, restarts the temporary Coordinator
  for every acknowledged `not_ready` parent, and reconstruction first runs
  idempotent parent reconciliation before re-establishing monitors or scheduling
  work. Repeated abnormal exits retain capped exponential recovery backoff until
  a live Coordinator reports a successful reconciliation; programming errors
  remain visible in the crash report. All-terminal/open historical rows are
  repairable; active children are not a recovery prerequisite.
- **Coordinator reconciliation result:** `joined_now`/`already_joined` stops
  normally. Permanent durable-parent absence frees capacity and retires without
  another retry. Only known transient `DBConnection` ownership/connection or
  SQLite busy/locked failures receive bounded redacted retry; schema/query and
  other programming faults crash visibly for OTP recovery. During a transient
  database interruption the operator may briefly see `finalizing`/`recovering`;
  a rolled-back parent cannot leave phantom progress messages or a hidden
  Coordinator.
- **Scheduler crash:** its supervisor restarts it permanently; it rebuilds
  active fan-outs and fair-queue membership from Objectives and Registry
  without changing durable FIFO order. Boot recovery reads the full durable
  parent/child snapshot before installing any process monitors, so a transient
  mid-snapshot failure retries without duplicate monitors. Live recovery and
  boot rehydration contain database unavailability inside Scheduler rather than
  restart-storming the top supervisor or taking Settings/channels down with it.
- **BEAM restart mid-fan-out:** boot rehydration uses the same acknowledged-
  `not_ready` predicate as live recovery. It repairs an all-terminal/open parent
  or starts a Coordinator for remaining work; runs then resume from the last
  durable step inside the window. Outside the window, stale fan-out children
  enter abandonment through the same terminal-transition boundary, so the last
  abandonment can close the parent and the report says so.
- **Backpressure:** Scheduler grants at most
  `max_concurrent_runs_global`, round-robin across fan-outs; each fan-out uses
  at most `max_concurrent_runs_per_fanout`. Extra children stay durable `open`;
  `max_children_per_fanout` only limits framing. FIFO positions are persisted,
  so restart reconstructs the same order. Status shows queued positions; a
  cancelled child never starts.
- **Control-query bounds:** human-facing list/show commands retain their
  explicit display limits. Correctness paths do not reuse those truncated
  lists: steering candidate discovery and ACP session cancellation query all
  active rows within the exact user/thread/session/fan-out scope. A fan-out
  cannot become unsteerable or uncancellable merely because more than 20/65/75
  newer objectives exist. Durable recovery/outbox scans likewise use their
  indexed state predicates rather than recent-history limits.
- **Notify failure:** adapter delivery error → `notify.failed` + audit; one
  bounded retry after the min-interval; then suppressed with reason (report
  still reaches the user via next-turn fallback — delivery failure never
  loses the report).
- **Notify disabled/completion-only:** status eligibility is coalesced before a
  per-progress delivery reservation, while `Channels.Notify` remains the final
  send-time authority. OFF/completion-only produces zero status transport calls
  and bounded suppression evidence rather than one SQLite write per internal
  progress event. The joined parent remains the durable completion outbox.
- **Joined-signal loss / consumer or SignalBus restart:** the signal is a
  low-latency wakeup, not completion storage. NotifyConsumer monitors bus
  ownership, re-subscribes after a bus-only restart, and reconciles durable
  pending parent reports after init/re-subscription. A `reserved` completion can
  resume because transport did not begin; interrupted `sending` becomes
  `uncertain` without autonomous retry; `delivered` plus a pending parent is
  acknowledged idempotently; definitive `failed` work receives only the bounded
  retry. The unique delivery key prevents duplicate transport and default-OFF
  reports remain pending for the next turn.
- **Uncertain notify:** provider acceptance with no persisted receipt →
  ledger state `uncertain`; no autonomous retry; status/next-turn retrieval
  retains the report and the markdown audit records the warning.
- **Delivery-ack uncertainty:** until Web returns the exact browser-mounted
  handle, kickoff remains `pending`. A definitive TUI returned error, exception,
  exit, or partial output records `blocked`. In either state children remain
  open; operator status/retry re-renders the same kickoff and receipt before
  acknowledging it.
- **Pending-report delivery uncertainty:** reading does not consume a report.
  Failed/uncertain transport retains the same report receipt; only successful
  transport/render/print or durable public-protocol recording acknowledges it.
- **Turn-timeout interplay:** interactive-channel Runtime work only frames +
  returns the kickoff (well under the 120s default); child runs are not bound
  by that turn deadline. OpenAI/ACP await separately through the continuation
  API and apply their public-request timeout without cancelling the fan-out.
- **Join outcome:** all completed → `completed/success`; any completed plus
  failed or cancelled → `completed/partial`; no completed and any failed →
  `failed/failed`; all cancelled → `cancelled/cancelled`. Reports enumerate
  every child.

## §G — Data Flow And Authority Invariants

- Durable truth: Objectives rows/steps/events (SQLite). A fan-out child's
  terminal row/event and the last-child parent join/report-outbox transition are
  one transaction. Process state is a rebuildable projection (ADR 0083);
  signals are notifications, not storage.
- Terminal invariants: terminal children never reopen or gain an attempt; no
  parent finalizes with a non-terminal child; a committed terminal transition
  cannot leave all children terminal and the parent `not_ready`; parent outcome
  equals child reduction; and one parent has one join event/report receipt.
- Kickoff receipts are opaque, identity-bound, single-use continuation
  handles, not authority. Acknowledgement only makes framed children runnable;
  it never grants an action, approves confirmation, or weakens policy.
- Report receipts are likewise identity-bound delivery handles. Reading a
  report is non-destructive; acknowledgement after successful delivery is the
  only consumption transition.
- Notify operational state lives in the additive delivery ledger; the parent's
  pending report is the completion outbox from which eligible delivery work is
  reconstructed. Redacted append-only evidence lives under Allbert Home through
  `Runtime.Audit :channel_notify`. Neither grants authority.
- New authority surface: EXACTLY ONE — autonomous notify (ADR 0084),
  settings-gated per channel, default OFF, enforced at `Channels.Notify`,
  audited, redacted. Kickoff acks and next-turn reports are turn responses,
  not autonomous sends. Attached web/TUI push rendering is outside the class.
- Not authority: decomposition output, fan-out/run/objective/step ids,
  steering directives, supervised processes, signals. Every effectful step
  goes through registered actions with unchanged confirmation classes
  (`Actions.Registry` + `Runner.run/3`).
- `send_channel_message` (ADR 0063) keeps `confirmation: :required` —
  operator-initiated compose and autonomous notify are different classes on
  the same `deliver_outbound/3` transport.
- Fan-out framing persists the exact origin thread-ref id/digest,
  receiver-account ref, channel, and local user. Notify loads that exact ref
  and re-proves its current identity mapping at send time; missing,
  conflicting, cross-account, or cross-user refs are suppressed. Stored text
  never becomes an address. The stable digest covers exactly channel,
  receiver-account ref, and provider-thread key. Mutable provider metadata or
  display/reference fields may refresh without invalidating the origin, but
  changing the account or provider-thread key changes the digest and fails
  closed. Authorization is repeated immediately before every transport call;
  framing-time consent or an earlier reservation is not sufficient.
- Cancellation kills only processes the run spawned (os_pid/process-group
  captured at spawn, ADR 0085); OTP supervision is not a security boundary.
  Each ProcessOwner pins `execution.cancel.grace_ms` from Settings Central at
  spawn; an explicit bounded internal proof/test override wins for that spawn.
