## §A — First-Run Data Flow (detect → enable → disclose)

```
boot (web mount | allbert tui | mix allbert.tui | bare allbert | allbert ask)
  │            (after ensure_http_started + fresh-process settings read)
  ▼
FirstRun.detect_details/1  ──────────  existing probe chain, cached, read-only
  ├─ configured local endpoint ── ModelDoctor.diagnose (loopback/configured only)
  ├─ localhost Ollama ─────────── binary / /api/version / curated tag in /api/tags
  └─ hosted key presence ──────── env/vault presence check, NO egress
  │
  ▼
Enablement engine (S1)                       consent key stored?
  ├─ stored false ───────────────────────▶ :sticky_disabled (never overridden)
  ├─ stored true ────────────────────────▶ already enabled; no writes
  └─ ABSENT + first usable hit in strict order:
        configured-local → localhost → hosted-key
        │
        ▼
     StoreLock-owned raw-presence compare-and-write
     (absent != schema-default false; explicit false is sticky)
     M1a selector: doctor-healthy configured local → exact curated pulled tag
                   → configured-unverified hosted profile
     (arbitrary pulled tags wait for M4 catalog/profile ownership)
     + audited safe-write pair (direct_answer + model_assist)
     + model_preferences.primary when unset
     + provenance audit row {enabled_by: detection, profile, local|hosted}
        │
        ▼
     durable pending disclosure marker (per surface, Home marker)
        │
        ▼
     surface renders disclosure FROM the provenance row:
       web chat preface | TUI banner | CLI first-run paragraph
       hosted transport waits for rendered acknowledgement
       (provider + egress fact BEFORE first send, including allbert ask)
       web  = exact mounted LiveView delivery handle; absent/stale/forged
              leaves it pending and transport inadmissible; reconnect
              re-renders and re-acknowledges (v1.1 delivery-ack precedent)
       TUI/CLI = successful write to the output stream, tty or not
              (a redirected `allbert ask "x" > out.txt` is acknowledged
               when the write succeeds)
  │
  ▼
no hit ──▶ detect-state matrix (§D): chat still opens, deterministic
           fallback answers, exactly one repair CTA (pull / install / BYOK)
```

The explicit local-TUI admission spine is independent of model detection; no
detect-state outcome enters or authorizes it:

```
packaged allbert tui | development mix allbert.tui
  │
  ▼
AppBootstrap ready ──▶ resolve effective child profile (child opts win)
  │
  ▼
Settings.Store.prepare_local_tui_launch/1 (one StoreLock + one snapshot)
  ├─ raw channels.tui.enabled == false ──▶ STOP before Adapter
  │      no writes; print package/source re-enable guidance
  └─ otherwise, one validated raw-absent-subset write
         ├─ channels.tui.enabled absent ──▶ persist true
         ├─ identity_map raw-present ─────▶ preserve exactly
         ├─ effective profile != default ─▶ never invent identity
         └─ default + identity_map absent ─▶ persist ordinary list-shaped
                                             default → local entry
                       │
                       ▼
             Adapter starts only after preparation, snapshots Settings, and
             every normal/slash turn still resolves through
             Channels.Identity.resolve/3
```

M1b implementation note: the six-state probe classifier remains intact;
`FirstRun.Enablement` supplies the second (hosted-presence) axis and owns the
twelve-cell projection. A non-test boot Task runs this after Settings
supervision in a fresh process. Direct-answer resolution honors a raw-explicit
primary before legacy task defaults, so a detection-selected hosted profile
cannot be shadowed by default `local`; an absent/default primary retains the
pre-v1.2 ordering.

M2 implementation note: the disclosure obligation is persisted before the
atomic enablement write, a conservative ordering that prevents hosted
transport from becoming admissible without durable disclosure state. CLI and
TUI consume the marker only after a successful output write. Web consumes it
only after an exact mounted-handle acknowledgement; reconnects and failed,
missing, stale, or forged acknowledgements leave transport blocked. Readiness
guidance extends the existing TUI banner rather than adding a new output event,
preserving the frozen channel event shape.

M9 corrective note (LD26): FV-01 proved that guard inversion and model
enablement did not establish TUI identity admission. Packaged `allbert tui` and
development `mix allbert.tui` share the independent local-interactive
preparation shown above. A fresh default-profile launch atomically persists
raw-absent activation and identity defaults. Raw-present empty, custom, or
disabled maps remain authoritative; an effective custom child profile receives
no invented identity; and raw-explicit channel `false` blocks before Adapter
startup with re-enable guidance. Generic adapter/supervisor startup never enters
this spine. Concurrent launch converges on one audited transaction, and an
unmapped/disabled ordinary turn renders a bounded rejection while retaining its
rejected event and zero-runtime-call behavior.

M3 implementation note: direct step entry is separate from rewind. Entry keeps
completion and completed-step history intact, while rewind remains an explicit
progress edit. A ready model path is sufficient for wizard completion even when
direct answers carry a sticky explicit `false`; that decline is preserved and
gets one durable, connected-render re-enable offer. Consuming the offer never
enables anything—the operator must invoke the audited Settings Central action.

Invariants: detection performs no hosted egress, installs nothing, and pulls
nothing; its only writes are the audited model-enable pair + primary profile.
The separate local-TUI-launcher exception has the closed write set
`channels.tui.enabled=true` plus, for the built-in effective profile only, the
ordinary `default → local` identity map. It writes one validated raw-absent
subset before Adapter startup and honors an explicit channel disable as a
pre-Adapter stop. Double boot, wizard re-run, persona apply, and TUI restart are
idempotent against their durable state.

## §B — Turn-Time Resolution And Fallback Data Flow

```
user turn ──▶ Runtime.submit_user_input ──▶ intent ──▶ direct_answer
                                                        │
                                                        ▼
                              Settings.Models: ranked candidates for the task
                              (explicit selection first; otherwise local-first)
                                                        │
                                     resolved primary profile ──▶ ReqLLM call
                                                        │
                                          provider failure?
                                                        │
        models.fallback.enabled=false (DEFAULT) ──▶ honest static fallback text
                                                        │
        enabled=true:
          classify failure ── definitive ──▶ advance chain (≤ max_failovers_per_turn)
                            ── ambiguous ──▶ advance at most once
                            ── possible partial answer ──▶ NEVER silently retried
          next candidate crosses local→hosted?
                            ── allow_local_to_hosted=false ──▶ STOP, honest text
                            ── =true ──▶ proceed; reply metadata names answerer
          every failover ──▶ trace record + audit row {failed, class, answered}
          whole chain failed ──▶ deterministic text naming the failed chain
```

Image/voice keep their existing `candidates_for/2` behavior unchanged.

## §D.0 — Detect-State Derivation (binding)

`FirstRun.first_model_state/1` returns six values today
(`cli/first_run.ex:42-49`); v1.2 adds no seventh. The enablement states below
are a presentation projection of those six plus hosted-key presence.
`classify_model_probe/3` (`:151-158`) currently consults BYOK on exactly one
branch (`:missing`) — M1b changes the three cells marked ★ per LD24 so an
unusable local rung never masks a configured hosted rung.

| `model_state` | hosted key absent | hosted key present |
|---|---|---|
| `local_ready` | `:auto_enabled` (local) | `:auto_enabled` (local — local always wins) |
| `byok_ready` | — (unreachable) | `:auto_enabled` (hosted) |
| `runtime_missing` | `:nothing_detected` | `:auto_enabled` (hosted) |
| `model_missing` | `:needs_model` | ★ `:auto_enabled` (hosted); local pull is secondary |
| `runtime_unhealthy` | `:needs_model` (repair CTA) | ★ `:auto_enabled` (hosted); local repair is secondary |
| `below_hardware_floor` | `:below_floor` | ★ `:auto_enabled` (hosted) — local can never work here |

A stored consent `false` short-circuits every cell to `:sticky_disabled`.
`:enabled_unavailable` is not derived from detection: it is the state of a
Home whose consent key is already `true` while the current cell is
non-`:auto_enabled` — the Ollama-disappeared case. It renders the honest
unavailable text plus the repair CTA of its underlying cell, and never
re-shows the disclosure.

All twelve cells plus `:sticky_disabled` and `:enabled_unavailable` carry an
M1b regression and appear in the M6 integrated matrix.

## §D — Detect-State × Surface Matrix

| Detect state | Web workspace | TUI (packaged AND dev) | CLI (`allbert` / `ask`) |
|---|---|---|---|
| `detected_ready` (local) | chat answers; one-time disclosure preface | starts; banner disclosure; chat answers | answers; disclosure paragraph once |
| `detected_ready` (hosted key) | as above + provider/egress named before first send | as above | as above |
| `sticky_disabled` (operator-stored false) | deterministic fallback; no CTA nagging; settings hint | starts; fallback; hint | fallback + hint |
| `detected_needs_model` (no hosted key) | chat open, fallback; ONE CTA: one-click curated pull (live progress) | starts; fallback; pull guidance | fallback + pull command |
| `runtime_unhealthy` (no hosted key) | chat open, fallback; ONE CTA: restart/repair the local runtime | starts; fallback; repair guidance | fallback + repair command |
| unusable local + hosted key | answers via hosted; disclosure names provider + egress; local repair is secondary | starts; banner disclosure; answers | answers; disclosure paragraph once |
| `nothing_detected` | chat open, fallback; ONE CTA: guided install / BYOK | starts; fallback; install/BYOK guidance | fallback + repair suffixes |
| `below_floor` (no key) | chat open, fallback; BYOK-first guidance | starts; BYOK guidance | fallback + BYOK guidance |
| `below_floor` + hosted key | answers via hosted; disclosure names provider + egress | starts; banner disclosure; answers | answers; disclosure paragraph once |
| `enabled_unavailable` | chat open; honest unavailable text; repair CTA of the underlying cell; no repeated disclosure | starts; same | same |

Rules: the TUI starts for every model/readiness state (guard inverted;
dev/packaged parity); the sole channel-level stop is a raw-explicit operator
`channels.tui.enabled=false`, reported before Adapter startup with a re-enable
command. Optional onboarding neither requires nor creates that shutdown. On a
fresh default-profile Home the explicit local launcher atomically
persists activation plus `default → local`. A raw-present empty/custom/disabled
map stays authoritative and may produce the visible identity rejection instead
of a model turn; an effective custom child profile never receives the default
map. Generic Adapter startup never seeds. Web independently resolves
`web-local → local`, so both surfaces own the same canonical user's data
without the TUI mapping granting web authentication or auto-opening the same
thread;
auto-open of the onboarding canvas happens only for repair states and never
gates the chat; exactly one primary CTA per state; `onboarding_complete`
gates nothing in this table.

## §E — State And Key Inventory

- **Settings (existing, consumed):** `intent.direct_answer_model_enabled`,
  `intent.model_assist_enabled`, `model_preferences.*`, `model_profiles.*`,
  `providers.*`, `first_model.curated_model`, `first_model.curated_floor_gb`,
  `channels.tui.enabled`, `channels.tui.profile`, and
  `channels.tui.identity_map`.
- **Settings (new, additive):** `models.fallback.enabled` (false),
  `models.fallback.allow_local_to_hosted` (false),
  `models.fallback.max_failovers_per_turn` (1, bounded 1..2),
  `models.catalog.version` (1, read-only).
- **Home marker (`onboarding.json`):** wizard progress, applied persona,
  new disclosure state per surface (`pending | acknowledged`). Never gates
  local availability; hosted inference admission requires acknowledged
  disclosure and fails closed across a crash. Per-surface keys are updated
  read-modify-write through the existing atomic marker path
  (`cli/first_run.ex:301-310`); that path gives write-atomicity, not
  compare-and-swap, so a lost update under concurrent first boot of two
  surfaces may only REPEAT a disclosure, never suppress one.
- **Audit:** enablement provenance rows; fallback event rows under
  `settings/audit/model_fallback/YYYY-MM.md`; both
  redacted, no key material or raw endpoints. Enablement emits existing
  per-key setting audit rows plus one transaction provenance envelope naming
  applied and preserved keys. A fresh default-profile local-TUI preparation
  adds one `channels.tui.enabled` row, one `channels.tui.identity_map` row, and
  one transaction envelope with actor `first-run-local-tui-bootstrap`; restart
  adds none. A partially preconfigured Home audits only the raw-absent applied
  subset; explicit channel disable audits nothing because the launcher writes
  nothing.
- **No non-additive migration anywhere** (operator-locked for 1.2–1.4).

## §F — Authority Invariants

- Detection and catalog assembly are read-only; the enablement engine's
  only writes are the audited safe-write pair + primary profile, and only
  when the consent key is absent. Stored `false` is sticky.
- Absence is read from the raw user-settings map and conditionally written
  under one StoreLock transaction; effective/default-merged settings are
  never used as presence evidence and callers cannot race a separate check.
  Presence is tested per key across the whole write set, so an explicitly
  stored value on any of the three keys survives detection.
- The enablement write is system-initiated and rides `Settings.Store` (which
  audits) rather than a registered action (the agent-facing boundary). It is
  not a new privileged capability: only the three named keys, only when
  raw-absent, only from the boot/detect path, proven at M1a.
- The only other system-initiated Settings write is the exact-purpose LD26
  `Settings.Store.prepare_local_tui_launch/1` transaction. Only the two explicit
  local launchers may call it, only before Adapter initialization, and its
  closed write set is `channels.tui.enabled=true` plus the full list-shaped
  `default → local` entry for a built-in effective profile. It validates and
  persists one raw-absent subset under one lock. Raw-present channel `false`
  blocks the launcher; raw-present empty/custom/disabled identity state is never
  merged or overwritten; child launch options take precedence when resolving
  the effective profile. The Adapter has no identity fallback; arbitrary
  profiles and generic startup remain denied.
- Hosted key presence is labeled configured-but-unverified. Provider choice
  follows explicit primary, task candidate order, then the stable M0 order;
  environment enumeration order is never authority or priority.
- Operator/chooser settings writes ride existing registered actions /
  `Settings.put` with audit; the closed system-initiated enablement exception
  is the preceding Store primitive. Pulls stay confirmation-gated; no validation-only or
  first-run-only privileged capability exists.
- The only new automatic egress path beyond first-run selection of an already
  configured hosted provider is opted-in hosted failover behind the double
  gate; both paths are disclosed/audited and named in their metadata.
- Security Central, the vault model, provider key custody, surface policy,
  and the action boundary (`Actions.Registry` + `Runner.run/3`) are
  unchanged.

## §H — Focused Operator Validation (FV, executed at end of implementation)

Feature-acceptance walkthroughs, not another release gate. Preconditions
(all binding, from the v1.1 churn lessons):

- **Open FV only after one uninterrupted green authoritative
  `mix allbert.test release` at the pushed candidate SHA**, with
  `release.v1` + `release.v12` green at the same SHA.
- **Disposable Home only.** Every row sets `ALLBERT_HOME` to a fresh
  `mktemp -d` location; nothing touches `~/.allbert`; no cloned state.
- Paste-executable steps; no `set -e`/`set -u`/`exit` in any snippet; PASS
  criteria inline; provider/credential failures record `BLOCKED`, never
  PASS; redact transcripts before sharing.
- Corrective loop when a row fails: fix → focused suite → tag/manifest
  inventory + docs/drift checks → `mix precommit` → commit + push → verify
  clean `HEAD == @{upstream}` → `release.v1` →
  corrected `release.v12` → uninterrupted authoritative gate → execute the
  reopened FV rows from FV-01.

Setup (once per row unless stated):

```sh
export ALLBERT_HOME="$(mktemp -d /tmp/allbert-v12-fv.XXXXXX)"
export V12_EVIDENCE="$HOME/allbert-validation/v1.2-$(git rev-parse --short HEAD)"
export EXPECTED_VERSION="1.2.0"
mkdir -p "$V12_EVIDENCE"
git rev-parse HEAD | tee "$V12_EVIDENCE/candidate-sha.txt"
git rev-parse '@{upstream}' | tee "$V12_EVIDENCE/upstream-sha.txt"
git status --porcelain=v1 | tee "$V12_EVIDENCE/candidate-tree.txt"
test "$(git rev-parse HEAD)" = "$(git rev-parse '@{upstream}')"
test ! -s "$V12_EVIDENCE/candidate-tree.txt"
```
