# Allbert v1.3.1 Answering-Head Qualification

Request flow: `docs/plans/v1.3.1-request-flow.md`
ADRs: one new ADR ships with this release — ADR 0097 (answering-head
qualification bar — binding on M1–M4). Consumes ADR 0021 (intent/objective
capability and advisory boundary, including its deliberate
no-regex/no-domain-oracle constraint), ADR 0072 (recommended model profiles per
purpose), ADR 0061/0051 (model substrate and closed capability preferences), and
ADR 0083 (parallel child fan-out) unchanged. Amends nothing.

Status: **plan drafted; BUILD MUST NOT START until v1.3.0 is tagged, published,
and its triad archived.** M0 re-verifies every Current Code State anchor at
build-start HEAD.

Source: v1.3 M9.b.8, deferred by operator decision on 2026-08-02 after attended
validation recorded two independent answering-head failures. v1.3 ships the
default head unchanged, with both limits disclosed in
`docs/operator/model-recommendations.md` and a documented opt-in seam
(`intent.direct_answer_model_profile`). This release supplies the evidence that
opt-in currently lacks.

## Why this release exists

v1.3 attended validation recorded two failures of the shipped
`direct_answer_local` head, in different families:

1. **Factual.** Asked which children an Erlang/OTP supervisor restarts under
   `rest_for_one`, it described `one_for_one`. `llama3.1:8b` and
   `mistral-small3.1:24b` are wrong the same way; `gemma4:31b` is correct.
   Parameter count did not predict accuracy.
2. **Instruction-following.** Asked to acknowledge a stated preference, it
   answered that status summaries "will be provided" starting on a date,
   violating the `:acknowledgments_are_not_commitments` rule its own catalog
   carries. Not reproducible in thirty-six trials across four conditions,
   including the exact production request path.

Neither is an orchestration defect and neither is fixable by prompt work that
can be demonstrated. What v1.3 could not answer is the question underneath both:
**is a given head good enough to be Allbert's answering head, and how would an
operator know?** Today the answer is "select a larger model and hope", which is
the gap this release closes.

The second failure also disqualifies the obvious cheap version. A corpus that
only tests facts would have passed the head on the acknowledgment row, so the
bar must cover instruction-following under the rule catalog Allbert already
ships, not just knowledge.

## Locked decisions

1. **The bar qualifies a head; it does not change a default.** This release
   ships no new default profile and no automatic head selection. Raising the
   shipped default is a separate operator decision that this release makes
   evidence-based rather than making for them.
2. **Deterministic scoring only, no model judges.** Scoring is exact-match or
   closed predicate over frozen expected values. ADR 0021's
   no-regex/no-domain-oracle constraint applies to *product* paths deciding
   product behavior; a frozen offline evaluation corpus with recorded expected
   answers is evidence, not an oracle inside the request path. No model grades
   another model's output, which is the pattern v1.3 M9.b.6 deleted.
3. **Reliability is measured, not asserted.** Because the instruction-following
   failure appeared once in thirty-seven observations, every row runs N times
   and the bar records a pass *rate* with a stated minimum, not a single
   pass/fail. A head that passes 19/20 is reported as 19/20.
4. **The corpus is frozen and content-free in evidence.** Prompts and expected
   values live in a digest-bound fixture. The metrics store records counts,
   rates, digests, and the resolved profile — never prompts or answers.
5. **No new runtime dependency.** The bar is an opt-in development gate in the
   existing `mix allbert.test` family, following `bench-v13-*` conventions. It
   is not part of any aggregate, precommit, or CI step.

### M1 — Frozen qualification corpus

`[code]` `[docs]`

One digest-bound fixture with two row classes and recorded expected values.

- **Factual rows.** Closed questions with unambiguous, checkable answers drawn
  from domains Allbert's own documentation and validation already exercise —
  OTP supervision semantics, event-sourcing replay and idempotency, SQLite
  durability. Each row records the exact discriminating fact, so scoring asks
  "does the answer state this" rather than "is the answer good".
- **Instruction-following rows.** Prompts paired with the DirectAnswer rule they
  test, scored on the rule's own criteria. The acknowledgment row from v1.3
  SV-6A.1a.ii is included verbatim, scored on `no_future_commitment`.
- Rows carry no operator data and no credentials. The fixture is validated and
  digest-checked before any provider call, matching the `v13_fanout_eval`
  loading contract.

Acceptance: fixture schema and digest validated by an owner test; every row
names the rule or fact it discriminates; no row's expected value can be
satisfied by a refusal or a restatement of the question.

### M2 — Deterministic scorer and the reliability bar

`[code]`

- Exact closed predicates per row class: factual rows check for the recorded
  discriminating fact; instruction rows check the recorded closed criterion.
- Each row runs N times against one resolved profile. The gate records per-row
  pass counts, an aggregate rate, and the exact resolved
  profile/provider/model/endpoint digests.
- One stated minimum pass rate per class, frozen in the plan before any head is
  run, so no head is qualified against a bar chosen after seeing its score.
- Fails closed on provider unavailability rather than scoring a missing answer.

Acceptance: owner tests prove scoring on fixed inputs without a provider;
per-row counts are non-null on every path including timeout; the recorded
evidence is content-free.

### M3 — Head matrix and recorded results

`[gate]` `[external]`

Run the bar against the locally available heads and record the results as
evidence: at minimum `qwen2.5:7b`, `llama3.1:8b`, `mistral-small3.1:24b`, and
`gemma4:31b`. Record refusals and empty responses as failures rather than
skipping them — `qwen3.5:27b` and `gpt-oss:20b` returned no content through the
v1.3 structured-output path and that is a qualification result.

Acceptance: one recorded row per head at a clean pushed SHA, with pass rates per
class; no head is described as qualified or unqualified except by the frozen
minimum.

### M4 — Operator surface and documentation

`[docs]`

- `docs/operator/model-recommendations.md` replaces "qualify any head you select
  on your own material" with the actual bar, how to run it, and the recorded
  results.
- The v1.3 disclosure of both failure modes stays; it becomes the worked example
  of what the bar catches.
- State plainly what the bar does not do: it does not make a head correct, it
  does not cover the operator's own domain, and passing it is a floor rather
  than a warrant.

Acceptance: an operator can run the bar against a head they are considering and
read a rate, without reading the plan.

## Explicitly out of scope

- Changing the shipped default answering head. That decision consumes this
  release's evidence; it is not part of it.
- Any model-judges-model evaluation. Deleted in v1.3 M9.b.6 for recorded
  reasons that this release does not revisit.
- Runtime enforcement of rule compliance. A deterministic future-tense check in
  the request path is a domain oracle ADR 0021 forbids.
- Fan-out, memory, search, jobs, or packaging behavior. None changes.
