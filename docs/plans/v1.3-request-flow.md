# Allbert v1.2.4 -> v1.3.0 Request Flow

Status: **implementation-ready release-train contract**. v1.2.4 packages the
license inventory/viewer and converts the TUI to a daemon-owned session before
v1.3.0 adds long-term memory and Search Central. Milestone acceptance, parallel
workstreams, serial barriers, and gate timing live in
`docs/plans/v1.3-plan.md`; this document fixes the end-to-end behavior and
failure contracts those milestones must prove.

## Release-Train Shape

```text
stable v1.2.0
  |
  +-- v1.2.4 WS-L: license catalog -> artifact finalizer -> packaged viewer
  |
  +-- v1.2.4 WS-T: Attach v1 additive session -> daemon service -> thin TUI
  |                         \
  +--------------------------+-- exact-artifact rejoin -> v1.2.4 binary
                                                   |
                                                   v
                 Conversations.Corpus + source policy + Jobs.Managed
                              /                         \
                             v                           v
                  Memory claims + proposal store     Search projection/API
                             \                           /
                              +-- privacy/eval rejoin --+
                                                   |
                                                   v
                                            v1.3.0 binary
```

License and TUI implementation may proceed independently. Their first serial
barrier is the frozen final release layout: licensing finalizes only after the
dispatcher and every other payload are present, and packaged TUI validation
uses those same finalized bytes. v1.3 implementation does not begin until the
v1.2.4 binary acceptance barrier closes. In v1.3, Memory and Search may proceed
in parallel only after Corpus, identity, consent, and managed-job ownership are
fixed and proven.

## System-Wide Invariants

1. `AllbertAssist.Conversations` is the sole canonical owner of conversation
   content and source authorization. Consumers use `Conversations.Corpus`; they
   do not read conversation tables directly.
2. Memory and Search are independent consumers. Memory never reads Search or
   FTS, Search never reads Memory, and neither grants authority.
3. Surfaces render and dispatch typed registered actions. Web, TUI, CLI, and DMs
   do not own search SQL, memory policy, confirmation state, or job loops.
4. A message role is not an identity. Only a verified mapped principal may be
   classified as the operator; assistant authorship remains distinct.
5. Projection data is disposable. Canonical conversations and Markdown claim
   streams remain authoritative.
6. Source/claim eligibility, digest, state, and authorization are rechecked when
   a proposal is reviewed, a Memory candidate enters a prompt, and a Search
   result is disclosed. A stale projection never becomes a stale disclosure.
7. Consent is consumer-, origin-, and source-class-scoped. Routine approved
   background work does not reprompt per run; expanded scope and destructive
   operations do.
8. All effects still resolve through `Actions.Registry` and execute through
   `Actions.Runner.run/3`. Security Central remains the authority boundary.
9. Every data/schema/protocol change is additive. Legacy Attach requests and
   pre-v1.3 memory files retain their existing meaning.
10. No flow below introduces a generic source adapter, event bus, projection
    framework, query DSL, scheduler, license service, or encryption subsystem.
    The one carve-out is `AllbertAssist.Projection.PromoteProtocol` (plan
    LD 62): it owns a single checkpoint/close/reopen/swap/verify sequence shared
    by the Memory and Search projections and holds no schema, verification
    predicate, generation metadata, or rebuild source. Implementing that
    sequence twice would duplicate the one protocol whose failure mode is silent
    data loss.

# Part I — v1.2.4 Foundational Binary

## A. Final-Artifact License Flow

### A1. Reviewed inputs

```text
resolved OTP release application closure
  + mix.lock / resolved Hex metadata
  + ERTS/OTP and Elixir release inputs
  + known-extra catalog
      - SQLite/Exqlite amalgamation and NIF
      - OpenSSL only where copied into the target artifact
      - Castore code and Mozilla-derived CA payload
      - IANA timezone data
      - compiled/vendored web assets
      - staged plugins and packaged helper executables
      - dispatcher/runtime scripts
  + external-runtime declarations
      - Node / Playwright / Chromium
      - TradingAgents / Python packages
        (recorded external unless their bytes are actually present)
  |
  v
one reviewed declarative catalog + narrow exceptions
```

The catalog is the maintained knowledge boundary. It identifies known shipped
components, expected artifact paths or application names, license expression,
provenance, required license text, exact source-availability metadata, target
conditions, and whether the component is bundled or external. It is not a
recursive ownership database.

The Castore CA bundle is the one approved non-permissive exception: a narrow,
file-scoped MPL-2.0 record with exact Mozilla source provenance, payload digest,
license text, and an immutable exact-source retrieval reference with digest and
conversion provenance. Absence of that source-availability path fails the
build. External publication qualification performs an unauthenticated fetch of
the immutable reference and matches the recorded source digest. The
schema-v1 catalog selects the immutable-reference route and rejects companion
mode; a later schema may add companion packaging additively. The generator and
viewer remain offline. It does not admit MPL for arbitrary dependencies.
OpenSSL 3 is recorded under Apache-2.0 only on targets where the
release workflow copies its library into the artifact. SQLite remains recorded
as public domain.

### A2. Deterministic offline generation

```text
catalog + resolved build inputs
  |
  +-- reject missing known record / missing required text / disallowed license
  +-- reject known external runtime unexpectedly found in the artifact
  +-- canonical sort, path normalization, LF line endings, no clock/host paths
  |
  v
repo review products
  +-- THIRD-PARTY-LICENSES.md       known cross-target union
  +-- deduplicated required texts  stable content-addressed set
  +-- deterministic check output  no network, Repo, daemon, or user Home
```

`mix allbert.licenses --check` regenerates in memory and fails on catalog/report
drift. It does not download license data during a gate. An unclassified arbitrary
byte can be reported as evidence, but only a missing or unexpected component at
a cataloged managed seam fails the release. The product claim is therefore
"best-effort inventory of known shipped components," not complete byte-level
attribution, a universal SBOM, or legal certification.

### A3. Final composition and per-target manifest

```text
clean stale Phoenix digest output
  -> compile/digest current web assets
  -> Mix release :assemble
  -> stage packaged plugins/helpers
  -> apply conditional macOS OpenSSL closure patch
  -> install the allbert dispatcher
  -> LICENSE FINALIZER                         LAST PAYLOAD MUTATION
       copy root LICENSE and minimal NOTICE
       copy THIRD-PARTY-LICENSES.md + required texts
       inspect final target paths and resolved release closure
       emit THIRD-PARTY-MANIFEST.json
       verify known bundled/external decisions and orphan digests
  -> read-only artifact verification
  -> archive -> pre-promotion checksum + immutable workflow staging
  -> exact-artifact license/TUI qualification
  -> protected evidence-bound promotion gate
  -> rehash same archives -> cosign -> publish
```

The target manifest records target triple, exact resolved OTP/Elixir/ERTS
versions, known component/license entries, expected paths, required-text
digests, and bundle/external disposition. It omits host paths and generation
timestamps so rebuilding identical staged content produces identical license
outputs. The manifest may differ across targets because their payloads differ.

All three native builders use the same exact-version `erlef/setup-beam` path,
pinned by immutable action SHA. The macOS artifact is requalified once after
removing floating `brew update && brew install erlang elixir` provisioning. The
OpenSSL patch remains only if post-change dependency-closure evidence shows it
is still required.

### A4. Packaged viewer

```text
allbert licenses [summary|list|show <component>|notices|--json]
  |
  +-- top-level dispatcher recognizes `licenses` before Req/application startup
  +-- locate immutable files relative to the installed release
  +-- parser reads THIRD-PARTY-MANIFEST.json and packaged text files
  +-- output is stable, bounded, and pipe-friendly
  '-- no Req/Allbert runtime boot, Repo, daemon attach, regeneration, or network
```

The viewer is part of every binary, including a machine with no source checkout
or Elixir toolchain. Missing/corrupt packaged metadata returns a stable non-zero
diagnostic naming the artifact defect; it never falls back to workstation
dependency metadata or the network.

### A5. Exact-artifact reconciliation

Each native target is built once. The resulting finalized archive is the input
to license-viewer smoke, packaged TUI smoke, checksum/signature publication, and
install-path validation. The product-tag workflow stages versioned archives and
their pre-promotion checksums with `retention-days: 30`, then ends without
signing or publication only after its downstream no-build license/TUI
qualification jobs upload attempt-qualified digest-bound evidence artifacts in
that same source run. Every manifest binds repository, exact workflow file/id,
`event: push`, product tag/ref and source SHA, source run ID/attempt, immutable
artifact IDs/attempt-qualified names, and digests. Successful builder jobs do
not rerun for qualification-only corrections; `upload-artifact@v4` overwrite is
never used. Promotion must occur while every selected native artifact is no
more than 21 days past its GitHub artifact `created_at`; later qualification
attempts do not reset that clock. A separate
dispatch at the exact product-tag ref enters a job-level protected environment
before runner allocation; after approval it authenticates the run metadata and
supplied latest attempt, downloads archives/manifests by immutable artifact ID,
rehashes, and signs/publishes those exact staged bytes. It never rebuilds. A
partial retry creates the release only if absent, digest-compares and skips
identical assets, uploads missing assets, and stops on different bytes; it never
clobbers. Evidence reconciles:

- cataloged known union versus every target manifest;
- manifest paths and digests versus extracted final bytes;
- target-specific OpenSSL and external-runtime dispositions;
- current asset-manifest reachability versus staged digest files;
- `allbert licenses --json` versus the packaged manifest; and
- published archive digest versus the exact validated archive.

No gate rebuilds a lookalike artifact for validation.

## B. Daemon-Backed TUI Flow

### B1. Additive Attach v1 protocol

The existing Home-local Unix-domain socket, token, Home/user/version handshake,
packet bounds, and concurrent-client cap remain. The request shape gains an
optional request kind:

```text
kind absent or :command -> existing unary argv request/reply semantics
kind :tui_session       -> bounded authenticated session framing
unknown kind            -> stable unsupported-kind error
```

Existing clients that omit `kind` remain valid. The session extension is for
the TUI contract only; it is not a general remote transport or application
streaming framework.

The Erlang-term wire shape remains atom-keyed and atom-tagged in the existing
bounded safe-term codec; string aliases are not accepted and decoding never
creates atoms from input. Because `kind` is inside the shared first term, the
transport performs the legacy-compatible `[:safe]` decode needed to classify
that packet; a raw `COMPRESSED` packet classified as `:tui_session` is rejected
before session schema/identity validation or runtime dispatch. Later session
packets reject `COMPRESSED` before term decoding. Session open is
`%{kind: :tui_session, frame: :open, ...}`. After it succeeds, the closed
client-to-daemon frame set is `:input`, `:resize`, `:cancel`, `:confirmation`,
`:ack`, and `:detach`.
The closed daemon-to-client set is `:snapshot`, `:delta`, `:status`,
`:confirmation`, `:completion`, `:error`, and `:close`. Frames carry protocol
version, session id, and monotonic sequence where ordering matters.
Unknown/invalid-schema/wrong-session frames fail with `:protocol_error`, bodies
over 64 KiB with `:frame_too_large`, sequence gaps/regressions/exhaustion with
`:sequence_error`, and regressed/impossible acknowledgements with `:ack_error`;
they fail the session, not the daemon. An incoming `ack` acknowledges this
endpoint's outgoing stream and must remain between the last peer ack and the
highest local sequence sent. The existing Settings Central
`channels.tui.max_text_bytes` value is reused as both the inbound-input and
rendered-text ceiling (bounded 1–32,000); no second TUI text-limit setting is
added.
The root map counts as container depth one; only maps and proper lists are
session containers, and exact schemas reject tuples, floats, process/runtime
terms, and unknown keys. Frame validation is atomic and ordered: schema/session/
direction, then sequence, then acknowledgement, then bounded admission. Render
revision remains presentation correlation only; snapshot replaces, while v1
does not infer authority or a transport close from revision monotonicity.
ADR 0091's protocol-v1 table is normative for exact required/optional fields,
field types, frame/text/resize/decode bounds, sequence and cumulative-ack
windows, queue limits/drop order, correlations, snapshot/delta shapes, and
close/error codes. `binary_to_term(..., [:safe])` is followed by that application
schema/bounds validation; safe-term decoding alone is never acceptance.

Every admitted `:input` carries a client-generated bounded `input_receipt_id`
whose identity is independent of the transient session id and sequence. A
retry after an ambiguous close, including through a fresh authenticated open,
reuses that receipt id. Before **every** ordinary, slash, correction, and coding
`:input` dispatch, the daemon atomically gates through an extended
existing `channel_events` inbound row keyed by verified local operator/profile
plus receipt id. The row binds the normalized payload with a domain-separated
`allbert.tui.receipt-payload.v1` HMAC derived from
`secret://system/integrity_v1`/version `1` and records
admitted/running/terminal state plus input-signal/message and safe result refs.
A live retry receives running/completed state without another dispatch; a
different payload under the same id fails closed. If the daemon restarted after
admission but before a durable terminal ref, retry returns `outcome_unknown` and
requires an explicit new receipt to retry—it does not claim impossible exactly-
once effect recovery. The client creates the id before send and retains it until
a terminal acknowledgement. Frame sequence/
ack state provides bounded transport pressure only; it is never the durable
input-idempotency key.
The separate `:confirmation` frame remains idempotent through its existing
confirmation id and same-channel callback binding; it does not use an
`input_receipt_id`.

M0.b2 adds one narrow capability to existing Settings Secrets/Key Custody:
serialized `fetch_or_create_system/2` accepts only closed ref
`secret://system/integrity_v1`, generates 32 random bytes only for a genuinely
fresh Home, commits encrypted material before returning it, and never exposes
the value through ordinary settings output. The TUI derives only
`allbert.tui.receipt-payload.v1`; v1.3 reuses the same ref with distinct Memory,
Search, and delete-preview domains. The shared helper derives each domain key as
HMAC-SHA-256 of the Home key and UTF-8 domain string, then HMACs the canonical
length-prefixed ordered field list with that domain key. Its callable seam is
`system_hmac(domain, fields, key_version)` plus
`verify_system_hmac(domain, fields, tag, key_ref, key_version)`; the raw
fetch/create primitive remains private. There is no second key process,
file, or per-consumer encoding, and consumers receive tags/verification results
rather than raw Home key material.

As landed, a new receipt commits `received` and then `admitted` before handing
normalized input to the Adapter for classification and dispatch. A rejected
handoff is terminalized as failed. This is deliberately more conservative than
leaving an unrecorded classification/dispatch window and does not add a second
classification service.

### B2. Ownership and startup

```text
operator runs allbert tui
  |
  +-- resolve ALLBERT_HOME; read attach socket/token
  +-- socket/token absent
  |      -> fail closed with exact `allbert serve` / service repair guidance
  |         (never boot an embedded Runtime)
  +-- handshake mismatch
  |      -> refuse with Home/user/protocol/version diagnostic
  '-- authenticated open
         -> daemon reserves the Home's one TUI session
         -> run existing IdentityBootstrap.prepare_local_launch semantics
         -> explicit-false remains disabled; otherwise start exactly one
            temporary headless TUI adapter child
         -> duplicate open returns already_attached
         -> daemon emits initial snapshot
         -> client enters raw mode only after open succeeds
```

The daemon owns Runtime, operator identity, confirmations, Pi-mode state,
conversation persistence, action execution, and event fan-out. The client owns
TTY detection, input normalization, resize signals, rendering, and idempotent
terminal restoration on handled exits. SIGKILL, power loss, or terminal failure
cannot run cleanup; operator diagnostics provide `stty sane`/`reset` recovery
without a watchdog. The client sends no authority-bearing module/action
names supplied by model output; user input follows the existing Runtime and
registered-action paths.

Before authentication, the daemon permits at most 16 concurrent pending
handshakes, each with the existing five-second read deadline. This is separate
from the 16-child unary-command task cap. A successful open transfers the socket
to its monitored session owner and releases the pending slot; failure closes it
without creating an adapter or runtime work.

The normal daemon channel supervisor excludes the TUI adapter until an
authenticated session open; the session owner performs the same bootstrap that
the embedded launcher previously performed and starts one supervised temporary
child. Session close stops it; a later open repeats bootstrap/settings resolution
and starts a fresh child. This avoids both an unconditionally booted stale/
disabled adapter and a duplicate dynamically started adapter.

If the Attach listener cannot bind, `serve` and Web may remain available with a
visible unhealthy/degraded Attach status. TUI and attach-only CLI commands fail
closed with repair guidance; they do not start a competing embedded writer.

The M0.b2 session owner is a plain GenServer because it owns bounded transport
custody and lifecycle cleanup but no action authority or durable state machine.
M0.b3 excludes the static adapter from normal application startup and replaces
both launchers with the same attach-only thin client; neither `allbert tui` nor
its Mix twin has an embedded Runtime fallback.

### B3. Session lifecycle, pressure, and cancellation

```text
terminal input -> bounded client frame -> daemon session owner
  -> existing TUI Adapter / Runtime attended-turn FIFO
  -> confirmations and action effects through ordinary authorities
  -> ordered bounded event frame -> render
```

- One active TUI session per Home; no live frame-stream reconnect/replay in
  v1.2.4. A fresh session may inspect/retry an ambiguous input with the same
  `input_receipt_id`; it sees terminal/running state or `outcome_unknown` under
  the durable receipt contract above and never automatically redispatches an
  uncertain input.
- Resize and render events coalesce. Low-value progress may be dropped under
  pressure; confirmation, completion, error, and terminal-state frames may not.
- Daemon CRLF/LF output becomes bounded logical terminal lines, including blank
  lines. The client repeats that expansion defensively for all presentation and
  confirmation text, replaces every other C0/C1 control rather than executing
  it, and fails closed if required confirmation disclosure cannot fit.
- Droppability follows presentation priority/custody rather than the frame tag:
  an authority fan-out `:delta` keeps its waiter through gap recovery until
  cumulative client ack or teardown. A close drains already-queued
  non-droppable frames after applying the peer ack and is the final frame;
  bounded inability to drain fails custody and closes as overflow.
- A slow client cannot grow daemon memory without bound or block Runtime.
- Socket loss releases the session; a surviving client that detects it restores
  its own terminal.
- Durable background jobs already admitted may complete after disconnect.
- An attached, effectful Pi coding turn is cancelled fail-closed on session loss;
  no unseen confirmation or next effect proceeds.
- TTY restoration runs for normal exit, Ctrl-C, daemon error, decoder error, and
  abrupt socket closure.
- The packaged dispatcher and source qualification runner append OTP `+Bc`
  only for the thin-client VM. This delivers raw Ctrl-C to state-aware handling:
  interruptible attended states or unresolved client-custodied input cancel with
  `:operator_interrupt` before detach, while idle/error/durable-background state
  with no unresolved input detaches without a synthetic cancellation. It does
  not change daemon signal handling, invoke `stty`, or rely on private OTP
  terminal-mode APIs.
- Uncatchable client termination has explicit `stty sane`/`reset` recovery and
  no claim that client cleanup ran.

## C. v1.2.4 Release Rejoin

Immutable attempts `v1.2.1` at SHA `9f47c7c7`, `v1.2.2` at SHA `15c15484`, and
`v1.2.3` at SHA `b8a01584` produced no workflow artifacts or GitHub Release.
The first exposed an unbound web asset-clean root; the second proved that nested

Nothing rebuilds or publishes under any failed tag.

The v1.2.4 candidate barrier requires one clean pushed SHA and the exact native
artifacts derived from it. Focused license and TUI lanes run during development;
the rejoin records docs/drift review, dependency-refresh disposition, focused
test/static/security metrics, and the structurally verified ordered-step
definition `release.v121 = release.v12 + v1.2.4 focused contracts`. It executes

definitions remain composed so final M9.b can prove and execute the cumulative
contract at one exact v1.3 SHA.

After that focused source rejoin passes, the `v1.2.4` tag triggers exactly one
native build for each target. The resulting versioned archives and digest manifest are
retained for 30 days and held for separate packaged-license qualification and
TUI FV; no validation rebuild is allowed. Downstream jobs in that source run
consume the immutable archives, upload attempt-qualified artifact container
`m0a3-evidence-a<run_attempt>` with stable inner `m0a3-evidence.json`, then
compose attempt-qualified `qualification-evidence-a<run_attempt>` with stable
inner `qualification-evidence-manifest.json` after TUI FV; neither job uploads new
product bytes. Once that source run succeeds, dispatch the separate protected
`workflow_dispatch` promotion at the exact immutable tag ref while that per-
artifact window remains open. The promotion tag input must match
`GITHUB_REF_NAME`; it also
receives the source workflow run id/attempt plus exact digest/evidence artifact
IDs and digests. The `release-promotion` environment gates the
job before a runner or environment secret is available. After approval,
explicit `actions: read`, `contents: write`, and `id-token: write` permissions
let it authenticate repository/workflow/`push` event/conclusion/tag/SHA/attempt,
download by artifact ID, verify archive digests and evidence bindings,
rehash, cosign-sign, and publish those same bytes. It contains no build job.
Unchanged-byte qualification retries upload new attempt-qualified evidence and
reuse staged archives without rerunning successful builders. A source or
artifact-byte fix requires a new
operator-authorized immutable patch tag; missing, older-than-window, or expired
staging evidence stops for operator disposition and never silently rebuilds
under an accepted digest set. Tap fill, install, signature verification, and
re-smoke follow. A publication retry skips only digest-identical existing
assets, uploads missing ones, rejects differing bytes, and never uses
`--clobber`.

# Part II — v1.3.0 Memory And Search

## D. Canonical Corpus And Source Policy

### D1. SourceEnvelope production

```text
Memory collection or Search projector asks Conversations.Corpus.page/1
  |
  +-- canonical ownership query scoped to operator/Home and high-water bound
  +-- stable keyset cursor (inserted_at, stable message id)
  +-- verified channel/principal mapping and current source classification
  v
typed, versioned SourceEnvelope
  - stable message/thread/operator/principal identifiers
  - author kind and role as separate fields
  - source class, surface/channel, thread kind, and trust classification
  - canonical creation/order timestamp and current content digest/version
  - content and bounded origin/trace references
  - no permission or authority grant
```

The high-water bound makes one scan repeatable while new messages arrive.
Opaque cursors are internal Corpus tokens, not table offsets exposed as public
contracts. Consumers persist only their own cursor/digest state; no generic
consumer cursor table is introduced.

Corpus also owns batch `rehydrate_and_authorize` and bounded
`conversation_context` reads. Search and Memory use those operations for final
eligibility/digest checks and nearby assistant disambiguation respectively.
They never join or attach the canonical conversation tables themselves.

Verified operator authorship requires the current principal mapping and trust
classification; `role == "user"` alone is insufficient. In one inbound
admission transaction, each canonical remote message stores nullable
`origin_thread_ref_id`, immutable normalized `origin_principal_digest`, and
`principal_normalizer_version`, while its provider message ref stores the exact
`thread_channel_ref_id`; Corpus compares that snapshot with the current enabled
identity mapping. A legacy remote row is backfilled only if one exact ref and
principal mapping is provable, otherwise it is
`legacy_principal_unverified` and excluded. Local authenticated Web/TUI/CLI rows
derive operator identity from canonical user ownership plus local trust and need
no fake provider ref. Visible assistant
replies copy the verified request origin evidence while retaining assistant
authorship and may be indexed by Search, but they cannot
originate or corroborate a memory claim.

### D2. Change notification without a new event platform

```text
canonical conversation commit/delete/remap
  -> existing signal path emits a content-free coalesced dirty wakeup
  -> Jobs.Managed.kick("search-index", Home) advances the existing entry's due
     time without creating a job or running Search directly
  -> the ordinary Jobs runner records and executes Search ingestion when due

hourly search-index repair
  -> capture the epoch's Corpus high-water, starting `eligibility_epoch`,
     and starting projection revision
  -> bounded cyclic Corpus inventory with an independent repair cursor/epoch
  -> compare canonical ids/digests/eligibility with projected rows
  -> upsert current rows and mark them seen in this repair epoch
  -> at a completed compatible epoch, sweep only rows whose immutable
     first_projected_revision <= the epoch-start revision and which were not
     seen/currently eligible
```

Canonical writes never wait for Search. A missed wakeup only affects reported
freshness: query-time Corpus reauthorization still prevents disclosure. There
is no durable event bus or cross-database transaction. The repair cursor is
Search-owned projection state and advances across bounded hourly runs; it does
not restart a full-corpus scan every hour or turn into a generic consumer
offset service. Writes after the epoch high-water remain dirty and cannot be
swept as unseen members of the older epoch. A pause on `search-index` suppresses
dirty kicks without clearing dirty state; resume, manual run, or the next hourly
due run catches up through the same Jobs entry and run history.

Corpus owns two independent monotonic boundaries: ordinary append advances the
source high-water, while canonical deletion/visibility change, principal remap
or invalidation, Search-grant revocation, and Search E2EE opt-out advance
`eligibility_epoch`. A later source high-water leaves compatible build work
valid and dirty for catch-up; an eligibility-epoch change invalidates a builder
whose authorized population may have shrunk or moved.

### D3. Feature grants and source classes

Memory consolidation and Search have independent, non-transitive Settings
Central grants, switched by two named keys with deliberately opposite defaults:
`memory.consolidation.enabled` (default **false**) and `search.enabled`
(default **true**, one switch over both query availability and the ordinary
local managed set). `private_operator` remains the trust/source class, but its
grant also carries one of the three frozen origin scopes — `local_operator`,
`mapped_operator_dm`, `e2ee_operator` — so local defaults cannot accidentally
authorize a less-private transport:

- `local_operator`: verified local Web/CLI/TUI origins. Search is implicit and
  default-on for this origin; Memory remains explicit and default-off.
- `mapped_operator_dm`: current and future verified mapped one-to-one operator
  DMs. One disclosed opt-in per consumer covers this origin—not one prompt per
  channel or thread. Search query scope still defaults to the current DM
  channel/thread under §F3.
- `e2ee_operator`: an additional audited per-consumer overlay on either origin.
  Search discloses that indexing creates a local plaintext-derived projection;
  Memory discloses that a reviewed proposal may become a plaintext Markdown
  claim.
- group/shared/programmatic/unknown: excluded in v1.3.

A Search grant never authorizes Memory collection; a Memory grant never
authorizes Search projection. Once the relevant consumer/origin grant exists,
ordinary eligible ingestion and recurring work do not ask repeatedly. The
canonical invalidation matrix is:

| Event | Memory proposals/claims | Search results/projection |
|---|---|---|
| canonical message/thread deletion | affected pending proposals/legacy drafts become content-free stale outcomes; kept claims survive with unavailable provenance | suppress immediately; dirty repair removes rows |
| principal invalidation or unverified remap | affected pending proposals stale; kept claims survive with unavailable provenance | suppress immediately; dirty repair removes rows |
| Memory origin-grant revoke or Memory E2EE opt-out | affected pending proposals stale; kept claims survive | unchanged |
| Search origin-grant revoke or Search E2EE opt-out | unchanged | suppress immediately; dirty repair removes rows |
| origin remapped and reverified | each consumer re-evaluates only under its own current grant | each consumer re-evaluates only under its own current grant |

An unverified principal/remap makes the source ineligible to both consumers;
consumer-specific grant changes affect only that consumer. No schedule or
projection row confers authority.

Already reviewed Memory claims remain separate operator-owned records until an
independent Archive or confirmed Forget action. Provenance reports that their
source is unavailable/revoked rather than fabricating accessible evidence.

### D4. Confirmed canonical conversation deletion

The third readiness pass found LD 50 and §K3 depending on a canonical delete
that does not exist in the tree; the fifth pass gave it its own architectural
home in **ADR 0093** and plan **LD 79**, because deleting the operator's
history is a Corpus-owned destructive capability rather than a search concern.
M2 adds one ordinary registered Conversations
action, `delete_conversation_content`, not Search or Memory functionality. Its
request is `{target_kind: :message | :thread, target_id, expected_digest?}`.
The authenticated canonical user/operator is server-derived and the target must
belong to it. The client digest remains optional, but the server preview always
derives and binds the exact conversation-owned cascade: message/thread
identities and row versions/content digests plus the ordered channel-thread/
message-reference row identities/versions that the Repo transaction will
delete, followed by a versioned ordered known-core survivor/blocker count
vector and disclosure version. Durable confirmation
stores safe user/operator id, target kind/id/counts, and non-secret key ref/
version plus an `allbert.conversations.delete-preview.v1` HMAC over that ordered
preview, never message text or plain content digests. Cross-domain dependents
are counted for disclosure but are not part of the cascade:

```text
operator requests one exact message or thread target
  -> preview target kind/id, exact conversation-owned cascade, dependent counts,
     and narrow-copy consequence disclosure
  -> destructive confirmation through Security Central bound to that preview
  -> canonical delete COMMITS FIRST in Conversations
       message: delete that message and its canonical reference rows
       thread: delete the thread and cascade its messages/reference rows
  -> Corpus immediately reports the source missing/ineligible
       (query-time reauthorization now covers the whole repair interval)
  -> content-free Jobs.Managed search-index kick schedules projection removal
  -> pending Memory proposal/legacy-draft payloads sourced only from deleted
     messages are scrubbed to content-free stale outcomes
  -> independently kept Memory claims are NOT deleted
       provenance reports the source as unavailable until Archive or Forget
  -> content-free result
       target kind/id, deleted/already_deleted, deleted message count,
       downstream_reconcile_required
```

`delete_conversation_content` is `resumable?: true` and is explicitly added to
`ApproveConfirmation`'s existing generic-resume allowlist. The durable pending
confirmation id plus its server-bound preview is the retry key. If the process
stops after the Repo cascade but before confirmation resolution, retrying that
same pending approval finds the target absent, returns `already_deleted`, and
re-drives the idempotent/coalesced downstream stale-mark/Jobs kick. A fresh
ordinary request for an absent target returns `not_found`. The hourly reconcile
remains the no-retry backstop. No impossible YAML/Repo atomicity, receipt row, or
new deletion-ledger store is introduced. A
caller-supplied or server-bound digest
mismatch requires a new preview/confirmation rather than deleting changed
content. The action recomputes the full cascade digest inside the immediate Repo
transaction, including the bound known-core count/disclosure vector; a
concurrent message/ref/dependency change makes the confirmation stale rather
than expanding its authority. Message deletion recomputes
`conversation_threads.last_message_at` as remaining-message `MAX(inserted_at)`
or the thread's own `inserted_at` when none remain. A thread title
previously derived from that message is intentionally retained and disclosed—it
has no current provenance field and v1.3 does not add one merely to rewrite it.

Before thread deletion, a best-effort known-schema dependency inventory blocks
on live execution-bearing references (active origin-thread Jobs/objectives,
nonterminal fan-out delivery, or open workspace state) with explicit finish/
cancel/rehome guidance; approval rechecks those blockers inside the same
immediate Repo transaction as the cascade. Historical Jobs/runs, objectives, StockSage analysis/
queue rows, channel events/deliveries, artifact links, traces, and closed
workspace state remain separately governed unavailable provenance. The
inventory does not claim universal plugin discovery; unknown/plugin copies are
part of the disclosure. Canonical retention is otherwise unchanged and indefinite; there is
no automatic conversation pruning. Deletion removes only the canonical
Conversations rows and Search derivative. Non-FK Objectives, Jobs/runs, traces,
artifact links/content, and workspace canvas/ephemeral state survive as
separately governed data, retain at most an unavailable provenance reference,
and must tolerate a missing thread/message without restoring authority. The
confirmation discloses those surviving Allbert-managed classes as well as
independently kept Memory, channel/provider copies, backups, exports, snapshots,
and storage remnants.
Deletion is the operator-facing counterpart to Memory Forget: Forget removes
what Allbert concluded, while this removes what Allbert recorded as said. The
two are deliberately separate confirmed acts with separate consequences.

## E. Memory Flow

### E1. Collection and proposal production

```text
memory-consolidation managed job or on-demand registered action
  |
  +-- memory.consolidation.enabled=false -> recorded no-op, no source read
  +-- source-class grant absent           -> recorded no-op, guidance
  +-- pending count at cap                -> recorded no-op, review prompt
  v
bounded Corpus scan (default initial lookback 30 days)
  -> verified operator SourceEnvelopes only
  -> optional bounded same-conversation assistant context
       (transient disambiguation only; never evidence)
  -> deterministic segmentation/normalization/secret rejection
  -> configured local-model advisory extraction, if available
       (no hosted fallback; deterministic high-confidence subset or abstain)
  -> SPAN PROVENANCE GATE (LD 59)
       every semantic field of a consolidation-generated conversation proposal
       maps to an operator-authored source span as:
       source id + source digest + UTF-8 byte start/end + raw-span digest +
       normalized value + deterministic transform kind/version
       assistant context may resolve deixis only by selecting another
       operator-authored span; it can supply no field value
       uncovered field -> proposal REFUSED (counted, never accepted with
       assistant-derived content)
  -> model-independent identity, source, class, secret, digest, dedupe,
     conflict, and policy gates
  -> at most 20 new proposals/run; stop at 50 pending
  -> redacted run summary and next Corpus cursor
```

Traces and objective IDs may be retained as bounded correlation references
already attached to an originating conversation. Trace bodies, objective text,
job history, assistant claims, Search matches, and FTS snippets do not originate
or strengthen a v1.3 memory proposal.

The invariant is enforced by span coverage rather than by asserting the model
ignored text in its own prompt. Coordinates are UTF-8 byte offsets into the
content whose recorded digest is rechecked at review. The transform allowlist
is small and versioned—trim/case normalization and frozen typed date/value
parsers, never model-written replacement text. A bounded assistant excerpt may
be supplied for deixis resolution ("the second one", "there", "she"), but the
accepted claim's field values must be deterministically recoverable from the
operator-authored spans. If the value exists only in assistant text, extraction
abstains. This is what makes
`v13-assistant-not-authority-001` mechanically checkable: an opaque local model
cannot be proven to have discounted context, whereas span coverage is a
deterministic property of the stored proposal.

This span contract applies only to consolidation-generated proposals derived
from conversations. Explicit remember/update actions, confirmed manual
imports, and exact-confirmed legacy drafts do not fabricate conversation spans;
they enter the same claim writer with typed actor/action provenance appropriate
to their real authority path.

An ordinary durable proposal contains normalized proposed claim fields, typed
source IDs and current digests, classification, proposal revision/idempotency
key, extractor profile/version, run id, and review state. It does not copy a
transcript. Review fetches a bounded redacted excerpt from Corpus. A protected
third-party/minor/dependent proposal stores only a redacted pending stub before
individual review. Secret-filter hits are dropped and counted, never stored in
either form.

The registered consolidation action uses additive `:memory_propose`. A current
verified collection grant authorizes only bounded writes of inert proposals,
so scheduled runs do not ask for confirmation every week. That permission
cannot keep/edit/archive/restore/Forget a claim. Those remain separately
dispatched operator Memory actions, with Forget requiring destructive
confirmation; job identity and cadence grant nothing.

Conflict handling is intentionally conservative:

- exact same normalized claim and validity: dedupe;
- provably non-overlapping explicit validity intervals: separate proposal;
- explicit correction/change/effective date supplied by the operator: proposal
  carries the relationship;
- overlapping or underspecified assertions: unresolved proposal;
- `recorded_at` never decides which value is true.

### E2. Frozen review boundary

```text
proposal list -> Web / CLI / thin TUI view
  -> choose exact proposal_revision ids + digests
  -> registered review action via Actions.Runner
       -> rehydrate source + recheck principal, grant, digest, classification
       -> valid keep/edit     : mark applying with deterministic transition id
                                append accepted claim revision once
                                scrub proposal text to content-free result ids
       -> valid reject        : record suppression for unchanged proposal
       -> stale/ineligible    : skip with explicit per-item result
       -> protected proposal  : individual decision only
  -> durable per-item result; idempotent resume/retry
```

`Keep All` is an explicit operation over the exact visible ordinary proposal
revision set captured by the operator; it is never an open-ended query. Partial
success is normal: valid items commit, stale/ineligible items skip, and retry
does not duplicate accepted revisions. Protected proposals never participate in
bulk Keep. Frozen batch/results persist ids, digests, and outcomes rather than
claim content. Review excerpts are fetched transiently and never durably
cached.

Repo proposal state and Markdown cannot share a transaction, so the applying
phase is the recovery contract rather than an implied atomic write. The
deterministic transition id binds the proposal revision/digest, operator/
namespace, and normalized review-decision payload digest, including edited
claim, validity, and relationship fields. The existing applying row temporarily
freezes that normalized payload and digest until append succeeds; the claim
revision stores the transition id. If the process stops after the Markdown
commit but before Repo scrubbing, retry/restart finds the identical committed
transition, scrubs the proposal/applying payload, and finishes once. If the
claim append did not commit, retry first repeats the current Corpus principal,
grant, source-digest, and classification checks, then writes the same frozen
payload once. An ineligible source becomes a stale terminal item; a changed
decision payload or conflicting claim stream fails closed for a new preview/
operator repair. All mutations enter
`Memory.Claims.append(claim_id, expected_tail_digest, transition)`: one per-claim
lock re-reads/validates the tail and pending/completed Forget tombstone, returns
`stale_tail` to a competing writer, writes a complete same-directory temp file,
syncs it, atomically renames, and syncs the directory. An identical committed
transition id is a no-op; a different transition from the same old tail cannot
overwrite it. The last successful authorization and tombstone/tail recheck before append is the
linearization point: a canonical deletion that commits later changes provenance
availability but does not revoke the already reviewed claim. This applies per
item, so a frozen bulk review remains partially successful and idempotently
resumable.

Web and CLI provide the complete review/history path. TUI may show counts and
dispatch the same per-item DTO/actions; it does not own another review store or
workflow. DMs may notify and link to review, but cannot bulk-keep proposals.

### E3. Markdown claim stream

```text
accepted review or explicit remember/update/archive action
  -> enter per-claim serialization with expected tail digest
  -> load and validate one logical claim stream; recheck Forget tombstone
  -> verify immutable prior revision hashes and ordering
  -> append one revision block
       claim_id (stable) + revision_id/sequence (immutable)
       review/author transition
       valid_from / valid_to
       recorded_at (knowledge/system time)
       source ids + source digest + classification
       optional supersedes_claim_id / effective relation
       deterministic actor/action or proposal transition id
       previous-revision digest + revision digest
       domain-separated native-authority key ref/version + integrity tag
  -> sync temp -> atomic same-directory replace -> sync directory
  -> advance the active Memory projection revision idempotently

raw well-formed manual append
  -> quarantine as pending manual revision
  -> registered one-claim repair/import action + explicit confirmation
  -> recheck exact pending revision digest and unchanged prior chain
  -> append content-free manual_import_confirmed transition
       pending revision digest + normalizer version + non-secret key
       reference/version + domain-separated Key Custody integrity tag
  -> projection admits the manual revision only with that valid next transition
```

One human-readable Markdown file is authoritative for each logical claim.
Earlier revision blocks are never modified to mark them retired; a later block
records the transition and the projection derives the effective interval and
current state. A supersession proposal changes no kept claim until accepted.

Every post-v1.3 action-authored authority transition is authenticated under the
`allbert.memory.claim-transition.v1` domain of one per-Home integrity secret; a
valid digest chain without a valid tag remains manual/untrusted content. The
secret is the 32-byte value already provisioned by M0.b2 at
`secret://system/integrity_v1`/version `1` through Settings Secrets/Key Custody
before the first tagged write. Settings master-key rotation rewraps it rather
than replacing it, referenced versions are retained, and a Home containing
tagged state fails closed if the key disappears instead of generating a new one.
The other exact domains are `allbert.memory.manual-confirmation.v1`,
`allbert.memory.destination-chain-confirmation.v1`, and
`allbert.memory.forget-suppression.v1`.

Legacy flat entries load as grandfathered synthetic revision zero with their
current meaning. Their logical id is UUIDv5 namespace
`3a933b90-6d58-5d8c-9cdb-1233c996532f` over name bytes
`legacy-memory-v1\0<category>\0<normalized-Home-relative-path>` using ADR 0002's
path rules; it reads no claim text. Before adoption, a move is a removed source
plus a newly discovered entry. They are not bulk rewritten; the next accepted
change appends a signed adoption/native transition binding the exact legacy
digest and synthetic id, after which the embedded id remains stable across
moves. Duplicate embedded ids or an impossible UUID collision quarantine all
candidates. Value-bound Forget suppression still prevents a copied/moved
unadopted forgotten value from reappearing. The only supported raw manual
change shape is a new append-only revision, and it remains quarantined until the operator confirms that exact
unchanged revision through the registered one-claim repair/import action. That
action appends a content-free `manual_import_confirmed` transition referencing
the pending digest, normalizer version, and non-secret key reference/version,
and carrying a domain-separated integrity tag from existing Key Custody.
Rebuild admits the manual revision only when the current chain contains a valid
confirmation for that exact digest under this Home's key; no Repo confirmation
ledger is consulted.
Modification, reordering, removal of prior content, or a missing/invalid tag
quarantines the claim; validation reports repair guidance without silently
rewriting the operator's file.

Copying a tagged claim stream without its Home's Key Custody material makes the
whole chain pending/quarantined at the destination; it does not make content
authoritative. The destination operator may confirm the exact unchanged whole-
chain digest once, appending a content-free `destination_chain_confirmed`
transition with the destination key reference/version under the destination-
chain-confirmation domain. The unverifiable source tags remain inert history. A
same-Home restore with the original key verifies
without another prompt. This preserves file portability without inventing key
export or rewriting prior revisions.

### E4. Memory projection and temporal retrieval

```text
validated Markdown claim streams
  -> one Memory-owned rebuildable SQLite projection under Allbert Home
  -> shared private promote sequence:
       checkpoint busy=0 -> close -> self-contained reopen -> integrity/query
       proof -> atomic same-filesystem promote -> retain previous
  -> verified generation + monotonic projection revision metadata

direct-answer / vision prompt asks Memory.retrieve(query, opts)
  -> opts.valid_at defaults now; opts.known_at defaults now
  -> reject ambiguous natural-language time as a parameter source
  -> list only reviewed, non-archived claims valid at both axes
  -> deterministic lexical score + scope + stable tie-break
  -> bounded top-N claim rehydration against current canonical stream digest,
     revision/state, and Forget tombstones
       mismatch/archived/forgotten -> omit + queue projection repair
  -> bounded LTM/general context budget
  -> existing direct-answer/vision prompt seam only
```

The projection is complete but disposable; it is neither the canonical app DB
nor Search's DB. On corruption or version mismatch it rebuilds semantic state
from Markdown and consults existing Key Custody only to verify integrity-tagged
manual-import transitions; the key store holds no claim state.
If no verified generation exists, retrieval fails closed with repair guidance;
it does not full-scan every claim during each prompt turn.

An incremental canonical claim transition advances the active projection's
revision; it does not rename/promote a generation. Full rebuild, schema/
normalizer incompatibility, corruption repair, and Forget byte cleanup use a
temporary generation and the same small private promotion helper as Search.
Query-time bounded rehydration makes canonical Markdown/tombstones authoritative
through a crash between a canonical transition and projection repair: a stale
row can reduce recall temporarily but can never restore stale prompt content.

Explicit typed/absolute dates may become `valid_at`/`known_at`. Ambiguous
phrases such as "before I moved" require clarification; model output cannot
silently move either temporal axis. Retrieval remains lexical—no embeddings,
learned ranker, or Search fallback. Unreviewed proposals, archived claims,
forgotten claims, invalid hash chains, and claims outside the requested temporal
view contribute no prompt chunks.

### E5. Archive and destructive Forget

```text
existing delete_memory_entry compatibility action
  -> Archive/retire action
  -> append archived revision; history retained; reversible by append

separately named Forget action
  -> show exact claim and honest deletion boundary
  -> destructive confirmation through Security Central
  -> persist/fsync content-free pending tombstone FIRST at
     <memory_root>/tombstones/<claim_id>.md, resolving memory_root through
     AllbertAssist.Paths
       claim id, deletion time, actor, closed safe reason code, normalizer version,
       non-secret key ref/version, keyed suppression digest, recovery phase
  -> proposal production, claim append, and retrieval deny the digest immediately
  -> idempotently delete authoritative claim stream
  -> logically scrub matching content-bearing proposal/review/batch and
     legacy-draft/applying YAML + referenced draft artifact payloads
  -> remove active projection rows; rebuild/promote a clean generation and
     retire every previous/temp/failed/retired/pending-prune generation
  -> retain content-free proposal/batch outcome ids only
  -> mark the tombstone complete after all active-store steps verify
```

Forget is the operator-authorized exception to append-only history. Its keyed
suppression digest uses existing Settings Secrets/Key Custody with a
domain-separated per-Home key; it does not add a new crypto service or retain
recoverable claim text. It suppresses the exact forgotten claim while allowing
a later genuinely different value for the same predicate to be proposed. The
tombstone records the frozen normalizer version; later normalizers retain the
old verifier while such tombstones exist so an upgrade cannot silently
resurrect an exact forgotten value.

Startup and explicit retry reconcile every pending tombstone from its recorded
phase. Because the tombstone commits first, a stop after any later step is
fail-closed: retrieval and proposal production still deny the value, and retry
continues deletion without duplicating outcomes. No new Forget coordinator or
cross-store transaction is introduced. `Memory.Projection` verifies and loads
tombstone suppression before declaring retrieval ready, then kicks the existing
managed Memory rebuild/reconcile action to resume pending tombstones, applying
rows, draft scrubs, and projection work through existing claim/Repo/projection
Modules. That action finishes tombstone cleanup before attempting any applying
proposal/legacy-draft append, then repairs projection state; the claim writer's
final tombstone recheck is still mandatory. Free-form operator reasoning is transient/redacted and never enters the
content-free tombstone.

The UI and CLI state the bound precisely: Forget guarantees logical
inaccessibility from active Allbert claim, proposal/review, and projection
paths. The disposable Memory projection is rebuilt and all managed old
generations/sidecars are retired. Repo content scrubbing enables core SQLite
`secure_delete` and attempts a bounded WAL checkpoint; FTS secure-delete is a
Search-only concern under §F5. A busy reader or old free page makes physical
byte removal best-effort rather than the completion condition. Forget cannot
prove erasure from unreachable SQLite pages/WAL remnants, backups, snapshots,
exported Homes, filesystem copies, or storage-device remnants; it does not run
whole-application VACUUM or add an encryption subsystem to strengthen that
claim.

**The originating conversation is not deleted, and remains searchable.** Forget
acts on Memory, not on canonical history: the message in which the operator
stated the fact stays in `AllbertAssist.Conversations` and stays in the Search
projection. Forgetting "my address is X" therefore stops Allbert from holding,
retrieving, or re-proposing that claim, but a conversation search for the term
still finds the original turn. This is coherent — the tombstone permanently
blocks re-proposal — but it must appear in the pre-confirmation disclosure
beside the backup boundary, because v1.3 ships conversation search in the same
release and an operator who reads "Forget" as "erase" would be misled about the
one thing they were trying to protect. Removing the underlying message is the
separate confirmed canonical conversation delete action (§D4), and the
disclosure names it as the next step for an operator who wants both.
The redacted portability envelope carries neither suppression tokens nor key
material and import remains dry-run, so it makes no cross-Home suppression
promise. A same-Home full restore preserves suppression only when tombstones and
their existing Key Custody secret survive together. A copied/restored tombstone
with a missing or mismatched key reference causes proposal-producing actions to
fail closed with `tombstone_key_unavailable`; a genuinely fresh Home/new key has
no knowledge of another Home's forgotten values. This limitation is documented
instead of adding a key-export subsystem.

### E6. Legacy memory absorption

Cutover preserves callable shapes while removing duplicate authority:

| Existing shape | v1.3 behavior |
|---|---|
| `search_memory` | Remains the claim-scoped registered search action with its request/result DTO. It reads the Memory projection when enabled/available and preserves its bounded canonical-Markdown fallback when `memory.index_enabled=false` or the projection is unavailable. That fallback is operator-invoked only, never automatic prompt insertion and never a second compiled index. |
| `Memory.Index` / `memory.index_enabled` | The old compiled artifact is never read after cutover. Intent returns no indexed memory candidates when the flag is false; Active Memory remains controlled by `active_memory.enabled`, independent of the legacy flag, and becomes projection-backed. |
| `compile_memory_index` / `max_entries` / `memory.max_index_entries` | The action retargets the `memory-index-rebuild` managed entry and preserves the request/result DTO. The cap bounds one rebuild execution and is reported honestly; reaching it returns typed partial/degraded progress and never promotes an incomplete generation or silently drops claims. |
| `memory-index-rebuild` / `Memory.ReviewCadence` / `memory.review_cadence` | Reconcile the retained stable identity onto `Jobs.Managed`; keep the cadence effective and remove the Memory-private timer. |
| `prune_memory_entries`, `prune_nominated`, retention/limit settings | Preserve preview/result DTO and settings. All candidates stay advisory until the confirmed action appends reversible archive/archive-nominated transitions; none imply Forget or physical deletion. |
| `memory.auto_promote_sensitive_entries` | Keep the operator's stored value readable/writable, mark it deprecated and behaviorally inert, and never treat either value as authority. Do not rewrite it merely to neutralize it. |
| discovery memory suggestions/drafts | Stop only the actual producer, `SelfImprovement.Discovery.suggestion_type/1`, from emitting new `memory_promotion`/`memory_update` suggestions. Retain accepted kinds in `Tools.Discovery`, schemas, stores, display/creation, and promotion paths so existing rows drain. |

Promotion of an existing memory draft requires operator confirmation bound to
the exact draft id and digest. The confirmation rechecks that the draft is
unchanged, then passes its fields through the authoritative claim writer with
typed `legacy_confirmed_draft` actor/action provenance. It neither calls the old
direct Markdown write nor invents a historical conversation span. Retry uses a
deterministic transition id derived from draft id/digest and follows the same
applying/append/scrub recovery contract as proposal review.
After the authoritative append, that recovery replaces the legacy draft YAML
and referenced artifact payload with a content-free terminal outcome. Forget
traverses matching pending/applying legacy state, and the claim writer's locked
tombstone recheck prevents delayed recovery from resurrecting forgotten
content.

## F. Search Central Flow

### F1. Projection ownership and ingestion

```text
Jobs.Managed dirty kick OR hourly search-index due run
  -> the one existing (Home, search-index) entry enters ordinary Jobs execution
  -> registered :search_manage action via Actions.Runner
  -> coalesce ordinary writes toward the 60-90 second freshness target
  -> Search projector obtains bounded Corpus page
  -> current source-class eligibility
  -> Security.Redactor before projection write
  -> ordinary content-free document-locator row in dedicated search.sqlite3
       shared integer rowid + unique (source_type, source_id)
       source id, author/trust/surface/thread/current origin tuple/timestamp
       canonical digest, redactor/tokenizer/schema version
       immutable first_projected_revision (preserved by later upserts)
  -> content-storing FTS5 row at that same rowid
       redacted searchable text only
  -> transaction advances indexed-through cursor, freshness, and monotonic
     projection revision
```

The Search DB is a dedicated disposable projection under Allbert Home and is
excluded from authoritative backups. It contains visible verified operator
messages and visible assistant replies with author labels. Hidden system
prompts, raw provider/tool payloads, action logs, traces, objectives, Memory
claims, notes, files, and attachments are out of the v1.3 index. Assistant
turns produced by Search result rendering carry a deterministic typed marker
and are also excluded so snippets cannot recursively become corpus.

Use one content-storing FTS5 table plus one ordinary document-locator table and
minimal generation metadata rather than an external-content mirror or Ecto
domain. The locator owns the B-tree indexes and every typed filter/order field;
FTS owns no unique or secondary indexes. Locator and FTS mutation plus control-
revision advancement is one transaction, and integrity verifies their one-to-
one shared-rowid relation. Search owns one plain supervised
projection/connection process; it owns no wakeup process, timer, scheduler, or
parallel run ledger. Coalescing is the dirty/due behavior of the one managed
Jobs entry. Startup asserts the shipped SQLite version is at least 3.42 and
that FTS5 is compiled; schema, tokenizer, or redactor incompatibility requests
rebuild instead of accumulating projection migrations.

The tokenizer/query contract is `unicode61 remove_diacritics 2` with bounded
word, quoted phrase, explicit prefix, and typed filter search. Surfaces never
submit raw FTS `MATCH` expressions.

### F2. Verified generation rebuild

```text
manual/on-demand search-rebuild managed entry
  -> capture Corpus high-water, `eligibility_epoch`, and projection revision
  -> build a temporary same-filesystem Search DB generation
  -> page/redact/index to high-water; persist resumable cursor
  -> before each resume/finalize, require the captured eligibility epoch and
     configuration versions current
  -> FTS integrity check + counts/digest/capability verification
  -> shared private promote sequence:
       WAL checkpoint(TRUNCATE) busy=0 -> self-contained builder reopen +
       integrity/query proof with no required sidecar -> stop new admissions ->
       bounded drain + close current and builder handles -> atomically swap
       current/previous -> open/verify new current -> re-admit calls
  -> preserve dirty work newer than the captured Corpus high-water and kick
     search-index for incremental catch-up
  -> retire older generation during bounded maintenance
```

Queries keep using the last verified generation during rebuild and report its
`indexed_through`/staleness. A failed rebuild preserves it. With no verified
generation, Search returns `search_not_ready` plus bounded progress; it never
falls back to canonical table scans. Each committed incremental mutation
advances a projection revision. Any `eligibility_epoch` or incompatible
configuration-version change invalidates a
resumable builder before its next page or promotion; it restarts from a new
high-water rather than publishing rows captured under an old grant/revocation
state. A cursor binds generation, projection revision, normalized request/scope/
order through an opaque `allbert.search.cursor.v1` binding and non-secret key
ref/version, plus the last
**scanned** rank tuple. Its authenticated payload exposes no plain query/filter
digest. If either generation or revision differs, pagination returns
`search_changed` and the caller restarts instead of mixing a result order whose
BM25 statistics changed.

`Search.Projection`, as sole writer and serving-handle owner, serializes that
short promotion cutover with incremental writes. If readers do not drain within
the M1 bound, or the new current fails reopen verification, promotion aborts and
the retained prior generation is reopened/kept serving. No reader remains on a
renamed live SQLite handle. Same-filesystem rename is a namespace atomicity
claim, not crash-durable storage; retained previous state plus startup
verification/recovery is the durability strategy.

### F3. Central query and canonical reauthorization

```text
Web / TUI / CLI / mapped operator DM
  -> registered Search action with typed request
  -> authenticate operator + resolve surface source scope
       local Web/TUI/CLI: all currently eligible history by default
       mapped DM: canonical thread + exact current origin tuple by default
       DM cross-surface: one exact request/cursor-chain confirmation
  -> parse bounded safe search grammar
  -> current verified FTS generation + projection revision
  -> bounded batches of BM25 candidates with deterministic tie-break
  -> batch Corpus.rehydrate_and_authorize(ids, principal, scope, digests)
       missing/deleted/revoked/digest mismatch -> omit + enqueue repair
  -> refill until requested page is full, FTS EOF, or scan budget is reached
  -> generate bounded redacted snippets only for authorized current content
  -> typed result DTO + stable cursor/revision/freshness/scanned-filtered counts
```

The exact total orders are relevance `(bm25 ASC, timestamp DESC, source_id
ASC)`, newest `(timestamp DESC, source_id ASC)`, and oldest `(timestamp ASC,
source_id ASC)`; FTS5's numerically lower BM25 score is the better match. There
is no hidden recency blend. Default limit is 20, hard maximum 100, and snippet
bytes/count are Settings Central bounds. Results carry source
message/thread IDs, author/trust/surface/thread/timestamp, redacted snippet,
score, generation, projection revision, and freshness—not a full transcript.
`source_type` is an optional result discriminator fixed to `:conversation` in
v1.3; it does not create a generic source adapter or dormant filter branch.

Authorization filtering occurs before page formation. M1 freezes bounded
candidate-batch and maximum-scanned values, including hard ceilings for the
maximum public page size. The next cursor advances after the last scanned
ordering tuple, not the last returned row, so filtered rows cannot loop and
leading stale hits cannot permanently underfill later pages. If the scan
budget stops a not-yet-full page, the DTO reports `incomplete: true` and
`incomplete_reason: :reauthorization_scan_budget` with scanned/filtered counts;
EOF reports a complete short page.

For mapped DMs, same-channel/thread means canonical thread equality intersected
with the exact current per-message origin tuple `(owner_scope, channel,
receiver_account_ref, provider_thread_key)`; merged-thread membership never
widens it, and ambiguous legacy assistant origin is excluded. This scope needs
no per-query confirmation once the consumer/origin grant exists. Cross-surface
elevation dispatches registered resumable action
`authorize_search_query_scope`, explicitly allowlisted by the existing generic
confirmation-resume path, for one bounded-expiry request bound to principal,
origin, normalized request, expanded scope, sort, and limit; M1 freezes the
exact expiry. Confirmation storage contains only the confirmation id, expiry,
safe filter kinds/count, scope class, source message id, non-secret key ref/
version, and an
`allbert.search.query-scope.v1` binding—never query text, filter operands, snippets, a plain
content/query digest, or raw resume parameters. Approval returns
`query_resubmit_required`; that resolved confirmation id is the
`query_chain_id`. The DM resends the transient exact request with the chain id,
and Search recomputes/verifies the binding without writing a second grant.
Result cursors carry the chain id and original expiry, so pagination needs no repeat
confirmation but cannot extend the grant. A changed request or expired chain
requires a new confirmation. `search_changed` invalidates only the stale page
cursor: an exact page-one resubmission may reuse the same chain id/binding until
its original expiry.

Search is explicit operator intent. There is no autonomous model search, fuzzy
or trigram index, substring scan, embeddings, or semantic ranking. An explicit
"summarize these results" request is a separate ordinary model turn and follows
the configured provider/egress confirmation policy; Search itself returns
deterministic source-linked results.

### F4. Trace-safe observability

The Search action uses one small additive `Actions.Runner` callback/field for an
action-defined trace-safe parameter summary. Runner invokes it **before** the
`action_requested` signal, validation diagnostics, or any durable action log;
the summary then governs requested/completed signals and error paths. Existing
actions need not opt in. For Search it may record action name, authorized scope
class, filter kinds/count, sort, limit, result count, generation/revision/
freshness, latency, and request/correlation/query-chain IDs. It never records
query text, FTS syntax, query or filter binding digests, filter operand values,
message content, or snippets. If Search summary construction fails, Runner
emits action/correlation plus `summary_unavailable`; it never falls back to raw
params. Validation/parser errors are stable codes/locations without echoing
input.

The same rule covers Security Central confirmation metadata. `params_summary`
uses only the safe shape above; `resume_params_ref` holds no query or operands
and cannot automatically replay Search. Approval requires an exact client
resubmission under §F3. Do not add global special handling for every field
named `query`.

This no-query-retention contract applies to Search-owned control,
confirmation/resume, observability, and managed-job state. It does not claim
that an operator's ordinary canonical conversation turn or configured provider
transcript is absent merely because that turn requested Search; those stores
retain content under their own disclosed policies. Search-result render turns
carry the typed exclusion marker from §F1 so their snippets are not indexed.

### F5. Delete, revoke, and purge

```text
confirmed canonical message/thread deletion
  -> canonical delete commits first
  -> Corpus immediately returns missing/ineligible
  -> Jobs.Managed kicks the one search-index entry
  -> remove projection row and advance freshness
  -> query-time reauthorization covers the non-atomic interval

principal invalidation / unverified identity remap
  -> Corpus `eligibility_epoch` advances immediately
  -> Search results suppressed and pending Memory proposals stale
  -> both consumer repair paths follow independently

Memory origin-grant revoke / Memory E2EE opt-out
  -> affected pending Memory proposals stale; kept claims survive
  -> Search state and authorization unchanged

Search origin-grant revoke / Search E2EE opt-out
  -> Corpus Search `eligibility_epoch` advances; results suppressed immediately
  -> Jobs.Managed kicks bounded Search cleanup
  -> Memory proposals and collection authorization unchanged
```

Canonical conversation retention remains unchanged and indefinite until an
explicit confirmed deletion. Routine Search pruning removes only obsolete
projection generations/tombstoned rows; it does not delete canonical history.

Manual secure purge is registered resumable action `purge_search_projection`,
explicitly added to the existing generic-resume allowlist, and is not a
recurring job. Its safe durable parameters contain only target/source-class
shape, non-secret key ref/version, and the opaque
`allbert.search.purge-preview.v1` confirmation binding.
The affected canonical content must
already be deleted/ineligible, or the affected
Search source class/feature must first be disabled; otherwise purge fails
because recurring ingestion would restore it. It closes Search connections and
covers every Search-owned current, previous, build-temporary, failed, retired,
and pending-prune DB plus `-wal`/`-shm` sidecars. For files that can be opened
it enables FTS `secure-delete=1` and SQLite `secure_delete`. Any generation that
may contain historical deletes is replaced from the currently eligible Corpus;
obsolete/failed generations are deleted wholesale. Replacement requires
`wal_checkpoint(TRUNCATE)` with `busy=0`, close, self-contained reopen,
integrity/query checks, and a negative search for the purge fixture. No openable
or startup-recoverable managed SQLite generation may retain the purged text.
Canonical source purge is handled by its own confirmed action, and neither path
claims erasure from backups, filesystem remnants, or storage hardware.

Before touching generation files, `AllbertAssist.Search.Control` atomically
replaces content-free `search-control.json` outside the generation DBs, advances
its projection/purge policy epoch, and
invalidates every resumable builder and query cursor. Its phases are
`pending`, `connections_closed`, `files_replaced`, `verified`, and `complete`.
Startup/query admission sees an incomplete phase, continues or reports bounded
`search_purge_in_progress`, and never reopens an invalidated builder/generation.
Every other Search query/management operation returns that outcome until the
same continuation completes; managed kicks only coalesce dirty work and retain
operator pause state. Each phase is idempotent, so interruption after any file/
checkpoint/rename step resumes without silently restoring the target. Retry
count and safe `last_error` code are separate diagnostics, never extra phases.
This is Search-owned recovery metadata, not a new scheduler or general
transaction framework.

E2EE-origin indexing adds no encryption layer. Its separate consent disclosure
states that Search creates a redacted but plaintext-derived local FTS file,
protected by filesystem permissions, backup exclusion, policy, canonical
reauthorization, and the purge path.

## G. Managed Recurrence And Batch Work

`AllbertAssist.Jobs` remains the only scheduler and run-history owner. The small
`Jobs.Managed` seam owns stable managed identity, action/operation, invariant
arguments, eligible cadence bounds, feature linkage, and reconciliation. It
does not own projector cursors/generations and is not a second scheduler.

| Managed entry | Trigger/default | Operation | Domain-owned state |
|---|---|---|---|
| `memory-consolidation` | weekly; disabled until grant | bounded collect/propose | Memory source cursor, proposal/run counts |
| `memory-index-rebuild` | retained `memory.review_cadence`; on-demand/resumable | build/verify/promote complete Memory projection | Memory rebuild cursor/generation/revision |
| `search-index` | coalesced dirty kick + hourly repair | ingest/reconcile if work exists | Search cursor, dirty/freshness state |
| `search-maintain` | bounded weekly | integrity, bounded merge, obsolete-generation pruning | Search generation/integrity state |
| `search-rebuild` | active manual schedule (nil due), resumable; bootstrap/recovery kick | build/verify/promote generation | Search rebuild cursor/generation |

Managed entries are visible in normal Jobs surfaces, retain ordinary run
history, and are manually triggerable. Operators may pause an entry and adjust
allowed cadence. Every spec uses its listed stable managed identity as the
deterministic reserved existing-row name and resolves it through the existing
unique `(user_id, name)` key; there is no parallel identity table. If an
operator-created row already owns that name, or invariant managed metadata
differs, reconcile reports `managed_name_conflict`/degraded state and never
overwrites, renames, or duplicates the row. The one adoption exception is an
existing `memory-index-rebuild` row with exact
`template_name: memory-index-rebuild`,
`managed_by: memory.review_cadence`, compatible legacy target, and canonical
local operator. It is retargeted in place while preserving id, run history,
allowed cadence, and pause; a template-only row conflicts. Jobs has no generic
delete path today, so v1.3 adds none merely to prohibit deletion; any future delete must
reject a live managed spec with feature-disable guidance. Disabling a feature
retains its one visible row and stored operator cadence/pause intent, clears
only effective due/admission, and on re-enable honors that prior intent; it
needs no deletion tombstone.

The Home is implicit in its Repo and managed reconciliation uses the canonical
local-operator `user_id`. Thus this document's `(Home, managed_identity)`
shorthand is the physical `(Home Repo, user_id, name)` uniqueness key.

`Jobs.Managed.kick/2` changes only the existing entry's bounded due/dirty state;
it creates no run history until ordinary Jobs admission, respects pause/
disable, and never invokes a domain action directly. Scheduled, manual, kick,
and recovery triggers use one atomic admission transaction and count queued,
running, and needs-confirmation runs as overlap. Every post-migration run sets
nullable `scheduled_job_runs.admission_key` to its job id; a partial unique
index covers non-null keys in those states. Legacy rows remain unmodified and
the transaction checks any legacy open row before insert. A competing admission
returns a typed coalesced/already-open outcome. Each admitted run records the
exact due/dirty value it claimed. Completion reloads the current job and clears
or advances only that value, preserving a newer kick, pause, or cadence edit;
typed continuation scheduling is merged after completion. Thus a kick racing
between action completion and schedule advancement remains due.

`search-rebuild`'s nil due time means active/manual, not paused. On first boot,
restore, or incompatible schema/tokenizer/redactor policy, reconcile kicks it
only when no compatible verified generation exists. An incomplete run becomes
due again with bounded recoverable backoff; a missing SQLite/FTS capability is
visible degraded state rather than an infinite retry loop.

Search management actions require additive `:search_manage` permission and are
local/internal administration. Memory consolidation uses the narrower
`:memory_propose` permission plus the current collection grant; it may create
inert proposals only and does not reprompt per scheduled run. Read-only Search
queries retain read-only authority. Full optimize/VACUUM is not weekly
maintenance; it belongs to explicit rebuild/purge closeout.

New operator-tunable values belong under existing Settings Central namespaces.
The plan fixes conservative defaults: consolidation disabled until grant,
weekly cadence, 30-day initial lookback, 20 proposals per run, 50 pending;
Search **enabled by default for local Web/CLI/TUI** with mapped DM and E2EE

existing Settings Secrets and are never added to YAML or job arguments.

The Search/Memory default asymmetry is intentional and is stated wherever both
appear (LD 60): Search is local, read-only, produces no proposals, writes into
no prompt, and its whole database is deletable and rebuildable, whereas Memory
collection produces durable candidate facts about the operator. Indexing what
the operator already wrote, for the operator's own retrieval, is a different act
from deriving new claims about them.

### Writer ownership across three databases (LD 61)

v1.3 takes the Home from one SQLite database to three. SQLite permits one
writer per database, and v1.1's systemic failure was resource ownership rather
than fan-out logic, so ownership is fixed here rather than discovered:

| Database | Writer owner | Supervision | Non-attached one-shot CLI |
|---|---|---|---|
| canonical Repo (`app` DB) | existing Ecto Repo, `pool_size: 1` (`config/runtime.exs:49`, `config/dev.exs:31`) — unchanged | existing application tree | existing unary attach behavior |
| Memory projection | `Memory.Projection` process, sole writer to its file | daemon-owned application tree | projection-dependent command attaches to daemon or fails closed with attach guidance — never opens the DB itself |
| Search projection | `Search.Projection` process, sole writer to its file | daemon-owned application tree | projection-dependent command attaches to daemon or fails closed with attach guidance — never opens the DB itself |

No cross-database transaction is claimed anywhere. ADR 0091 makes the daemon
the owner of writer discipline; these two processes live under it, and any path
that cannot reach the daemon must degrade rather than open its own writer. Both
projections are derived state: the Search database is excluded from
authoritative export/backup, and the Memory projection is likewise derived and
rebuildable from the Markdown claim streams, so neither belongs in the
migration-time database backup that protects canonical data.
