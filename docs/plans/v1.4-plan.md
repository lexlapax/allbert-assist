## Purpose

Ship the 1.4 flagship: Allbert profiles its own usage, proposes concrete
improvements with evidence, applies exactly what the operator confirms —
one click, one durable confirmation — and reports the outcomes observed after
each applied change without claiming causation. Per-role model profiles and proactive suggestion
delivery ride the same loop; the web workspace becomes genuinely usable
at phone widths.

1. **A usage-signal store that always works.** Additive, local, redacted
   per-turn usage events (decision outcome, action outcome class, model
   profile, surface, bounded millisecond duration — never bodies or secrets),
   with user ownership, idempotency, lifecycle controls, and bounded retention
   (ADR 0090 §1).
2. **Distill/suggest as a managed job.** Periodic, bounded, zero-egress
   deterministic profiling produces inert user-owned suggestion cards carrying
   typed evidence, a concrete proposed change, and its metric rationale; the dead
   `dismissed` status gains its writer and the approve-resume gap is
   fixed (ADR 0090 §2).
3. **One-click CONFIRMED customization.** `apply_suggested_customization`
   is `confirmation: :required` and safety-floor-pinned; changes are
   limited to the shipped allowlist (never permissions/security/egress/
   credentials/fallback gates); the confirmation shows the exact
   before→after diff; application is audited (ADR 0090 §3).
4. **Observed outcomes.** Applied changes link suggestion → confirmation →
   operation ledger → audit; later distill runs compare bounded matched windows
   and label the result as observed, insufficient, or confounded. Revert is one
   confirmed compare-and-set operation (ADR 0090 §6).
5. **Per-role model profiles.** `model_roles.fast|capable|thinking`
   formalized as additive fragments over the ADR 0088 catalog; profiling
   may propose remaps only through the confirmed path (ADR 0090 §4).
6. **Proactive suggestion delivery, default OFF.** The `:suggestion`
   kind on the ADR 0084 boundary with separate opt-in, quiet-hour defer/
   coalesce, and one per-user/channel/local-day reservation (ADR 0084
   amendment).
7. **Prompt-rule variant tuning (operator decision 2026-08-05).** The
   same distill → card → confirm → apply → observe loop, with a second
   delta kind: the shipped prompt-rule catalogs Allbert sends in the
   system role. Tuning selects among **shipped, reviewed variants** of a
   rule marked tunable — it never authors rule text (ADR 0090 §5, LD15).
8. **Mobile-ready web, stage 1.** Breakpoint token roles in the design
   system plus measured Chromium/WebKit usability for chat, objectives,
   settings, and memory at 320 px, 390×844 portrait, and 844×390 landscape.
   Physical-device dynamic-toolbar proof moves to the existing responsive-IA
   remainder; offline PWA and native shell also remain out (rider).

## Current Code State

Readiness-audited 2026-08-06 at `c77fc3719d541cae4159816ebff1a2e9681eaa4a`
after the accepted v1.3.1 source tag and archive. The anchors below are module,
schema, action, and function names; line numbers are historical search hints
only and are not part of the contract. M0 records the accepted-tag and
build-start observations side by side before editing production code.

The audit confirmed the passive v0.47 suggestion pipeline and resume gap, the
unqueryable turn signals, the non-confirming generic Settings write path, the
fan-out-specific `Channels.Notify` adapter, the absence of role aliases and
profiling schemas, the handwritten breakpoint set, and the missing `:v14` /
`preflight` gates. It also found four seams that this revision makes explicit:
user ownership and turn idempotency; compare-and-set plus cross-store recovery;
an enrolled notification target rather than a fabricated Objective; and
replay-safe prompt-rule snapshots.

**v0.47 suggestion pipeline (ADR 0045) — alive, passive.**
`AllbertAssist.SelfImprovement.TraceIndex.index/1` reads markdown traces behind
the self-improvement/trace-index switches. `Discovery.discover/2` maps its four
pattern classes into `tool_discovery_suggestions`, and `Drafts.Store` keeps
draft/discarded/promoted artifacts inert (`live_authority: false`). The
registered `discover_patterns` action is on-demand and read-only; no job
schedules it. Draft promotion uses registered `promote_*_draft` actions,
`Confirmations.create/1`, and `ApproveConfirmation`, but
`@self_improvement_action_names` omits the template and capability-gap promotion
actions. `Workspace.DiscoverySuggestions` is display-only for these cards, and
the existing `dismissed` status has no writer. M0 re-verifies those symbol-level
gaps before S2 changes them.

**Usage signals — rich, not queryable.** Intent router outcomes are transient;
selected detail reaches trace markdown, the assistant message `action_log`, and
`scheduled_job_runs.decision`. Traces are optional and their token estimate is
not a profiling contract. Structured stores exist for conversation messages,
objective events, job runs, and privileged runtime audits, but there is no
user-owned, response-signal-idempotent usage-event projection and no relevant
retention/pruning service. Security review can reconstruct decisions but is not
a general profiling log. S1 therefore projects a minimized terminal-response
event instead of querying or copying these bodies.

**The settings-write trap (the load-bearing fact for §3).**
`permissions.settings_write` defaults allowed; registered
`configure_channel_setting` and `update_setting` do not require confirmation.
`Security.Policy` already pins named sensitive actions such as
`migrate_secrets` and `apply_persona_profile`; apply and revert receive the same
kind of non-overridable floor. `Settings.put/3` validates through
`Settings.Schema` and then writes the store; `Settings.Fragments` explicitly
does not grant write authority. `Confirmations.Store` persists YAML plus a
markdown audit, and `Confirmations.Record.operator_resolution` is the closest
existing outcome linkage, but it is not a CAS/operation-recovery contract.

**Per-role groundwork.** ADR 0061 tiers are embedding/router/escalation
(NOT fast/capable/thinking): the current schema owns embedding, router, and
router-escalation profiles. `fast` is the only schema-default name in the
candidate alias family; `capable` and `thinking` occur in the provider catalog,
codegen alias map, and preference lists but are not Settings role mappings.
Concrete selection occurs in the ReqLLM embedder/disambiguator/proposer,
Coding.Config, Classifier, DirectAnswer, and primary-chat Models paths.
**Steering is deterministic — no model role exists there.** Legacy
`intent.model_profile`/`intent.direct_answer_model_profile` are compatibility
aliases and `set_active_model_profile` still writes the legacy key; removal is
migration-runner-blocked by ADR 0046 and stays out.

**Notify boundary (ADR 0084).** `Channels.Notify` owns the current
status/completion/confirmation-request/consent-offer kinds, ordered
`authorize_and_send/5` gate, Security consult, settings fragment, and
fan-out-shaped delivery adapter. `NotifyDelivery` owns unique delivery keys,
bounded attempts, and delivery states; only status is throttled today. The
once-only consent offer plus typed, identity-reproved callback is the enrollment
precedent. There is no kind allowlist setting, quiet-hours window, exact
suggestion target, or generic typed subject. M0 verifies fragment registration;
S6 generalizes the subject without fabricating an Objective.

**Jobs substrate.** Targets `runtime_prompt` | `registered_action`
through `Jobs.Runner`; `Jobs.Schedule` uses `TimeZoneInfo`; the default managed
job state is paused. `Memory.ReviewCadence` is the distill-cadence template and
v1.3's consolidation job is the second exemplar.

**Mobile baseline.** Tailwind v4 is CSS-first with tokens in `app.css` and no
Tailwind config file. The stylesheet repeats one 768/767.98px convention across
handwritten media blocks, plus a 760px outlier and coarse-pointer rule. The
workspace shell uses `data-layout-mode`, `data-mobile-tab`, a sticky composer,
and a read-only `workspace.mobile.breakpoint_px=768`; the viewport meta exists.
The design-system gap analysis records missing breakpoint roles/nav overflow,
and `Workspace.ResponsiveTest` pins the old values. M0 records the complete
symbol/selector/media-query census rather than freezing counts or line offsets.

**Tests and lanes.** Existing tags predate the v1.4 classification. New/changed
DB suites become `db_serial`; Settings/audit/CAS become `home_fs_serial`; pure
role/rule resolution becomes `pure_async`; LiveView stays `liveview_serial`;
measured browsers become `external_runtime_serial`; real delivery is external
smoke. M0.5 verifies any reclassification against the inventory owner.

## Locked Decisions

1–3 operator-locked (2026-07-24); the rest derived for veto at review.

1. **Mobile stage 1 rides v1.4 as non-flagship scope (operator).**
   Stage 1 + Dynamic-Breakpoints fold-in only; the existing stages 2–4
   remainder is responsive information architecture, offline-capable PWA,
   and a lightweight native shell. The rider may not displace
   flagship milestones — if squeeze occurs, the deferral proposal goes
   to the operator (no unilateral deferral).
2. **Additive-only release (operator, standing).** Usage store, roles
   fragments, suggestion types, notify keys — all additive; legacy
   aliases untouched; no migration-runner pull-forward.
3. **Flagship-focused FV validation (operator, amended 2026-08-05).**
   Disposable Homes; source FV remains a cheap pre-filter, while attended
   packaged primary-function validation runs on one provisional exact-clean-SHA
   candidate before the authoritative aggregate. Findings use the standing
   environment/documentation/executable classification and bounded re-run
   cadence; no validation-only product capability.
4. **Confirmed customization is structurally forced (derived, ADR 0090
   §3).** Both `apply_suggested_customization` and
   `revert_suggested_customization` are `confirmation: :required` and
   safety-floor-pinned by action name. Confirmations bind suggestion revision,
   expected-before value, proposed-after value, target version, and
   allowlist/catalog digests. Resume rechecks those bindings inside the same
   Settings lock as a compare-and-set write; stale state writes nothing.
5. **Suggestions stay inert and profiling owns its lifecycle (derived, ADR
   0045 posture).** Accept-click creates a confirmation; nothing applies
   without approval. User-scoped profiling suggestion, application-operation,
   and outcome records sit behind the shared Suggestions surface rather than
   overloading the draft-oriented discovery row. Dismissed gains its writer;
   the existing self-improvement resume gap is fixed in M2.
6. **The usage store is additive, local, user-owned, redacted, and bounded
   (derived, ADR 0090 §1).** `profiling.enabled=true` is the master switch;
   `profiling.usage_events.enabled=true` controls capture only;
   `max_rows=10_000` (`1_000..1_000_000`) and `max_age_days=90` (`7..365`)
   apply per user. One idempotent event is keyed by terminal
   `response_signal_id`. It stores typed outcomes, a clamped millisecond
   duration, and a per-Home HMAC prompt fingerprint—never bodies, snippets,
   trace prose, model prose, or secrets. Writer failure never fails the turn.
7. **Distill posture (derived).** Managed job, ReviewCadence pattern,
   `profiling.distill.enabled=false`, weekly default cadence, explicit
   activation, and zero egress. Explicit on-demand distill is allowed while
   `profiling.enabled` is true even when scheduling is disabled. v1.4 distill
   is deterministic and reads only usage events plus user-scoped typed
   objective/job outcomes; it does not read message/trace bodies or call a
   model. Synthetic fixtures prove mechanics, never real-world benefit.
8. **Per-role profiles are a naming layer (derived, ADR 0090 §4).**
   `model_roles.<role>.profile` fragments resolve through existing
   `Settings.Models`; no parallel resolver; purpose keys unchanged;
   chooser renders roles; remaps only via the confirmed path. The only role
   syntax is `role:fast|capable|thinking`; all three defaults are `nil`, an
   unconfigured role is skipped with a diagnostic, and role values accept
   concrete profiles only so cycles are impossible.

   **A suggestion remap may never change its configured provider, endpoint, or
   locality (operator decision
   2026-08-05).** Excluding the ADR 0088 fallback gates is not sufficient:
   `model_roles.fast.profile` is itself allowlisted, so a suggestion could
   remap a local role to a hosted profile and introduce egress without
   touching any gate. The allowlist enforces this **structurally** — a
   `model_roles.*.profile` write is admitted only when the proposed profile
   resolves to the same provider, endpoint, and locality tuple as the current
   value. Provider changes, endpoint changes, and local→hosted are refused before a confirmation is created, exactly
   as a non-allowlisted key is. Enforcing in the allowlist rather than
   inside `apply_suggested_customization` keeps one refusal point and one
   denial row. The kernel-redo analysis reaches the same floor
   independently ("model role remap … never crosses the local/egress
   boundary").
9. **`:suggestion` notify kind deepens ADR 0084, not its fan-out adapter
   (derived).** A typed notification-subject interface preserves the existing
   fan-out subject and adds a suggestion subject. An identity-reverified typed
   enrollment binds one exact user/channel/thread target; destinations are
   never inferred. Separate opt-in defaults OFF; email is excluded. Quiet-hour
   candidates defer and coalesce to one deterministic message at the next
   valid window edge. The cap is one reserved/sending/delivered/uncertain
   suggestion message per user/channel/local day. A notification never
   approves anything.
10. **Observed outcomes are measured, displayed, and never auto-acted
    (derived, ADR 0090 §6).** UI and docs say “observed after this change,”
    never “caused” or “helped.” Windows are at most 14 days, use equal matched
    samples with a 10-event minimum and 50-event cap, and expose counts,
    dates, medians/rates, and confounders. States are `pending`,
    `insufficient_data`, `confounded`, `observed_improvement`,
    `observed_regression`, and `no_clear_change`. No automatic rollback.
    Metric version 1 uses a five-percentage-point floor for correction-rate
    direction, a ten-percent relative floor for median duration, and a five-
    percentage-point failure/fallback regression guardrail; smaller movement is
    `no_clear_change`. These are classification floors, not causal or
    statistical-significance claims.
11. **Gate = a bounded `release.v14` delta; the aggregate covers
    everything (derived, operator decision 2026-08-05).** `release.v14`
    is `@v14_focused_steps` only — it does **not** stack
    `@release_v13_steps`, and it does not replay `release.v13`,
    `release.v131`, `mix precommit`, or a full suite. This follows the
    pattern v1.3.1 established rather than the historical
    `v121 ++ v13 ++ …` accumulation. A structure owner test proves: the v1.3 and v1.3.1 gate
    definitions are unchanged, the v1.4 delta is bounded, and the
    authoritative `mix allbert.test release` phases cover **every** owner
    file set — v1, v13, v131, and v14 — without nesting any versioned
    gate inside another. Evidence `release_evidence/v14/`; the already-current
    docs-gate active-plan list is verified at build start and removed only at
    archival.
12. **Behavioral evals + automated flagship loop first (derived,
    standing).** `:v14` enum first; rows per request flow §I with the
    meta-contract; the seeded-usage → distill → confirm → apply → observe loop
    is a CI regression before FV exists. Fixture outcomes prove state and math,
    not real-world efficacy.
13. **Mobile stage 1 acceptance is concrete (derived; standards rechecked
    2026-08-06).** Breakpoint token roles land in the design system doc and
    tokens. Chromium and WebKit measured tests cover 320 CSS px / 400% reflow,
    390×844 portrait, 844×390 landscape, 200% text resize, keyboard/focus
    order, focus not obscured by sticky bars, accessible names/status, no
    horizontal scroll, and zero console errors on chat, objectives, Settings,
    and Memory. The 768px pin becomes the 48rem role without changing behavior;
    every handwritten breakpoint, including the 760px outlier, migrates to the
    reviewed convention. No page-local CSS systems (ADR 0074 rule).

    **Touch targets: ≥44×44 CSS px is WCAG 2.2 SC 2.5.5 Target Size
    (Enhanced), Level AAA** — not the AA bar, which is SC 2.5.8 Target Size
    (Minimum) at 24×24 CSS px. v1.4 keeps the 44px figure (it also matches
    Apple HIG 44pt) as the preferred enhanced target, but v1.4 does not claim
    blanket AAA. The acceptance floor is the AA rule and its spacing
    alternative—a ≥24×24 target, or a smaller target with ≥24px offset to
    every adjacent target—recorded per surface.

    **Vertical viewport units are part of this milestone, not incidental.**
    `100vh` resolves against the *largest* viewport, so on a phone with the
    address bar visible the bottom of the layout is cut off — precisely the
    sticky-composer failure this stage exists to fix. Current `dvh` uses and
    raw `100vh` shells coexist today; M7 inventories the set by selector and
    chooses per site deliberately:
    **`svh` is the default** (fixed to the smallest viewport, so content
    fits on first paint), `dvh` only where a live-resizing height is
    actually wanted and is not animated — `dvh` changes value during scroll
    and causes jitter in transitions. `dvh`/`svh`/`lvh` reached Baseline
    Widely Available in June 2025 (~95% of users); keep a `vh` fallback
    declaration for the remainder. Physical-device dynamic-toolbar proof is
    explicitly deferred to the existing Stage-2 responsive-IA remainder;
    emulation is not represented as equivalent evidence.
14. **Fresh/disposable Homes for all scenarios (derived, standing).**
15. **Prompt-rule tuning is variant selection, never text authoring
    (operator decision 2026-08-05; ADR 0090 §5).** Two facts from
    the tree force this shape and both were verified before the decision
    was written down.

    **Almost no shipped rule is presentational.** Of the nine
    `DirectAnswer.Policy` rules, exactly one — `useful_factual_and_brief`
    (criteria `useful/factual/direct/brief`) — is about style. The other
    eight are authority, truthfulness, or the prompt-injection boundary:
    `supplied_text_is_data` **is** that boundary, `memory_is_reference`
    denies Active Memory authority, `no_false_effect_claims` and
    `acknowledgments_are_not_commitments` are truthfulness,
    `no_routing_or_confirmation` is authority, and
    `answer_current_request` / `preserve_supplied_semantics` /
    `no_unsupplied_details` are correctness. A naive "tune the prompt"
    feature would make the injection boundary editable. Therefore each rule
    spec carries an explicit `tunable?` field **defaulting to false**, set
    true only for rules whose criteria are wholly presentational, reviewed
    like the settings allowlist. The catalog census is a milestone
    deliverable, not an implementation detail.

    **Rule catalogs are digest-bound.** `Worker.QualityPolicy` computes
    `rule_catalog_digest/1` over the rules and records it in quality
    receipts. Free-text rule authoring would either break that chain or
    force the digest to cover operator-authored content. Variants keep the
    catalog a closed shipped set, so the resolved digest stays meaningful
    and a variant change is *visible* in the receipt rather than hidden.

    Consequently a variant is an **enum settings value**
    (`prompt_rules.<catalog>.<rule_id>.variant`), which rides ADR 0090 §3's
    confirmed compare-and-set path. M4.5 builds the replay-safe catalog/snapshot
    substrate and completes the census, but ships variants for exactly one
    rule: `useful_factual_and_brief/default` preserves today's text byte for
    byte; `balanced_detail` resolves to “Keep the answer useful, factual, and
    direct. Include enough detail to answer the request completely, without
    unrelated material.” The enum defaults to `default`; every other rule stays
    non-tunable and exposes no variant key. A typed
    `better|same|worse` card rating after ten eligible turns is the primary
    outcome; length and correction movement are descriptive only.
16. **Data clearing, partial failure, and network posture fail safe (operator
    decisions 2026-08-06).** Confirmed clear deletes usage events, profiling
    cards, and outcomes but preserves Settings, applied-operation records,
    confirmations, and security/audit history. A Settings write followed by an
    audit/linkage failure is `recovery_required`; it is never silent success or
    a blind compensating rollback. M0 also corrects the packaged endpoint's
    current all-interfaces bind to loopback; authenticated/configurable
    non-local access remains v1.6.

## Operator-Visible Win

Allbert starts noticing how you actually use it — and instead of silently
changing anything, it shows you cards: "your quick lookups wait on a slow
model — consider a same-provider/endpoint/locality fast-role remap (evidence: 40 turns,
median 9s)".
One click, one confirmation showing exactly what changes, done — and two
weeks later the card reports what was observed after the change, including
sample counts and confounders, with a confirmed revert. Explicitly enroll one
channel target and a deferred, coalesced headline can reach it after quiet
hours—never more than once per local day. The workspace also works at phone
widths in measured Chromium and WebKit runs.

## Planned Interfaces

- `AllbertAssist.Profiling.UsageEvents` — additive user-owned table and
  terminal-response writer. Fields are user/thread/message and signal
  correlation IDs; terminal, intent, action, confidence, fallback, steering,
  profile/endpoint, surface/channel classes; clamped `duration_ms`; prompt
  length band; per-Home HMAC fingerprint; timestamps. `response_signal_id` is
  unique. Per-user reads and OR-based age/row pruning are bounded.
- `AllbertAssist.Profiling.Distill` — registered action
  (`distill_usage_profile`, `exposure: :internal`) + managed job
  (`profiling.distill.{enabled,cadence}` via the ReviewCadence pattern);
  deterministic user-scoped reads only; emits dedicated profiling suggestion
  rows and abstains below evidence floors. Run summaries are redacted.
- `AllbertAssist.Profiling.Suggestion`, `.Application`, and `.Outcome` —
  dedicated schemas behind the shared surface. Card states:
  `open|confirmation_pending|applied|dismissed|expired|stale|reverted`;
  operation states: `prepared|applied|recovery_required|reverted|failed`;
  outcome states per LD10. Revision/digest, evidence/metric version, sample
  window, allowlist/catalog digest, expiry, and dedupe key are mandatory.
- `apply_suggested_customization` and `revert_suggested_customization` —
  registered confirmation-required, safety-floor-pinned actions using CAS
  bindings and an operation ledger. `clear_profiling_data` is separately
  registered and confirmation-required; it deletes profiling events/cards/
  outcomes but preserves applied-operation and security history. Settings audit
  v2 adds stable entry, operation, suggestion, revision, and confirmation IDs.
- `AllbertAssist.Profiling.CustomizationAllowlist` — exact v1.4 keys:
  `operator.communication_style`, `operator.handoff_detail`, registered
  `channels.<id>.response_style`, `model_roles.{fast,capable,thinking}.profile`,
  and `prompt_rules.direct_answer.useful_factual_and_brief.variant`. Every
  other key is denied; role writes also enforce the same provider/endpoint/
  locality predicate.
- Suggestion lifecycle completion: `dismiss_suggestion` writer; resume
  list fix for the two missing promote actions; web panel gains
  accept/dismiss/apply-flow handlers (render-and-dispatch only); CLI
  source `mix allbert.profiling status|distill|suggestions|apply|dismiss|revert|clear`
  and packaged `allbert admin profiling ...` parity.
- `model_roles.{fast,capable,thinking}.profile` fragments + resolution
  aliases in `Settings.Models`; nil defaults; `role:<name>` chain refs;
  requested-role plus concrete-profile provenance; chooser rows; role-remap
  suggestion type.
- `AllbertAssist.Models.PromptRules` — the variant resolution layer: a
  `tunable?` field default false, the one LD15 variant set, and immutable
  catalog/purpose/version/variant/text/digest snapshots. Six prompt-envelope
  consumers and the separate Worker quality-contract replay path use the same

## Code Seams

**S1 — usage-signal store (M1).** Additive migration and writer invoked once
per terminal response signal from `Runtime.submit_user_input/1`, after response
construction; assistant-message linkage is optional when that persistence
fails softly. The writer is idempotent, user-scoped, content-free, and
noncritical. Startup/post-insert chunked pruning enforces age OR row bounds even
when capture is disabled. Status/disclosure/clear APIs expose no samples.

**S2 — distill/suggest (M2).** Deterministic action reading S1 plus typed,
user-owned objective/job outcomes—never conversation content, trace prose, or
model output. It computes bounded duration, failure/fallback, correction, and
keyed-repeat aggregates; metric version 1 reads the latest 10–50 eligible
events over at most 14 days and abstains below 10 or on ambiguity. It enforces
revision, evidence, a 14-day card expiry, dedupe, and 30-day terminal-card
cooldown. Managed-job activation and explicit on-demand semantics follow LD7.
The reserved per-user job is paused with no effective due time while disabled;
enablement reconciles/resumes the configured cadence, while on-demand execution
does not mutate job state.

**S3 — confirmed customization (M3).** Apply/revert actions plus floor pins,
a separately confirmed clear action, exact allowlist, and revision/value/
version/digest-bound confirmations;
Settings-lock CAS; idempotent operation records keyed by confirmation ID;
audit v2 linkage; startup/on-demand recovery; and one-click web/CLI dispatch
through `Runner.run/3`. Explicit denial marks the card dismissed. Confirmation
expiry marks the card expired (or stale if its binding drifted) and requires a
fresh card/confirmation; it never reopens the revision. Revert refuses to
overwrite a later operator edit.

**S4 — observed-outcome loop (M4).** Equal-size matched windows, metric
mapping, confounder detection, outcome states, panel wording, and confirmed
revert. Communication/handoff/channel style uses steering-correction rate with
length distribution descriptive; roles use median duration with failure/
fallback guardrails; prompt variants use the typed operator rating. Synthetic
CI proves mechanics and wording only.

**S5 — per-role profiles (M5).** Nil-default fragments and
`Settings.Models` alias resolution; purpose keys may reference `role:fast`
without changing existing concrete values. Role mappings accept concrete
profiles only; unconfigured/disabled roles skip with diagnostics; resolution
retains both requested role and concrete profile. S3 enforces configured
profile plus same provider/endpoint/locality. Legacy aliases stay untouched.

**S6 — suggestion notify (M6, ADR 0084 amendment).** Refactor the fan-out-
specific adapter behind a typed subject contract; add an enrolled suggestion
target and ledger subject fields without changing fan-out behavior. The typed
enrollment action re-proves identity and binds the exact channel thread.
Quiet-hours rows defer/coalesce, restart safely, resolve overnight/DST windows,
and reserve the daily cap atomically. No consent-offer message is sent to ask
permission to send notifications; email is absent in v1.4.

**S7 — mobile stage 1 (M7, rider).** Correct production binding to loopback;
add rem-based breakpoint roles; migrate every handwritten media block,
including the 760px outlier; inventory all viewport-height uses with `vh`
fallback and deliberate `svh`/`dvh`; and run geometry/accessibility/console
checks over chat, Objectives, Settings, Memory, and Suggestions in Chromium and
WebKit. Physical-device
proof is not a v1.4 acceptance row.

**Tailwind v4 breakpoint API and its unit trap (verified 2026-08-06).**
This app is Tailwind v4 CSS-first with no config file, and `app.css`
currently has **no `@theme` block** — M7 creates one. Breakpoints are
theme variables: `@theme { --breakpoint-<name>: <len>; }`, with
`--breakpoint-<name>: initial` to remove one and `--breakpoint-*: initial`
to reset them all before defining a custom set.

The trap: **breakpoints must all use the same unit.** Tailwind's defaults
are `rem`, and mixing `px` into them makes the generated utilities sort in
an unexpected order, so breakpoint classes override each other
unpredictably. Allbert's existing breakpoint is expressed in px (768, plus
the read-only `workspace.mobile.breakpoint_px` setting), so M7 defines the
reviewed roles in `rem` alongside the defaults. **768px is exactly 48rem,
which is Tailwind's own `md` breakpoint**,
so the existing pin can be expressed as a role over `md` with no numeric
change and no drift against `workspace.mobile.breakpoint_px`.

**S9 — prompt-rule variants (M4.5).** Census six prompt-envelope consumers plus
the separate Worker quality-contract catalog. Every rule receives
`tunable?: false` by default; only DirectAnswer
`useful_factual_and_brief` ships LD15's two variants. Resolution produces an
immutable catalog/purpose/version/variant/text/digest snapshot, and durable
contracts replay that snapshot rather than current Settings. Non-tunable,
unknown, out-of-set, stale-digest, and historical-replay rows are red-first;
the default catalog remains byte-identical.

**S8 — eval rows + gate (M8).** `:v14` enum FIRST; behavioral rows
(request flow §I) + meta-contract sweep; `@release_v14_steps` =
`@v14_focused_steps` (bounded delta per LD11, not stacked); the
coverage structure test over v1/v13/v131/v14 owner files; evidence
clone; active-plan docs list verification. This is the ADR 0090 Accepted flip.

## Security Posture

This release adds one carefully-fenced application path and one
notification kind:

- **Confirmed customization is the only new effectful path.** Forced
  confirmation for apply and revert (contract + floor pins), the exact LD4
  allowlist, revision/value/version/catalog-digest bindings, Settings-lock CAS,
  idempotency by confirmation ID, and stable audit/operation linkage are
  gate-bound. A post-write linkage failure becomes `recovery_required`; it is
  never reported as success and never triggers a blind rollback.
- **Suggestions and profiles grant nothing.** Cards are inert; the usage
  store is user-scoped bookkeeping with a unique response-signal identity and
  per-Home keyed fingerprint (no bodies, snippets, arbitrary prose, or secrets);
  deterministic distill is zero-egress; ADR 0045's advisory posture holds
  everywhere else.
- **`:suggestion` notify is default OFF** on the single ADR 0084
  boundary. Exact user/channel/thread enrollment is identity-reverified; quiet
  hours durably defer and coalesce; sending/delivered/uncertain reservations
  consume the per-local-day cap; payloads are redacted pointers and can never
  approve anything.
- **Role remaps ride the spine**: settings actions + confirmed path
  only; the fallback egress gates from ADR 0088 are not remappable via
  suggestions (allowlist exclusion). Additionally, a role remap may not
  change provider, endpoint, or locality — the allowlist refuses a
  `model_roles.*.profile` write unless the proposed concrete configured profile
  has the same tuple as the current one (LD8).
- **Prompt-rule tuning cannot reach an authority rule.** Only rules
  explicitly marked `tunable?: true` — presentational ones — are eligible,
  the field defaults to `false`, and the variant must come from the shipped
  reviewed set. The supplied-text injection boundary
  (`supplied_text_is_data`), the memory-is-not-authority rule, the
  truthfulness rules, and the routing/confirmation rule are all
  non-tunable by classification and gate-bound denial row. No operator or
  suggestion text ever enters the system role.
- Mobile stage 1 is presentation-only; packaged web binds to loopback by
  default and non-local authenticated access remains v1.6.

## Non-Goals

- Automatic application of any suggestion; automatic rollback.
- Learned/trained profiling models (System Memory Distillation parked).
  Prompt-rule **variant selection** (M4.5) is deliberately not that: it
  chooses among shipped reviewed alternatives and trains nothing.
- Authoring or editing prompt-rule text. Tuning selects a shipped variant;
  free text never enters the system role, and non-presentational rules —
  authority, truthfulness, and the supplied-text injection boundary — are
  not tunable at all (LD15).
- Proactive notification classes beyond `:suggestion`.
- Legacy `intent.*model_profile` removal (migration-runner train);
  OAuth and configured non-local access (v1.6; catalog lists do not grant
  authentication or bind authority).
- Mobile stages 2–4: responsive information architecture, offline-capable PWA,
  and native shell. Real-device dynamic-toolbar/sticky-composer proof remains
  an acceptance row of the first of those existing remainders, not v1.4.
- New telemetry/egress of any kind; usage data never leaves the machine.
- Retention changes to conversations/traces beyond the usage store's
  own bounds.
- Model-assisted profiling, raw-content joins, causal product-efficacy claims,
  or synthetic fixtures presented as real-world improvement evidence.

  profiling/admin CLI mappings. No malicious validation-only card exists. The
  aggregate has one recorded owner/run at the final remediated candidate, and
  publication evidence binds the promoted artifact generation.

## Validation Design (churn guardrails, binding)

The standing v1.1-lessons contract, instantiated: no validation-only
product capability; the flagship mechanics are CI regressions before FV;
behavioral eval rows plus meta-contract; synthetic fixtures never stand in for
product-efficacy evidence; explicit surface census (web panel, source/packaged
CLI, enrolled notify channel, Chromium/WebKit viewports); disposable Homes;
source FV only after preflight; attended packaged FV on the provisional exact-
clean-SHA generation before the authoritative aggregate; and one classified,
batched corrective loop. Outcome validation initially expects `pending`, not an
instant claim of real-world improvement.
