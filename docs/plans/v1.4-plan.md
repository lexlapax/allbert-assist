# Allbert v1.4.0 Spine Enablers And Kernel Foundation

Foundational flagship: the kernel application and Pack contribution boundary.
The settings/action-spine enablers and three worked pack extractions prove that
flagship rather than competing with it, and the release is sequenced first
because every later release builds on the resulting boundary.

Constraining ADRs: **ADR 0046** (settings schema migration policy), **ADR 0065**
(central action param-contract enforcement) — both already Accepted. This
release applies ADR 0046's admission rule and keeps its runner deferred because
M0 found no eligible real consumer; it reconciles ADR 0065 against the current
shipped action catalog rather than assuming its already-shipped central
enforcement was partial. **One new ADR ships here — ADR 0098** (kernel
application, pack contract, and tier model), written and accepted for
implementation 2026-08-06 per the kernel-redo analysis §13.2 decision 10. It
amends ADR 0017 (plugin contract) and ADR 0031 (settings schema fragments and
authority) and supersedes neither. Its §7 carries the 2026-08-07 operator
amendment: v1.0 is the migration guard; v1.4 establishes the successor
component-owned contract and affected-component test authority.

Companion: `docs/plans/v1.4-request-flow.md`.

complete; M7.1 dependency closure and move freeze is next.** M1.a3's final

### M7.1 — READY; sealed-contract option A approved (2026-08-08)

- **Binding decision and reason.** ADR 0098 already forbids kernel-to-pack
  dependencies and requires inversion before relocation; no new ADR is needed.
  M7.1 implements that decision with small concern-specific contracts because
  v1.4 must let later features and their tests change locally without reopening
  the kernel. There is no global `KernelContext`, untyped service locator, or
  callback from kernel code into a named feature pack.
- **Lifecycle.** A compiled native/residual owner contributes immutable values
  through a narrow snapshot and effectful operations through a kernel-owned
  port. During candidate finalization, composition validates schema, unique
  owner, implementation module/application, and generation; it then binds the
  complete contract set atomically to the exact Registry snapshot and
  Readiness epoch before effects open. Missing, duplicate, malformed, stale, or
  subsequently unavailable providers close Readiness and return the existing
  product-not-ready/fail-closed vocabulary. A previously bound contract is
  never silently reused for a newer generation.
- **Home/Identity closure.** `AllbertAssist.Paths` receives a non-secret,
  immutable Home/config snapshot. `ConfigContext` is explicitly classified as
  companion Home substrate or inverted before R2; feature-specific path
  overrides are contributed by their owning component. The relocated concern
  cannot name Settings, App Registry, Plugin Registry, or a residual module.
  Integrity custody crosses the boundary only as narrow HMAC/verification
  operations or opaque handles; raw integrity secrets never enter snapshots.
- **Security closure.** Policy/settings posture is a validated immutable
  snapshot. Coding grants, Skills, App/Plugin membership, Registry facts, and
  signal/audit/redaction effects are supplied through the smallest applicable
  snapshot or kernel-owned port, not direct module calls. Security remains the
  authority boundary; contribution metadata and provider output grant no
  permission. `External.HttpPolicy` and `External.RequestSpec` are classified
  together: both move as Security substrate, or their seam is closed before R2.
- **Capability closure.** Registry and Runner consume a sealed action catalog
  plus membership/availability metadata and narrow signal/effect ports. They do
  not call App Registry, Plugin Registry, residual release-availability code,
  or Signals directly. Canonical `Response` keeps its M3 contract; dependencies
  on intent/resource structs and redaction are moved with the concern or
  inverted without creating another response format.
- **Generated edge ledger.** Run official Mix xref JSON from
  `apps/allbert_assist` (where sources are `lib/...`) and record every direct
  and transitive compile/export/runtime edge for the exact M8 target roster.
  Supplement xref with AST/module ownership, Mix dependencies, application
  start/config, `priv`/release resources, and owning tests because external
  libraries and dynamic references are not a complete xref proof. Every edge
  receives exactly one reviewed disposition: move companion substrate, retain
  an allowed OTP/library dependency, or introduce and test a kernel-owned
  snapshot/port before R2.
- **Known first-pass edge families.** The ledger starts with, but is not limited
  to: Paths -> ConfigContext/Artifacts/Confirmations/Execution Audit/Memory/

**Six ledger findings that changed a disposition.**

1. **`WriterLock.Holder` is a startup host, not substrate.** It is a supervision
   child added only in daemon/serve mode; its `database.ex` edge exists solely
   to resolve the repo path at `init/1`. Classifying it as retained residual

   residual-to-kernel, which the invariant permits. Moving it would have
   dragged `database.ex`, `repo.ex`, `runtime_env.ex`, and `plugin/paths.ex`
   into the kernel to buy nothing.
2. **`Paths`'s five residual references are configuration keys, not calls.**
   `app_root(AllbertAssist.Settings)` and its four siblings are
   `Application.get_env(:allbert_assist, Module)[:root]` lookups; no function is

   close as one immutable `HomeRoots` snapshot keyed by canonical root id, with
   the owning component contributing its override. This is the `home_roots/0`
   contribution contract of ADR 0098 §4 doing the job it was defined for.

   `RequestSpec → Resources.Ref` by relocation would pull `ref.ex` (467),

   `resource_uri.ex` in a second time. The single call site is
   `Ref.from_external_request_summary/1`, so a one-callback `ResourceRefs` port

   is not inflated either.

`grants`, `home_roots`, `membership`, `release_availability`, `resource_refs`,
`response_values`, `settings`, `signals`, and `skills`.

**Operator decision 2026-08-08 — the Security settings seam is a port, not a
value snapshot.** This section previously specified "policy/settings posture is
a validated immutable snapshot". The generated ledger shows Security Central
reads settings **live on every call**: `Security.Policy.setting_value/2` and
`configured_policy/1` call `Settings.get/1` per invocation, and
`Security.Status.summary/1` calls `Store.resolved_settings/0` per invocation.
Materializing those values into a generation-scoped snapshot would mean an
operator changing a security setting has no effect until composition rebinds —
a product behaviour change the freeze forbids and that no acceptance row claims.
The operator approved closing this edge as a kernel-owned `Settings` port whose
*binding* is sealed and generation-bound while its *values* stay live. Snapshots
remain the mechanism where the facts are genuinely immutable: `HomeRoots`, and
the already-kernel-owned Pack action catalog. Sealed means the binding, not the
data.

**Contract surface.** Eleven concern-specific contracts, each 1–6 callbacks, is
the point of option A rather than its cost: there is no `get(:anything)` entry
point, so no kernel concern can reach a provider it was not bound to. A kernel
concern calls its own contract module by name; the binder is internal and
exposes no generic lookup, and a test asserts that its public function list
stays exactly `bind`, `current`, `fetch`, `generation`, `ids`, `release`, and
`required_callbacks` — the absence of a service locator is an architectural
property, so it is asserted rather than left to review.

### M8.1 — root cause proven by experiment (2026-08-08)

The `:product_not_ready` cascade was traced end to end. Each step was measured
rather than inferred from logs.

1. **The coordinator stops when a metadata generation changes under it.** That
   is ADR 0098's designed controlled restart, not a defect — any app or plugin
   registration triggers one, and tests register constantly.
2. **The default supervision intensity makes that designed response fatal.**
   Killing the coordinator four times inside the default three-in-five-seconds
   window ends `allbert_composition` permanently: the coordinator never returns,
   and the kernel contracts unbind for the life of the VM. Measured directly.
   The lane log shows exactly this shape — four terminations inside 60 ms.
3. **Raising the intensity is necessary but not sufficient.** With it raised,
   twelve rapid kills are survived and the application stays up — yet the
   contracts still never rebind, so the cascade continues.
4. **A restarted coordinator does not finish recomposing.** Readiness resets
   correctly to `:collecting` with a fresh barrier and the Pack registry
   recovers, but composition never completes. Polled for 90 seconds after a
   single kill: no recovery.
5. **It is blocked, not crashing, which is why nothing was logged.** A process
   stacktrace puts the restarted coordinator inside
   `CandidateBuilder.evaluate_passes/4`, in the `Task.async_stream` that runs
   the two capture passes. Retryable compose failures also retry silently, so
   neither path produced a log line — the reason the first two diagnoses were
   wrong.

6. **The capture pass is not blocked, and the timeout is not the problem.** Both
   passes run to completion: a candidate build measures ~12.9 s and ~12.7 s on
   two consecutive calls, well inside the stream's 60 s budget. The earlier
   reading of "blocked in `evaluate_passes`" was a stack sampled mid-work, not a
   deadlock.
7. **Composition completes and then fails at activation.** With non-retryable
   reasons now logged, every recomposition cycle ends the same way:
   `%{code: :activation_nack, phase: :authorizing, pack_id: "allbert_assist",
   expected_ids: ["allbert_assist"], actual_ids: ["allbert_assist"]}`. The
   barrier reopens, asks the residual pack to activate for the new epoch, and is
   refused. The cycle repeats roughly every 25 s indefinitely — measured for
   120 s with no recovery.
8. **The refusal has a concrete cause.** `ActivationGate.fail_activation/2`
   records it: `{:activation_worker_child_failed,
   [AllbertAssist.JidoBacked.Supervisor, AllbertAssist.Objectives.Engine.Agent],
   :EXIT}`. The residual effect subtree cannot start for the new epoch because
   the previous activation's processes are still present. `retire_effect_before_resubscribe/1`
   exists for exactly this, so the retirement path is incomplete rather than
   absent.

9. **Retirement is not the defect either.** The previous activation's processes
   do retire: `Objectives.Engine.Agent` and `JidoBacked.Supervisor` are both
   gone within 15 s of the coordinator's death and stay gone. There is no name
   collision and no surviving subtree.
10. **The real cause is the SQL sandbox.** Logging the raw activation reason
    before redaction — the redacted tag collapses a child start failure to a
    bare `:EXIT` — gives
    `%DBConnection.OwnershipError{message: "cannot find ownership process for
    #PID<...> (AllbertAssist.JidoBacked.Supervisor) (AllbertAssist.Repo) using
    mode :manual"}`. The newly started activation subtree has no checked-out
    sandbox connection, so `Objectives.Engine.Agent` cannot start.

11. **The permanent loop was an artifact of the probe, not the system.** Every
    recovery measurement above used a bare `ExUnit.Case` probe, which checks out
    no sandbox connection at all — so activation could never succeed and the
    loop looked endless. Re-run under `AllbertAssist.DataCase` with its shared
    owner, **recomposition succeeds in 26 seconds**. The system recovers; it is
    slow, not dead.
12. **The real cost is an outage window, and it is large enough to explain the
    count.** Each metadata generation change closes readiness for ~26 s, during
    which every action-based row fails `:product_not_ready`. The lane log
    records 19 coordinator terminations, so roughly eight minutes of a
    ten-minute lane run are spent unavailable. That accounts for the 640
    failures without any permanent failure at all.

**This is a test-environment failure, not a product defect.** Ownership mode is
`:manual` only under `Ecto.Adapters.SQL.Sandbox`. At application boot the
sandbox is not yet manual, so the first activation succeeds; once ExUnit takes
over, any recomposition spawns an activation subtree with no connection
ownership and fails. It also explains the lane distribution exactly: the
Repo-backed `db_serial` lane loses 640 of 1,247, while `global_process_serial`
passes 316 of 316.

**Where the repair lands.** Two levers, both on the test side; production
semantics and ADR 0098's activation contract stay untouched.

- **Reduce the trigger count.** A test that mutates the global App or Plugin
  registry kills the global coordinator and buys a 26-second outage for every
  test after it. `AllbertAssist.TestSupport.RegistryIsolationFixtures` exists so
  a test can hold its own registries instead; the rows that do not use it are
  the defect. This is the same isolation lineage as v0.53 and v1.0.2.
- **Reduce the recomposition cost.** 26 seconds is dominated by the candidate
  build, measured at ~13 s and run as two determinism passes. Whether both
  passes are needed on a *re*-composition, as opposed to the first, is worth
  asking.

Sandbox ownership for the activation subtree is *not* the repair. Under the
shared owner a real test already has, activation works.

**Trigger inventory, handed to M12.1.** 35 test files register into an App or
Plugin registry; only 2 use
`AllbertAssist.TestSupport.RegistryIsolationFixtures`. The other **33 mutate the
global registries** — 26 in `allbert_assist`, 3 in stocksage, 2 in
`notes_files`, 2 in web — and each one that lands outside an existing outage
window costs the next 26 seconds of the run. Nineteen terminations rather than
thirty-three is consistent with that: a registration during an open outage
changes nothing, because the coordinator is not subscribed while it recomposes.

Converting those 33 to isolated registries is suite repair, which is M12.1's
milestone rather than this one. M8.1 establishes and quantifies the mechanism;
M12.1 owns the conversion and re-measures `db_serial` against the 640 baseline.

**Not a cheap win.** The two determinism passes in `evaluate_passes/4` run
concurrently at `max_concurrency: 2`, so removing one would not halve the 26
seconds, and the pass exists to prove the candidate is deterministic. The cost
is the build itself, not the duplication.

**Five wrong diagnoses preceded this one**, each disproved by measurement rather
than argument: that raising supervision intensity would fix it; that the capture
pass was deadlocked; that the stream timeout needed widening; that effect retirement was
incomplete; and that the sandbox could not grant the activation subtree
ownership. The last two were both recorded in this plan before being disproved,
and each was the most confident reading at the time. Every one survived because the
failing path logged nothing useful: retryable compose failures log nothing at
all, and activation failures logged only a redacted tag that discarded the
cause. Both are now logged, and that is what produced the answer.

**Carried forward from this diagnosis:**

- Supervision intensity is raised, because the four-in-60 ms shape is real and
  separately fatal. It is retained as a correct fix for a measured failure mode,
  while explicitly not the fix for the cascade.
- Non-retryable compose failures now log their unredacted reason before the
  stop reason is redacted. Twelve of nineteen terminations in one lane run had
  collapsed to `:composition_rejected`, hiding the cause.
- **Retryable compose failures still log nothing.** That silence is what made
  this take three attempts to diagnose, and it should be closed as part of the
  repair.

### M12.1 — ROOT CAUSE: recomposition costs ~18-27s and nothing waits for it (2026-08-09)

The survey and a bisect finally reach the bottom of this.

**Survey of all 81 lane-failing files, run standalone.** 37 are **clean on their
own** — pure pollution victims — and 44 genuinely fail, totalling **161
standalone failures**. Against a lane of 621, that puts **~460 failures (74%) on
cross-test pollution**, not per-file defects. The per-file conversion is
therefore 161 failures across 44 files, not the ~130 files first projected.

**Bisect: it is not one polluter, it is the pattern.** Running
`mix test <candidate> intent_agent_router_test.exs --seed 0` across the 22 files
that call `PluginRegistry.clear()`, **18 of them break all 27 victim rows**.

**The chain, established by probe rather than inference:**

1. `restore!` is not lossy — every shipped plugin comes back, and the plugin and
   app entries for `notes_files` are byte-identical before and after.
2. Yet `intent_descriptors` for `notes_files` go `3 -> 0` and stay there.
   Normalization returns `{:unknown_action, "write_note"}`.
3. `Descriptor.registered_capability/3` resolves actions through
   `ActionsRegistry.capability/2`, which reads
   `SnapshotCatalog.capability(pack_snapshot(opts), action)` — **the composed
   Pack snapshot**, not the live registries.
4. `Readiness` goes `:ready -> :collecting` on the clear and **reopens only
   after 18-27 seconds**. Sampled: subscription lands at T+5.0s,
   `expected_ids` is still empty at T+16s, `:authorizing` at T+17.9s, `:ready`
   at T+18.0s. `expected_ids` is set by `Readiness.open/3`, so the coordinator
   spent ~18s inside `compose/1` before it could call it.
5. `await_bootstrap` is **0ms** and `ProjectionProvider.closed/0` is **13ms**
   (cached), so the cost is the build/finalize/bind stretch — the behaviour
   digest, measured earlier in this milestone at 12.9s and optimised to 9.0s.

**So every registry-clearing test opens an ~18-27 second window in which the
product is not ready**, and no test waits for it. Whatever runs in that window
fails — with `:product_not_ready` for effect-gated calls, or with silently empty
descriptors for intent rows, because `descriptors_from_source/2` swallows the
failure (`rescue _ -> []`, `catch :exit, _ -> []`) and reports "this app has no
actions" instead of an error. That swallow is why none of this appeared in any
log across four investigations.

**This retro-explains every dead end.** Composition *rejections* were never
load-bearing — the reopen **latency** is. Fixing rejection classes moved
rejection counts and left the failure count at ~621, exactly as it should have.
It also explains why the failures reshuffle with ordering: which tests land
inside the window depends on execution order.

**Where the repair belongs.** A clear-and-restore returns the catalog to an
*identical* baseline, so the ~9s behaviour digest is recomputed to the same
value it just had. Memoising the digest on candidate content would make
restore-to-baseline nearly free and would cut the window for every one of the 18
files at once, without touching a single test. That is a production change to
the composition path and wants its own measurement against the 621-634 baseline.

### M12.1 — a reproducible lane baseline at last (2026-08-09)

Pinning the ExUnit seed was necessary and **not sufficient**. Two runs at
`--seed 1` still gave **634** and **667** failures, with per-partition counts of
`97/115/240/182` against `182/206/133/146`. The seed was genuinely applied —
`seed: 1` appears in both logs.

**The partition packer was the larger source.** `PartitionPacker.pack/3` is
deterministic given its costs, but the costs come from `TestMetrics.file_costs`
— the repo metrics store, which *every test run appends to*. One run's timings
therefore repack the next run's partitions, different files land together, and
the order-dependent pollution moves with them. A pinned seed is a request for a
reproducible lane, so it now pins the packing too: costs are dropped and each
file is priced from its test count alone, which nothing a run can change.
Unseeded runs keep the balanced packing that makes the gate fast.

### M12.1 — all 44 genuinely-failing files repaired (2026-08-09)

The standalone survey found 44 files genuinely failing, totalling **161
standalone failures**. All 44 now pass standalone, verified by a full re-sweep
rather than by the per-file runs that fixed them.

**Six production defects surfaced by the repair**, each of which a user could
hit:

1. **A disabled scheduler ran due jobs.** `Executor.poll_once/2` carries the
   `enabled?: false` clause returning the `"disabled"` summary, but every
   dispatched cycle admits its epoch first and so enters `poll_once/3` — which
   had no such clause, read `jobs.schedule_policy`, and ran work. The guard was
   left behind on the old arity when M1.a3 added the epoch-carrying path.
2. **The TUI adapter crashed instead of failing closed.**
   `dispatch_confirmation/4` never admitted a readiness epoch and reached a
   `Map.fetch!` on `:allbert_pack_epoch`, raising rather than returning
   `:product_not_ready` the way `process_text/3` does.
3. **`allbert admin confirmations approve --remember exact` could never record
   its grant.** `CommandGrants.settings_context/1` dropped `:allbert_pack_epoch`
   from the context it forwards to `Settings.put/3`, while its sibling
   `Resources.Grants.settings_context/1` keeps it.
4. **`mix allbert.delegate` could never succeed.** It dispatched with a nil
   context, so `Areas.Objectives` fell back to `default_context/0`, which
   carries no epoch.
5. **Surface errors were silently dropped.** `EventRecorder.record_error` had no
   context-carrying arity at all, so `Channels.create_event/2` failed closed and
   the audit row vanished exactly when an operator would want it.
6. **The v1.3 zero-shot eval raised `MatchError` instead of its documented
   error.** `evaluate!/2` matched `:ok = EffectGuard.validate(epoch)`, so a stale
   epoch gave no indication that readiness was the cause; the module already had
   `require_current_epoch/1` for this.

**Two test-side classes worth recording**, because they will recur:

- **Arity traps.** The fail-closed clause sits at a different arity per API, and
  the context's position is not consistent: `Confirmations.create/3` takes it
  second with opts third, `resolve/4` takes it fourth, and `expire/2` takes it
  **first**, ahead of opts. A call at the wrong arity resolves to no clause or
  to the fail-closed one rather than erroring usefully.
- **Epoch identity, not just presence.** `select_composition/5` compares the
  claim's own `:effect_context` against the one in opts, so passing a *fresh*
  epoch reads as `:stale_epoch`. Reuse `claim.effect_context`.

**A methodological correction.** An intermediate sweep reported 39 of 44 green;
the next reported five *different* files failing. That was not flakiness — each
reproduced consistently on re-run. Separate `mix test` invocations share the
SQLite file, so leftover rows from whichever file ran before can flip a result.
**Sweep-reported greens are weaker evidence than per-file runs**, and the final
count here is from a full re-sweep at the committed tree.

### M12.1 — the cascade hypothesis is DISPROVED; root cause found (2026-08-09)

The composition-lifecycle cascade recorded in the census findings below is not
the cause of the `db_serial` failures. Three separate repairs to that lifecycle
were implemented and measured against the 644-failure baseline; none moved the
number outside run-to-run noise, and all three were reverted rather than left in
as unvalidated complexity:

- **App-registry reconcile instead of clear.** Register what is missing,
  unregister only what is extra, so the registry is never momentarily empty.
  **658 failures.** No improvement.
- **App-clear-first ordering.** Clear apps first and rebuild them last, so the
  dangling predicate holds at every intermediate point. **622 failures**,
  dangling log lines 109 → 60. Within noise on failures.
- **Coordinator quiescence across `ShippedRegistries.restore!`.** Stop the
  coordinator with `Supervisor.terminate_child/2` for the width of the rebuild
  so its ~20 designed restarts collapse to one. **626 failures, 200
  terminations** against 193 and 203 on the two runs either side. It did not
  even reduce terminations, which means the terminations do not originate in
  `restore!` either.

**What the instrumentation actually established.** `:dangling_app_action_membership`
fires only when an **app** claims an action module that is absent from the
static catalog *and* claimed by no plugin — line 173 of `action_projection.ex`.
The first instrumentation logged the whole `dangling_modules` list, which
normally contains every plugin-provided action, so the StockSage names in it
were the benign majority and were misattributed. Logging only the offending
subset, then the plugin entries beside it, showed the real state: a full app set
paired with a plugin snapshot holding a single plugin. That is a **torn read** —
`compose/1` snapshots the two registries independently and runs
`candidate_builder.build` *before* the `bind_epoch` staleness check that exists
precisely to detect a moved generation. A stale snapshot pair therefore yields a
content verdict instead of a retry. **That ordering defect is real and is
recorded here as a ticket, but it is not what fails the lane.**

**The actual root cause.** Commit `016706066` "1.4 M1.a3 checkpoint explicit
effect carriers" made effect-gated APIs require a context carrying
`:allbert_pack_epoch`, with a fail-closed clause returning
`{:error, :product_not_ready}` for callers that do not supply one. The test-side
conversion was never finished. 264 of the 626 lane failures are a direct
`right: {:error, :product_not_ready}` from a test passing a bare context map.
`016706066` is an **ancestor of the v1.4 start point `791e5aae6`**, so this is
pre-existing and is not an M7/M8 regression.

**Why the earlier census read it as a cascade.** `:product_not_ready` is what
both the cascade and the missing epoch produce, so the log signature could not
distinguish them. What distinguishes them is that the failures reproduce
**standalone**: `supervision_test.exs` failed 38 of 40 in 1.5 seconds on its
own, with no coordinator termination and no composition failure logged at all.
Cross-test pollution cannot explain a single-file run.

**Repair mechanism and cost.** The conversion is mechanical and the feedback
loop is a single file in ~1.5 seconds rather than a ~30-minute lane run.
`AllbertAssist.TestSupport.ReadyEffectContext.attach/1` and `.context/0` are the
canonical carriers and already exist. Worked through on
`supervision_test.exs` as the reference conversion: 38 failures → 1.
  - 39 `Fanout.acknowledge_start(receipt, %{user_id: "alice"})` sites → `attach/1`
    (38 → 11).
  - 2 `Fanout.frame/2` call sites and `create_child_confirmation/3`'s effect
    context → `attach/1`.
  - 4 `Steering.steer/3` sites → `steer/4` with a ready context; `steer/3` is
    the fail-closed legacy arity.
  - `RunServer` does `Keyword.fetch!(opts, :allbert_pack_epoch)`, so a run a
    test starts directly through `DynamicSupervisor.start_child/2` must carry
    its own epoch (11 → 1).
  - The one row still failing is a `Budget v1 recovery` reconciliation timeout,
    a different defect that the conversion does not touch.

**Torn read in `compose/1` — FIXED, and the first proposed fix was wrong.**
The plan initially recorded that both `bind_epoch` calls should move ahead of
`candidate_builder.build`, on the grounds that `bind_epoch_state` is a pure
staleness check. That is only half true and the reorder would have been a
regression: `bind_epoch` *binds the epoch* as a side effect, so binding before
the candidate is known-good leaves `epoch_binding` set when the build then
fails, and every later `bind_epoch` returns `:already_bound` — a permanent
wedge rather than a retry. Operator signed off on the fix on 2026-08-09; the
mechanism below is what was implemented instead.

Both snapshots are taken through `snapshot_and_subscribe`, so a generation that
moved under the coordinator has *already queued a message in its own mailbox*.
`build_candidate/4` therefore reads that mailbox non-blockingly when the build
fails, and reports `:metadata_generation_moved` in place of the content verdict.
That is a pure check with no side effect and no new ordering, and it leaves
restart behaviour identical — a generation change stops the coordinator either
way — while naming the real cause instead of a false
`:dangling_app_action_membership`.

**Measured in isolation** on `db_serial` at four partitions: **645 failures**,
inside the 622-658 band the three reverted attempts established, so no
regression and — as predicted — no improvement in the count. **46 composition
failures are now reported as `:metadata_generation_moved`** rather than as a
false content verdict. 179 `:dangling_app_action_membership` verdicts remain, so
roughly a fifth of them were torn reads; the rest are either genuine or a
generation change still in flight that had not yet reached the mailbox when the
build failed. The value of this change is diagnostic honesty, not throughput.

### M12.1 — an idempotent-restore attempt, reverted (2026-08-09)

`TestSupport.ShippedRegistries.restore!/0` clears both global registries and
re-registers the shipped baseline unconditionally, and the registries advance
their metadata generation whenever the entry set *changes* — so a clear followed
by a re-register of the identical set bumps twice per registry, four times per
call. 37 test files reach this helper. On paper it is the dominant trigger, and
making the helper idempotent by signature looked like the single highest-leverage
fix available.

**It made things worse and was reverted.** Measured on the same two eval files:
one coordinator termination before, three after, with the run then failing in the
composition owner's test helper. Two holes were found and closed during the
attempt — an `:unavailable` signature comparing equal to itself and so skipping
every restore, then an id-only signature blind to an entry replaced under the
same id — and neither explained the regression.

**What this rules out, so the next pass does not repeat it.** Skipping the
restore is not equivalent to performing it, even when the registry entries are
byte-identical. Something restore's clear-and-rebuild re-establishes is not
captured by the entries it leaves behind — the Settings fragment cache that
`register_module` invalidates is the first candidate, and plugin diagnostics the
second. Until that is identified, the trigger count cannot be reduced by making
the helper cheaper; it has to be reduced by tests not reaching for the global
registries at all, which is the conversion work this milestone already owns.

The reverted attempt cost nothing else: the tree is unchanged, and the 30%
encoding win recorded above is independent and stands.

### M12.1 — recomposition cost reduced 30% (2026-08-09)

The outage window is the cascade's whole cost, and the window is the candidate
build. Profiling it — rather than guessing again — found canonical JSON encoding
dominant, and two defects in it.

- **Escaping allocated a codepoint list per string.** `encode_string!/1` ran
  `String.to_charlist/1` then `Enum.map/2` over every codepoint: 274 million
  calls and roughly half the build. It now scans the binary and copies
  unescaped runs wholesale. Equivalent by construction — every escapable
  character is ASCII and every byte of a multi-byte UTF-8 codepoint is `>= 0x80`,
  so a byte-wise scan can neither split nor misread one — and the common
  no-escape byte is matched in a clause head rather than paid for with a
  function call per byte.
- **Every nesting level materialized its own binary.** `canonical_json!/1`
  called `IO.iodata_to_binary/1` for each map and list, so a subtree was
  re-copied into its parent once per level of depth. It now returns iodata and
  the single caller converts once.

**12.9 s to 9.0 s per build, a 30% reduction, with the behavior digest
byte-identical at `2a3195c0…`.** That is the acceptance that matters: canonical
bytes feed every Pack digest, so a faster encoder that changed one byte would be
a silent contract break rather than an optimization.

This shortens each outage from roughly 26 s toward 19 s. It does not remove the
outage — the remaining lever is the 33 test files that mutate global registries,
which is the conversion work this milestone still owns. Measured against the
640-failure `db_serial` baseline once that lands.

**Also verified during this work:** `String.to_charlist/1` in `canonical_string?/1`
had the same allocate-a-list shape and was replaced by a direct binary scan, but
it accounted for only ~8% and is recorded so the next reader does not re-try it
expecting more.

### M7.2 — READY; test split approved (operator, 2026-08-08)

- **Why this milestone exists.** M8's premise is that relocating a module
  relocates its test. The 25 source modules close, but only two of their sixteen
  owning tests do: `writer_lock_test` and `safe_term_test`. The other fourteen
  reference residual modules — `AllbertAssist.Settings` in seven,
  `TestSupport.ReadyEffectContext` in six, plus `Plugin.Registry`, `DataCase`,

  than the compile one. The kernel gate owner independently forbids it — its
  declared lanes are `pure_async`, `app_env_serial`, `home_fs_serial`, and
  `global_process_serial`, and `permission_gate_test` is

  kernel-pure half that relocates and a fixture-bound half that stays with the
  residual, rather than moving only the two that already close or granting the
  kernel a test-only dependency on the pack. The rejected alternatives were
  explicit: moving only two leaves the kernel shipping v1.4 with almost no tests
  of its own concerns, and `{:allbert_assist, only: :test}` is the exact edge
  §2 exists to make impossible.
- **This is content-changing work, so it precedes relocation.** M7.2 edits
  tests; M8 stays a pure move. R2's frozen test digests are reopened here and
  re-frozen at the end of this milestone. That ordering is the same rule M7.1
  followed and ADR 0098 §3 states: a relocation that changes content is not a

- **Provisional shape.** 4,032 lines and 128 test rows across sixteen files. A

  close. A row that cannot be made kernel-pure without changing what it asserts

  element-for-element against the pre-split run rather than by total.
- **Acceptance.** Isolated kernel compile with no `allbert_assist` dependency;

## Locked Decisions

1. **The kernel foundation merges into this release (operator, 2026-08-06).**
   Not a separate release, because param-contract reconciliation, envelope
   consolidation, and the inversions share the same generated roster and the
   sweep must be paid once. Major rejoin points produce exact-clean-SHA evidence
   checkpoints with a named rollback, not product/source tags. `v1.4.0` remains
   one binary release and is not split merely because the implementation is
   large.

2. **Registry inversion is a provable no-op and establishes the pack contract
   (derived).** Historical measurements found 246 action modules using the macro
   and 248 declaring `exposure:`. M0 regenerates the real roster. The inversion
   derives from kernel-owned contribution metadata, preserves deterministic
   `modules/0,1`, `agent_modules/0,1`, internal partitions, and `resolve/1,2`
   behavior element-for-element, and fails closed on
   duplicate action names, pack IDs, setting owners, or gate owners. Kernel
   lists are deleted only after every shipped core and legacy-path pack has a
   contribution and the derived roster matches the frozen M0 roster.

3. **Relocation is not deferred (operator, 2026-08-06).** Deferring it was
   proposed and rejected: the releases immediately after this one build new
   subsystems, and without the kernel boundary in place they would land in the
   monolith and need moving later. Because module names are independent of
   application names on the BEAM, relocation itself is a pure file move. A
   dependency-closure milestone first inverts or relocates every forbidden
   dependency, then freezes content hashes. **M8 accepts zero content diff on
   any relocated module relative to that immediately preceding checkpoint.**
   A content change during M8 means something other than relocation happened.

4. **v1.4 replaces v1.0 as internal contract/test authority at closeout.**
   `release.v1` is a compatibility guard during implementation and must be green
   at the M14 re-baseline. M14 freezes the new component-owned denominator;
   M16 proves and promotes it, after which future changes use component impact
   selection plus the current foundation contract. Observable Tier-1 1.x APIs
   remain compatible at their boundary; this is not permission for a minor-
   version API break.

5. **The ADR 0046 runner remains deferred (operator, 2026-08-06).** M0 found no
   eligible real non-additive consumer, so the operator selected migration
   option A. v1.4 removes the runner, maintenance projection, migration FV, and
   migration DoD while retaining the kernel/Pack/settings-ownership work. A
   future release may admit the runner only with a real consumer that satisfies
   ADR 0046; ownership moves, fixtures, and active compatibility aliases do not.
6. **PermissionGate retires directly into Security Central (operator,
   2026-08-06).** Param validation is orthogonal to authorization. Every caller
   that authorizes continues to call Security at the same action-local point;
   policy vocabulary comes from `AllbertAssist.Security.Policy`, response
   mapping from `AllbertAssist.Runtime.Response.permission_status/1`, and an
   allowed-decision predicate remains local or moves to one canonical helper.
   `decision.source` intentionally becomes `AllbertAssist.Security`; all other
   authorization, confirmation, denial, and response semantics are preserved.

Numbering is local to this plan. Decisions 1, 3–6 carry the 2026-08-06 operator
direction; the remaining implementation consequences are binding unless a
readiness finding reopens them explicitly.

7. **Param-contract work reconciles the current catalog.** M0 establishes the

## Security Posture

PermissionGate deletion retires a facade, not authorization. That is the
highest-risk caller migration in this release and is gated accordingly:

- M0 inventories every production caller and classifies authorization, policy
  vocabulary, response mapping, and allowed-decision usage;
- every authorization caller is characterized red-first at its existing
  action-local point, then moved to `AllbertAssist.Security.authorize/2`;
- `decision.source` is asserted to change to `AllbertAssist.Security`; every
  other decision field, confirmation path, denial reason, response status, and
  trace/audit event is asserted identical;
- the deletion milestone carries adversarial rows attempting to reach an action
  through every path the facade previously covered.

The envelope consolidation must not change any `permission_decision`,
`response_status`, or denial reason. Any difference is a defect, not an
improvement.

## Non-Goals

maintenance projection, or automatic boot migration. Extracting the M0-rostered
non-extracted legacy-path plugins. Dead-code
removal not proven by M0's re-run and M4's production-reference analysis.

## Validation Design (churn guardrails, binding)

- All automated tests and release rehearsals use temporary Allbert Homes and
  never mutate a real `~/.allbert`.
- PermissionGate rows are red-first against the facade snapshot and green only
  after direct Security migration. They assert the deliberate `decision.source`
  delta and exact parity of all other decision, confirmation, response,
  audit/trace, and effect-blocking behavior. Param validation has its own tests
  and is never used as the authorization oracle.
- Envelope consolidation compares every rostered module's full maps and exposed
  serialization for success, denial, confirmation, invalid-param, domain-error,
  and exception paths. Representative sampling alone is insufficient.
- Pack tests prove component-row/`.rel`/raw-`.app`-reconciled
  `Application.load/1` (including already-loaded
  apps), permute diagnostic loaded-application order, and cover missing/
  duplicate/unknown contribution metadata, deterministic action resolution,
  component/`.rel`/`.app`/descriptor disagreement, `.app` digest drift,
  forbidden effective-env override, legacy compatibility scans,
  declared metadata without code loading,
  and preservation of every M0-rostered non-extracted legacy plugin.
- Relocation validation compares R2 hashes, module/public inventories, xref and
  compile dependency graphs, application startup, `priv` lookup, configuration,
  license/release assets, and package loading. A content change belongs before
  R2 or after M8, never inside the move.
- Real configured provider/endpoint validation is required for Telegram and
  email; `notes_files` uses a real disposable filesystem tree. Fakes remain
  automated-test fixtures only. External smokes are opt-in, run after preflight,
  and record endpoint/provider identity without secrets.
- Every gate/lane/partition run records the structured metrics required by
  `docs/developer/test-strategy.md`. Any executable byte change invalidates the
  candidate and re-enters the one-batch remediation cadence before the sole
  aggregate.

## Definition Of Done

1. **D1 — Entry and handoff evidence:** v1.3.1 and v1.3.2 are shipped/tagged;
   R0, R1, R2, R3, R4, R4a, R4b, and R5 identify exact clean SHAs/artifact
   generations, roster/hash/gate evidence, owners, rejoin status, and a bounded
   rollback/discard boundary; no intermediate tag exists merely to split v1.4
   by size.
2. **D2 — Pack/registry contract:** every kernel/native-pack application has one
   valid compiled descriptor and every surviving legacy plugin has one adapter;
   composition-host applications are explicitly classified and do not pretend
   to be packs; declared manifests remain data-only. Ordering, exact Registry
   surfaces, exposure, resolution, tiers, provenance, collisions, application/
   startup readiness, settings/gate owners, and compatibility paths meet M1;
   typed `home_roots/0` policy is containment-validated and grants no authority;
   no kernel existence list remains.
3. **D3 — Param contract:** every action in the final generated static roster,
   reconciled to the M0 baseline through the append-only v1.4 delta ledger,
   validates before its body with the frozen invalid-param response, and the
   evidence honestly records fixes or no-op parity; dynamic/declared overlays
   have an explicit disposition.
4. **D4 — Security facade:** `PermissionGate` and all production references are
   gone; action-local `Security.authorize/2` checks and confirmation/effect
   boundaries remain; only the documented `decision.source` value changes.
5. **D5 — Envelope/cleanup:** the generated action envelope covers the final
   generated roster reconciled to M0 through the append-only v1.4 delta ledger,
   with full behavioral parity and reasoned overrides; clone/dead-code/test
   changes have production-backed proof; `truthy?/1` and `json_safe/1` each have
   a recorded per-semantics decision and final metrics cite the store.
6. **D6 — Settings and gates:** pack-owned fragments preserve every public
   setting contract and secret rule without central owner lists; gate-owner
   manifests reconcile exactly to the independent M7.0 652-file/4,627-row
   repair checkpoint, the ledger-owner delta to 653 files/4,633 rows, and every
   later append-only v1.4 delta; they disposition every M0 path reference and
   follow relocated tests/sources with zero stale old paths, while all frozen
   normalized predecessor obligations/order and preflight integrity checks
   remain green.
7. **D7 — Kernel relocation:** M1.a creates the kernel shell and owns Pack
   behavior/loader/Registry/Readiness before dependency closure; M7.1 proves the
   remaining relocation closure before R2; M8's manifest-listed moves are
   hash-identical to R2; module names/config/`priv`/
   startup/package behavior are preserved; and compile/xref reject every
   kernel-to-pack edge.
8. **D8 — Worked packs:** notes_files, telegram, and email are umbrella sibling
   applications with pack-local settings/tests/assets and no kernel edit point;
   their declared dependency/start DAG is acyclic; every M0-rostered residual
   plugin/asset survives; real configured acceptance smokes pass.
