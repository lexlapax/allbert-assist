# Allbert v1.4.0 Spine Enablers And Kernel Foundation

Enabler release. No flagship feature; this release changes the settings and
action spine that every later release builds on, **and lands the accepted kernel
foundation**, and it is sequenced first for that reason.

Constraining ADRs: **ADR 0046** (settings schema migration policy), **ADR 0065**
(central action param-contract enforcement) — both already Accepted, this
release executes them. **One new ADR ships here — ADR 0098** (kernel
application, pack contract, and tier model), written 2026-08-06 per the
kernel-redo analysis §13.2 decision 10. It amends ADR 0017 (plugin contract) and ADR 0031 (settings schema
fragments and authority) and supersedes neither. That ADR also carries the
re-baselined public-contract freeze, because the freeze tiers and the
kernel/pack boundary are the same concern.

Companion: `docs/plans/v1.4-request-flow.md`.

Status: **planned — triad drafted 2026-07-30; kernel foundation merged in by
the 2026-08-06 operator decision; readiness passes not yet run.** Locked
Decisions 1–4 below carry operator signature from 2026-08-06; the rest are
derived and open to veto at review.

## Build Progress

## Purpose

Land the spine changes that everything after 1.4 depends on, take the one large
mechanical cleanup that shares their blast radius, and land the kernel
foundation so that new capability code has somewhere correct to go.

**Why the kernel work merged here (operator decision 2026-08-06).** The
kernel-redo analysis was accepted and its foundation phase merged into this
release rather than becoming a separate one. The reason is measured, not
aesthetic: param-contract enforcement touches all 249 action modules, the
envelope consolidation touches the same 249, and the analysis's own rationale
for its foundation release is that these passes should not be paid twice. One
sweep, not three.

The second reason is sequencing. The releases immediately after this one build
new subsystems — Knowledge Stage 1 and Knowledge Central. If the pack pattern
does not exist when they start, they land in the monolith and have to be moved
later, which is exactly the coupling regrowth the analysis diagnoses. This
release therefore ships a **proven pack extraction**, not just the inversions.

1. **A settings migration runner that actually runs.** ADR 0046 has been Accepted
   since v0.59, but the runner has been deferred every release because no
   migration was non-additive enough to force it. Three consumers are now
   queued behind it, and v1.7/v1.5 should not be the release that discovers the
   runner is still missing.
2. **Full cross-action param-contract enforcement.** v0.59 shipped a subset;
   the full v0.54 cross-action scope was never closed. Until it is, the contract
   is advisory in exactly the places nobody checks.
3. **PermissionGate deletion.** The gate is the thing param-contract enforcement
   replaces. Deleting it after enforcement is complete removes a parallel
   authority path that has to be kept in sync by hand.
4. **The action response envelope, consolidated.** Folded in deliberately — see
   the sequencing note below.
5. **Registry inversion.** The kernel's hand-maintained action list is deleted
   and the registry derives from metadata the modules already carry. This is the
   highest value-per-risk item in the release and the reason it goes first — see
   LD2.
6. **Settings and gate inversion, `apps/allbert_kernel`, and relocation.** The
   kernel application is created and Home/Paths, Security Central with
   `HttpPolicy`, and the Capability plane relocate into it.
7. **Three proven pack extractions.** `notes_files`, then telegram and email.
   Not cleanup — the template the next two releases build against.
8. **The re-baselined public-contract freeze.** v1.0's inventory describes a
   codebase that no longer exists structurally after this release; the new
   inventory is taken here (LD4).

**Not in this release:** the preflight gate and the release-sequence rules
(AGENTS.md Release Sequence) land in **v1.3.2**, not here. v1.4 inherits
their local preflight attestation, advisory compatibility probe, fixture-drift
registry, and fail-closed change-scope selector. What
remains for v1.4 on the testing side is the deeper problem preflight does not
solve — absolute suite duration. Preflight makes failures *cheap to find*; it
does not make the authoritative aggregate shorter. If the aggregate still peaks
near its recorded 47.7 minutes after v1.8, M5's test-hygiene work is where that
is attacked, informed by the metrics store rather than by impression.

## Sequencing Note (why the envelope work rides here)

Param-contract enforcement touches all 249 modules under
`apps/allbert_assist/lib/allbert_assist/actions/`. A 2026-07-29 duplication
survey found the same 249 modules carry roughly 4,000 lines of derivable
boilerplate:

| Hand-rolled helper | Modules defining it |
| --- | ---: |
| `defp denied/1` | 130 |
| `defp action/3` | 121 |
| standard four-key `output_schema` | 214 of 249 |
| `defp completed/2` | 56 |
| `defp error_message/…` | 34 |
| `defp denied_status/…` | 32 |
| `defp failed/…` | 30 |
| `defp error/2` | 22 |

`action/3` differs across sites only in the `name:` and `permission:` literals —
both already passed to `use AllbertAssist.Action` and stored as `capability/0`.
The macro (`action.ex:55`) generates no response helpers today.

Doing this in the same milestone as param-contract enforcement means one sweep
over 249 files instead of two, and the enforcement work needs to understand those
envelopes anyway. Held separately, the two would conflict on nearly every file.

Near-clone action families found in the same survey and folded in:
`channels/{slack,discord,telegram,matrix,email}_doctor.ex` (534 LOC, ~83%
identical) and `mcp/scan_{enable,pause,resume,run_once}.ex` (473 LOC, ~84%
identical).

The survey also flagged scattered primitives with **divergent semantics** —
`truthy?/1` with 50 definitions across 8 different truth sets, `json_safe/1` with
12 divergent implementations. Those are behaviour reconciliation, not refactor,
and each needs its own decision about which semantics are correct. They are
**not** folded in here as a refactor; M5 disposes of them explicitly.

## Locked Decisions

1. **The kernel foundation merges into this release (operator, 2026-08-06).**
   Not a separate release, because param contracts, envelope consolidation, and
   the inversions share the same 249 files and the sweep must be paid once. The
   analysis's own escape valve applies: bounded by point tags, one per coherent
   unit, with only the final tag a binary release.

2. **Registry inversion is a provable no-op and goes first (derived).** 246
   action modules already `use AllbertAssist.Action` and 248 already declare
   `exposure:`; the registry's 251 aliases and two hand-maintained lists
   duplicate metadata that already exists per-module. `registry.ex` itself
   records the duplication — channel doctors are kept out of the agent set "so
   `agent_modules/0` agrees with capability exposure (v0.54 M9.1 reconcile)".
   The method is therefore: build the derivation, **assert it equals the current
   hardcoded list element-for-element**, then delete the list. A disagreement is
   a latent bug found before shipping, and there is precedent for exactly that —
   v1.3's first authoritative release attempt was stopped by "registry listed a
   destructive action as agent-exposed", caught only after 1,384 tests. This
   change retires that defect class.

3. **Relocation is not deferred (operator, 2026-08-06).** Deferring it was
   proposed and rejected: the releases immediately after this one build new
   subsystems, and without the kernel boundary in place they would land in the
   monolith and need moving later. Because module names are independent of
   application names on the BEAM, relocation is a pure file move —
   **acceptance requires zero content diff on any relocated module.** A content
   change during relocation means something other than relocation happened.

4. **v1.4 re-baselines the public-contract freeze (operator, 2026-08-06).**
   v1.0's tiered inventory describes a structure this release replaces. The new
   inventory is taken at **closeout**, from this release's final shape, and
   supersedes v1.0's from v1.5 onward. Until closeout the v1.0 freeze remains
   **enforced as a regression signal, not a veto**: a milestone that genuinely
   needs to break a v1.0 contract records the decision and proceeds. Retiring it
   at the start would leave the largest mechanical change in the project's
   history with no contract regression check at all, which is the opposite of
   what a re-baseline is for. ADR 0081's Tier-2-to-Tier-1 promotion process
   carries forward unchanged and applies to the new tiers.

5. **The migration runner is the declared pull lever (operator, 2026-08-06).**
   It is the only deliverable here that can damage an existing operator
   installation, and it is independent of everything else in the release. If
   this release runs long, the runner and its two consumers are what get pulled
   — stated now rather than discovered at week six. Automated rollback is its
   **precondition**, proven before the runner migrates anything. Note the
   coupling: pulling the runner also pulls telegram/email pack extraction, which
   depends on their settings becoming plugin-owned. `notes_files` extraction is
   deliberately placed before the runner precisely so the pack template survives
   that pull.

Numbering is local to this plan. None is operator-signed yet.

6. **The migration runner ships unconditionally**, not "when a migration needs
   it". Three consumers are queued and the deferral has already cost four
   releases.
7. **Runner before consumers.** The telegram/email migration, the legacy
   `intent.*model_profile` removal, and automated rollback are all runner
   consumers and land after it, in that order.
8. **Automated rollback is part of the runner milestone**, not a follow-on. A
   migration runner without rollback is a one-way door.
9. **Param-contract enforcement completes the v0.54 scope**, verified by diff
   against what v0.59 actually shipped rather than by assumption.
10. **PermissionGate deletion happens after enforcement is complete**, never
   alongside it.
11. **The envelope consolidation is generated by the existing macro**, with
   `defoverridable` for genuine outliers. No new abstraction layer, no new
   module.
12. **Envelope consolidation is behaviour-preserving.** Any site whose generated
   envelope would differ from its hand-rolled one is an outlier and keeps its
   override, recorded with the reason.
13. **Divergent primitives are not silently unified.** `truthy?/1` and
   `json_safe/1` each get an explicit decision about correct semantics before any
   consolidation, or are deferred with the reason recorded.
14. **This release is additive at the public contract until closeout.**
    `release.v1` stays green as a regression signal throughout implementation
    (LD4). It is superseded only at closeout, when the new inventory is taken
    from this release's final shape. Additive-at-the-contract remains the
    working assumption; the analysis's own check is that module names are
    independent of application names on the BEAM, so inversion and relocation
    should not move a single frozen symbol.

## Security Posture

PermissionGate deletion removes an authority path. That is the highest-risk
change in this release and is gated accordingly:

- enforcement must be provably complete before deletion begins;
- every former gate call site is proven to resolve through the param contract
  with an identical decision, red-first;
- the deletion milestone carries adversarial rows attempting to reach an action
  through a path the gate previously covered.

The envelope consolidation must not change any `permission_decision`,
`response_status`, or denial reason. Any difference is a defect, not an
improvement.

## Non-Goals

OAuth, MCP parity, network hardening (all v1.7). Knowledge (v1.5/v1.6). Any new
feature. Any Tier-1 contract change. Dead-code removal beyond what the envelope
sweep naturally subsumes — the dead-code survey needs re-running first and is
tracked separately.

## Validation Design (churn guardrails, binding)
