## Purpose

Ship the 1.4 flagship: Allbert profiles its own usage, proposes concrete
improvements with evidence, applies exactly what the operator confirms —
one click, one durable confirmation — and reports whether each applied
change actually helped. Per-role model profiles and proactive suggestion
delivery ride the same loop; the web workspace becomes genuinely usable
on a phone.

1. **A usage-signal store that always works.** Additive, local, redacted
   per-turn usage events (decision outcome, action outcome class, model
   profile, surface, timing bands — never bodies or secrets), joined
   with the existing durable sources; bounded retention (ADR 0090 §1).
2. **Distill/suggest as a managed job.** Periodic, bounded, zero-egress
   profiling produces inert suggestion cards carrying evidence, a
   concrete proposed change, and a predicted benefit; the dead
   `dismissed` status gains its writer and the approve-resume gap is
   fixed (ADR 0090 §2).
3. **One-click CONFIRMED customization.** `apply_suggested_customization`
   is `confirmation: :required` and safety-floor-pinned; changes are
   limited to the shipped allowlist (never permissions/security/egress/
   credentials/fallback gates); the confirmation shows the exact
   before→after diff; application is audited (ADR 0090 §3).
4. **Effectiveness feedback.** Applied changes link suggestion →
   confirmation → audit; the next distill measures the delta and the
   panel shows it; revert is one confirmed click (ADR 0090 §5).
5. **Per-role model profiles.** `model_roles.fast|capable|thinking`
   formalized as additive fragments over the ADR 0088 catalog; profiling
   may propose remaps only through the confirmed path (ADR 0090 §4).
6. **Proactive suggestion delivery, default OFF.** The `:suggestion`
   kind on the ADR 0084 boundary with separate opt-in, quiet hours, and
   a per-class rate limit (ADR 0084 amendment).
7. **Mobile-ready web, stage 1.** Breakpoint token roles in the design
   system + phone-form-factor usability for the primary surfaces —
   chat, objectives, settings, memory — at 390 px with no horizontal
   scroll; stages 2–4 explicitly out (rider).

## Locked Decisions

1–3 operator-locked (2026-07-24); the rest derived for veto at review.

1. **Mobile stage 1 rides v1.4 as non-flagship scope (operator).**
   Stage 1 + Dynamic-Breakpoints fold-in only; stages 2–4 (API surface,
   remote auth, native shell) explicitly out; the rider may not displace
   flagship milestones — if squeeze occurs, the deferral proposal goes
   to the operator (no unilateral deferral).
2. **Additive-only release (operator, standing).** Usage store, roles
   fragments, suggestion types, notify keys — all additive; legacy
   aliases untouched; no migration-runner pull-forward.
3. **Flagship-focused FV validation (operator, amended 2026-08-05).**
   Disposable Homes; source FV remains a cheap pre-filter, while attended
   packaged primary-function validation runs on one provisional exact-clean-SHA
   candidate before the authoritative aggregate. Findings use the standing
   environment/documentation/executable classification and bounded re-run
   cadence; no validation-only product capability.
4. **Confirmed customization is structurally forced (derived, ADR 0090
   §3).** `apply_suggested_customization` is `confirmation: :required`
   AND safety-floor-pinned by action name; the allowlist ships in code,
   reviewed, and categorically excludes permissions/security/egress/
   credentials/fallback gates; the confirmation renders the exact
   before→after diff.
5. **Suggestions stay inert (derived, ADR 0045 posture).** Accept-click
   creates a confirmation; nothing applies without approval; dismissed
   gains its writer; the resume-gap bug is fixed in M2.
6. **The usage store is additive, local, redacted, bounded (derived,
   ADR 0090 §1).** Never bodies/prompts/secrets (schema-level, eval-
   bound); cap + age retention keys; always-on (it is telemetry-free
   local bookkeeping, not tracing) with a kill switch
   `profiling.usage_events.enabled` default `true` — operator veto at
   plan review.
7. **Distill posture (derived).** Managed job, ReviewCadence pattern,
   `profiling.distill.*` keys, explicit activation (paused-default
   gotcha), zero-egress, local-model assist only under ADR 0089 LD-R5
   bounds; default cadence weekly, kill switch honored; quality floor
   measured on real fixtures (no synthetic-template evidence — the
   v1.1 M12.8 lesson).
8. **Per-role profiles are a naming layer (derived, ADR 0090 §4).**
   `model_roles.<role>.profile` fragments resolve through existing
   `Settings.Models`; no parallel resolver; purpose keys unchanged;
   chooser renders roles; remaps only via the confirmed path.

   **A remap may never change a role's egress class (operator decision
   2026-08-05).** Excluding the ADR 0088 fallback gates is not sufficient:
   `model_roles.fast.profile` is itself allowlisted, so a suggestion could
   remap a local role to a hosted profile and introduce egress without
   touching any gate. The allowlist enforces this **structurally** — a
   `model_roles.*.profile` write is admitted only when the proposed profile
   resolves to the same `provider_class`/`endpoint_kind` as the current
   value. Local→hosted is refused before a confirmation is created, exactly
   as a non-allowlisted key is. Enforcing in the allowlist rather than
   inside `apply_suggested_customization` keeps one refusal point and one
   denial row. The kernel-redo analysis reaches the same floor
   independently ("model role remap … never crosses the local/egress
   boundary").
9. **`:suggestion` notify kind per the ADR 0084 amendment (derived).**
   Separate opt-in default OFF; quiet hours + per-day rate limit
   additive keys; ledger/throttle/audit unchanged; notification is never
   an approval channel.
10. **Effectiveness is measured, displayed, never auto-acted (derived,
    ADR 0090 §5).** Suggestion → confirmation → audit linkage; next
    distill computes deltas; revert is one confirmed click; no
    automatic rollback.
11. **Gate = a bounded `release.v14` delta; the aggregate covers
    everything (derived, operator decision 2026-08-05).** `release.v14`
    is `@v14_focused_steps` only — it does **not** stack
    `@release_v13_steps`, and it does not replay `release.v13`,
    `release.v131`, `mix precommit`, or a full suite. This follows the
    pattern v1.3.1 established rather than the historical
    `v121 ++ v13 ++ …` accumulation, which the kernel-redo analysis
    measures at 43 never-retired gate definitions in one 10,117-line
    module. A structure owner test proves: the v1.3 and v1.3.1 gate
    definitions are unchanged, the v1.4 delta is bounded, and the
    authoritative `mix allbert.test release` phases cover **every** owner
    file set — v1, v13, v131, and v14 — without nesting any versioned
    gate inside another. Evidence `release_evidence/v14/`; docs-gate list
    updated at build start.
12. **Behavioral evals + automated flagship loop first (derived,
    standing).** `:v14` enum first; rows per request flow §G with the
    meta-contract; the seeded-usage → distill → confirm → apply →
    measure loop is a CI regression before FV exists.
13. **Mobile stage 1 acceptance is concrete (derived; standards cited
    2026-08-05).** Breakpoint token roles land in the design system doc +
    tokens; at 390×844: chat (composer usable, sticky, no horizontal
    scroll), objectives tree, settings central, memory review all operable;
    the 768 pin test evolves rather than breaks; no page-local CSS systems
    (ADR 0074 rule).

    **Touch targets: ≥44×44 CSS px is WCAG 2.2 SC 2.5.5 Target Size
    (Enhanced), Level AAA** — not the AA bar, which is SC 2.5.8 Target Size
    (Minimum) at 24×24 CSS px. v1.4 keeps the 44px figure (it also matches
    Apple HIG 44pt) and therefore claims AAA on this criterion; say so
    rather than implying it is the baseline. Where a dense surface cannot
    reach 44px, the documented fallback is the AA rule and its spacing
    alternative — a ≥24×24 target, or a smaller target with ≥24px offset to
    every adjacent target — recorded per surface rather than silently
    dropped.

    **Vertical viewport units are part of this milestone, not incidental.**
    `100vh` resolves against the *largest* viewport, so on a phone with the
    address bar visible the bottom of the layout is cut off — precisely the
    sticky-composer failure this stage exists to fix. Current tree: 10
    `dvh` uses already landed, but `min-height: 100vh` remains at
    `app.css:832,921,981` (plus `40vh`/`70vh` maxima at `:910,3147`). M7
    eliminates the raw `100vh` shells and chooses per site deliberately:
    **`svh` is the default** (fixed to the smallest viewport, so content
    fits on first paint), `dvh` only where a live-resizing height is
    actually wanted and is not animated — `dvh` changes value during scroll
    and causes jitter in transitions. `dvh`/`svh`/`lvh` reached Baseline
    Widely Available in June 2025 (~95% of users); keep a `vh` fallback
    declaration for the remainder.
14. **Fresh/disposable Homes for all scenarios (derived, standing).**

one-handed on your phone.

**Tailwind v4 breakpoint API and its unit trap (verified 2026-08-05).**
This app is Tailwind v4 CSS-first with no config file, and `app.css`
currently has **no `@theme` block** — M7 creates one. Breakpoints are
theme variables: `@theme { --breakpoint-<name>: <len>; }`, with
`--breakpoint-<name>: initial` to remove one and `--breakpoint-*: initial`
to reset them all before defining a custom set.

The trap: **breakpoints must all use the same unit.** Tailwind's defaults
are `rem`, and mixing `px` into them makes the generated utilities sort in
an unexpected order, so breakpoint classes override each other
unpredictably. Allbert's existing breakpoint is expressed in px (768, plus
the read-only `workspace.mobile.breakpoint_px` setting), so M7 either
declares the new roles in `rem` alongside the defaults or resets the set
with `--breakpoint-*: initial` and defines a complete px set. Convenient
fact: **768px is exactly 48rem, which is Tailwind's own `md` breakpoint**,
so the existing pin can be expressed as a role over `md` with no numeric
change and no drift against `workspace.mobile.breakpoint_px`.

**S8 — eval rows + gate (M8).** `:v14` enum FIRST; behavioral rows
(request flow §G) + meta-contract sweep; `@release_v14_steps` =
`@v14_focused_steps` (bounded delta per LD11, not stacked); the
coverage structure test over v1/v13/v131/v14 owner files; evidence
clone; docs-gate list.

## Kernel-Redo Interaction (analysis, not binding)

   landed before any release that relocates large numbers of files, which v1.5's

   of M1.
2. **The flagship design is on the sanctioned path.** §14 decides that routine-
   and graph-shaped work deepens Jobs and Objectives rather than creating another

   distill → typed delta → inert suggestion → confirmation → audited apply →

3. **One floor was adopted.** The analysis's delta-kind table independently

Not adopted here: the analysis's generalization of the allowlist into an

## Security Posture

This release adds one carefully-fenced application path and one
notification kind:

- **Confirmed customization is the only new effectful path.** Forced
  confirmation (contract + floor pin), shipped allowlist excluding
  permissions/security/egress/credentials/fallback gates, exact-diff
  confirmations, full audit linkage — gate-bound denial rows for each.
- **Suggestions and profiles grant nothing.** Cards are inert; the usage
  store is bookkeeping (no bodies/secrets, schema-proven); distill is
  zero-egress; ADR 0045's advisory posture holds everywhere else.
- **`:suggestion` notify is default OFF** on the single ADR 0084
  boundary with quiet hours and a per-day cap; a notification can never
  approve anything.
- **Role remaps ride the spine**: settings actions + confirmed path
  only; the fallback egress gates from ADR 0088 are not remappable via
  suggestions (allowlist exclusion). Additionally, a role remap may not
  change the role's egress class — the allowlist refuses a
  `model_roles.*.profile` write whose proposed profile resolves to a
  different `provider_class`/`endpoint_kind` than the current one, so a
  suggestion can never turn a local role hosted (LD8).
- Mobile stage 1 is presentation-only; no authority content.

## Non-Goals

- Automatic application of any suggestion; automatic rollback.
- Learned/trained profiling models (System Memory Distillation parked).
- Proactive notification classes beyond `:suggestion`.
- Legacy `intent.*model_profile` removal (migration-runner train);
  OAuth hosted providers (1.5 train; catalog lists, this plan does not
  auth).
- Mobile stages 2–4 (API surface, remote auth, native shell).
- New telemetry/egress of any kind; usage data never leaves the machine.
- Retention changes to conversations/traces beyond the usage store's
  own bounds.
